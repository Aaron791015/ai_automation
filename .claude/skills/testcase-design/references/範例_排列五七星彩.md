# 完整範例：排列五／七星彩 新彩種首次探索（2026-08-20）

> **這是 `testcase-design` 方法論的實例**，走過一遍真實流程：charter → 五來源盤點 → 風險與目標深度
> → 逐步加深 → 十問推導案例 → 阻塞排序 → 三份產出分流。
>
> ⚠️ **換產品時整份替換。** 方法在 `SKILL.md`，本檔只是彩票領域的例子。
>
> 真實產物：`docs/CRUX/CRUX_排列五與七星彩.md`（機制）、`_驗證項目清單.md`（覆蓋矩陣）、
> `bugs/_reports/需求驗證報告_排列五七星彩新彩種探索_2026-08-20.md`（報告）。

---

## ① Charter（開瀏覽器前寫）

```
探索目標：CRUX 新移植的兩個彩種（排列五 gameId=3、七星彩 gameId=4）全區塊
時間盒：  一個工作天（範圍大，分多段）
要回答： ① 這兩個彩種有哪些功能點？與既有的排列三／福彩3D 差在哪？
         ② 哪些有對照組可比？→ 七星原系統 p5_b.qat.st（CRUX 的模型來源）
         ③ 哪些涉及金流？→ 賠率、攔貨、中獎判定、報表全部是
風險假設：這是「移植」而非全新開發 → 最可能的缺陷型態是
         「排列三的邏輯被沿用到四球彩種但不適用」（玩法表、位數、基準值）
安全邊界：QAT 總監1，Web／UI 寫入已預先授權；結算與開獎會影響其他 session → 先不碰
```

## ② 五來源交叉盤點（→ 8 大區 50 個功能點）

| 來源 | 這次抓到什麼 |
| --- | --- |
| **選單樹** | 設置／攔貨／報表／帳號／前台 等主要區塊的功能點 |
| **API 端點** ⭐ | `GetPlayTypes` 回的 21 種玩法、6 分類 —— **選單上看不到玩法清單，只能從 API 拿** |
| **對照產品** ⭐ | 七星 p5 有「四定化賠率」概念 → 回頭確認 CRUX 這兩個彩種的賠率基準應是 **10000 不是 1000** |
| **權限矩陣** | 平台 `游戏配置` 與後台大股東編輯頁**各有一個彩種開關** → 兩層，缺一個會員就看不到 |
| **規格文件** | 七星 docx 附錄1 的計算公式；⚠️ **docx grep 不到，先取文字才查得到** |

> ⭐ **只點選單的話**，會漏掉「玩法表結構」與「賠率基準應為 10000」這兩個**最關鍵**的功能點——
> 而後者正是本次最大的一批缺陷（CRUX-077 賠率只有應有值的 26～40%）。

## ③ 標風險 → 得出目標深度

| 區 | 功能點例 | 風險 | 目標 |
| --- | --- | --- | --- |
| A 定盤 | 賠率上下限值 | 金流 | **L4** |
| A 定盤 | 玩法獨立修改 checkbox | 顯示 | L2 |
| C 攔貨 | 虛盤四定化攤分 | 金流 | **L4** |
| D 報表 | 利潤率日報表 | 金流 | **L4** |
| F 前台 | 開獎號碼頁欄位 | 顯示 | L2 |
| H 其他 | 切換彩種的頁面行為 | 邊角（已有 5 張 JIRA 在處理） | L1 |

**得到的規劃資訊**：50 個功能點中，目標 L4 的有 ~20 個、L3 ~12 個、L2 ~13 個、L1 ~5 個。
本次實際達到：L0×18、L1×15、L2×8、L3×8、L4×1 → **達標 9/50**，剩餘 41 項就是待辦。

## ④ 逐步加深（不是逐頁做到底）

```
①② 選單樹＋API      → 50 個功能點初稿
③  逐頁 L1          → 立刻發現「四球四字现 5 玩法賠率為 0、不可下注」（CRUX-078）
                       ⭐ 這是 L1 就抓到的大問題，不必等 L3
④  挑對照組 L2       → 拿七星 p5 比對定盤值、利潤率單位、開獎欄名
⑤  挑有公式的 L3     → 虛盤四定化攤分逐項驗算（二定 ¥1 → 每四定 ¥0.01）
⑥  L4 只做要開單的   → 賠率上下限（CRUX-077 的佐證）
```

## ⑤ ★ 十問推導：從 1 個功能點推出 6 條案例

**功能點 A4「最小下注／單注上限／單項上限」，本次深度 L1（只清點了欄位）。**

逐一套用十問：

| # | 提問 | 這個功能點的答案 | 成為案例？ |
| --- | --- | --- | --- |
| ① | 可設定 vs 真生效 | 後台存得進去 ≠ 前台真的被擋 | ✅ **兩條**（A4-1、A4-2） |
| ② | 正向 vs 反向 | 超過要擋；**等於上限不該被誤擋** | ✅ A4-3 |
| ③ | 邊界與非法值 | 等於上限、上限＋0.01、0、負數、空值 | ✅ 併入 A4-2／A4-3 |
| ④ | 前端擋 vs 後端擋 | UI 擋住了，API 直送呢？ | ✅ A4-4 |
| ⑤ | 不變量 | 單項上限應 ≥ 單注上限 | ✅ 併入 A4-5 的斷言 |
| ⑥ | 樣本有鑑別力嗎 | ⚠️ **必須挑「上限值 ≠ 預設值」的玩法**，否則改不改都一樣，驗不出生效 | ➡️ 影響選樣，不另立案例 |
| ⑦ | 狀態轉移 | 封盤後改上限？→ **不適用**：封盤後本來就不能下注，無從驗證生效 | ⛔ 不適用（記理由） |
| ⑧ | 多條件組合 | 單注上限 × 單項上限 × 信用額度 三者同時限制，**誰先擋？** | ✅ A4-5（決策表） |
| ⑨ | 多層級傳遞 | 上級設了上限，下級能不能設更大？新建下級繼承嗎？ | ✅ A4-6 |
| ⑩ | 時序邊界 | 期中改上限，當期已下注的怎麼算？ | ⚠️ **未驗**（適用但這次沒做，進分母不進分子） |

### 推導結果：案例清單

| # | 案例 | 被測行為 | 預期（oracle） | 前置（可 API 加速？） | marker | 對應矩陣項 |
| --- | --- | --- | --- | --- | --- | --- |
| A4-1 | 後台設定單注上限後儲存，重新整理可回讀相同值 | 後台設定寫入 | 回讀值＝填入值（**B：對照七星同頁行為**） | 帳號鏈可 API 建 | write_action | A4 |
| A4-2 | 前台下注**超過**單注上限被擋並提示 | **前台下注** | 被拒絕（**A：規格文件的限額規則**） | 需先完成 A4-1 | write_action | A4 |
| A4-3 | 前台下注金額**等於**上限可正常成交 | 前台下注 | 成交（**A：同上，「上限」為可取值**） | 同上 | write_action | A4 |
| A4-4 | 繞過 UI 直接以 API 送出超限金額 | **後端檢核** | 後端亦拒絕（**B：不變量——前端檢核不應是唯一防線**） | 取 token | write_action | A4 |
| A4-5 | 單注上限／單項上限／信用額度三者同時限制時的優先序 | 檢核優先序 | 依決策表（**C：需向 RD 確認，先標 C 級**） | 需三個值互相衝突的設定 | write_action | A4 |
| A4-6 | 上級上限對下級的約束與新建下級的繼承 | 多層級傳遞 | 下級不得超過上級（**B：對照占成的逐層遞減模型**） | 需兩層帳號 | write_action | A4 |

> ⭐ **一個標「L1 未驗生效」的功能點，推出 6 條案例、1 條不適用、1 條未驗。**
> 覆蓋度寫法：**6/7 適用項已設計**（另 1 項⑦不適用，已記結構性理由）。

## ⑥ 依阻塞關係排批次

```
① 等 RD 修完賠率（CRUX-077／078）
   └─ 賠率不對時，A2／A5／A8／C1～C3／D6 全部驗不準 ← 先做也是白做
② 建一條完整鏈並設攔貨與回水
   └─ 這是後面所有金流驗算的前提
③ 結算一期完整走完（中獎判定 → 日報表 → 分類帳 → 帳單）
④ 控盤與分批
⑤ 報表全家族對帳
⑥ H5、總控、切換彩種 ← 多數已有他人的 JIRA 在處理，修完再回歸
```

⚠️ **不是照選單順序做**。照選單順序會先驗報表，而報表數字全部依賴①②。

## ⑦ 三份產出分流

| 這次學到的 | 寫到哪 |

| 21 種玩法表、只取前四球、四定化賠率公式、快譯語法 | **機制文件** `CRUX_排列五與七星彩.md` |
| 50 個功能點的深度、還要驗什麼、前置環境、批次順序 | **覆蓋矩陣** `_驗證項目清單.md` |

| 「11 項已查證的非缺陷，勿重開」 | 機制文件的附錄 ＋ `crux` skill 意圖對照 |
