# 測試案例設計

> **本 skill 管「驗什麼、幾條、多深、什麼順序、期望值哪來」。**
> 不管怎麼操作瀏覽器（`browser-ops`）、怎麼寫 pytest（`ui-test`）、怎麼開單（`bug-report`）。

**兩個產物，上下游關係**：

```
五來源交叉 ──▶ 【產物一】覆蓋矩陣 ──套十個提問──▶ 【產物二】案例清單 ──▶ pytest
              （功能點層級：還有什麼沒驗）        （案例層級：要跑哪些）
```

⚠️ 只做產物一 → 功能點盤完卻停在 L0，沒轉成案例。
⚠️ 只做產物二 → 有案例可跑，卻不知道**還有什麼沒盤到**。**兩個都要有。**

---

## 1. 功能點盤點：五個來源交叉

**單靠點選單必然漏。** 五個來源各自漏掉不同的東西，交叉才算盤完：

| 來源 | 怎麼取 | 抓得到 | 會漏掉 |
| --- | --- | --- | --- |
| **選單樹** | 逐層展開導覽列，逐頁記錄 | 有入口的功能 | **沒有入口的功能** |
| **API 端點** | 掃前端載入的 JS chunk、開 network 面板重走一次 | 有 API 但選單未露出的 | 後端才有、前端未接的 |
| **對照產品** | 同源或同類產品有的，這裡應該也有 | **移植時漏掉的功能** | 兩邊都沒有的 |
| **權限矩陣** | 換身份再看一次（主帳號 vs 子帳號、各層級） | 只有特定身份看得到的 | — |
| **規格文件** | 需求單、規格書、玩法定義 | **尚未實作的、規格有但沒做的** | 沒寫進文件的 |

〔例〕靠來源② 才發現「某些功能在後台完全沒有入口」——掃前端 78 個 JS chunk，
目標端點命中數皆 0，才確認不是自己沒找到。

**產出**：覆蓋矩陣每列標來源，讓「為什麼有這一列」可追溯。

## 2. 深度分級 L0～L4

| 級別 | 判準 |
| --- | --- |
| **L0** | 完全沒開過／沒查過 |
| **L1** | 頁面開得起來、欄位與選項清點過，**但沒比對值** |
| **L2** | 值與規格／對照組比對過 |
| **L3** | **有算式明細**，實際值 vs 期望值逐項對得起來 |
| **L4** | 實際寫入或操作，並回頭驗證結果與還原 |

> ⚠️ **L1／L2 不等於通過** —— 只代表「當時看起來沒問題」。
> 後續詳驗一律以「該項要達到目標深度」為目標，**L1／L2 的項目都要重做**。

---

## 3. ★ 風險決定「該做到哪一級」

L0～L4 若只用來記錄「做到哪了」，它就只是流水帳。**加上目標深度才成為規劃工具**：

| 風險類別 | 判準 | 目標深度 |
| --- | --- | --- |
| **金流／核心計算正確性** | 影響金額、數量、判定結果、對帳數字 | **L4**（端到端，含還原） |
| **資料完整性** | 寫入是否真的生效、是否留下稽核紀錄 | **L3**（算式或逐欄比對） |
| **權限與越權** | 誰看得到、誰改得動 | **L3**（正反向都要） |
| **顯示與互動** | 欄位標籤、排版、下拉行為 | **L2**（比對規格即可） |
| **邊角／他人處理中** | 已有單在跑、與主流程無關 | **L1**（清點後標記，等修完再回歸） |

**用法**：盤點完先標風險 → 得到目標深度 → **與「本次深度」的差距就是待辦**。
覆蓋矩陣因此能自己算出剩餘工作量（`scripts/coverage_matrix.py`）。

## 4. ★ Oracle 分級：期望值到底哪裡來

「不知道該驗成什麼樣」的根源是 **oracle 問題**。手上通常有多個 oracle，**可信度不同**——分錯級會把缺陷寫成規格。

| 級別 | 來源 | 使用注意 |
| --- | --- | --- |
| **A** | **權威規格文件**（規格書、玩法定義、計算公式附錄） | ⚠️ docx／PDF／xlsx **grep 不到**，要先取文字再查 |
| **A** | **使用者／PM 的裁定** | ⛔ 帶裁定來源的陳述**不得改寫**（見 CLAUDE.md 的共用檔紀律） |
| **B** | **對照產品**（同源系統、同類頁面） | ⚠️ 移植可能有**刻意的差異**，不符時先查有無變更聲明 |
| **B** | **驗算不變量**（恆等式、守恆關係） | **只能證偽不能證真**——對得上不代表公式對 |
| **C** | **RD 留言**（單子上給的預期值） | 是「RD 認為的」，不等於規格。可當斷言依據但**要註明來源** |
| **D** | ⛔ **系統現況**（實測值） | **不能當 oracle**。只能證明「現況是什麼」，**證明不了「現況是對的」** |

> ⛔ **這張表是 CLAUDE.md「實測與文件不符時」那條規則的正面表述。**
> 曾經發生過：用 D 級（實測）反推規格而把方向寫反；把缺陷改寫成規格。
> **設計案例時就先寫下 oracle 是哪一級**，驗證時才不會臨時拿實測當基準。

**寫進案例清單的 `預期（oracle）` 欄**：期望值 ＋ 來源級別 ＋ 出處。

## 5. 案例推導：十個提問

對每個功能點依序問。**能問出具體答案的才成為案例**；問不出來的標「不適用＋結構性理由」
（三分法：已驗／未驗／不適用，**不適用不進分母**——見 `jira-verify` 的覆蓋度規範）。

### 通用四問

| # | 提問 | 為什麼常漏 |
| --- | --- | --- |
| **① 可設定 vs 真生效** ⭐ | 「填得進去」和「真的作用」是**兩條案例** | **最高頻的漏洞**。設定類功能很容易只驗「存得起來」，沒驗「前台真的被擋／真的按新值計算」 |
| **② 正向 vs 反向** | 該生效的生效了；**不該變的有沒有被改壞** | 只驗正向會漏掉「改 A 壞了 B」 |
| **③ 邊界與非法值** | 等於上限、上限＋最小單位、空值、超長、負數、值域外 | — |
| **④ 前端擋 vs 後端擋** | 前端擋住**不代表 API 擋得住** | 只點 UI 驗不到後端缺口 |

### 領域兩問（★ 依產品替換——本節的例子是彩票金流）

| # | 提問 |
| --- | --- |
| **⑤ 有沒有可自檢的不變量** | 恆等式、守恆關係。有的話每條案例都該附帶檢查〔例：賠率 × 中獎組合數 ≈ 定值；各層占成加總守恆〕 |
| **⑥ 樣本有鑑別力嗎** | **兩種假說會給出不同答案的資料才有用**。〔例：某參數為 0 時新舊公式同值 → 該樣本驗不出差異〕 |

### 結構四問

| # | 提問 |
| --- | --- |
| **⑦ 狀態轉移合法嗎** | 畫出狀態機，**每個轉移一條案例**；**非法轉移要驗「被擋住」**；異常態要能**主動製造與還原**，不能只是「觀察到過」 |
| **⑧ 多條件組合列全了嗎** | 用**決策表**：條件 × 組合 × 期望結果，刪掉不可能的組合，每列一條案例。多開關疊加時特別容易漏 |
| **⑨ 多層級會不會傳遞** | 階層式系統的設定要驗四件事：**該層生效／下層連動（或不連動）／上層不受影響／新建的下級是否繼承** |
| **⑩ 時序有沒有邊界** | 週期切換的瞬間、截止前後、跨週期操作、日切時點。高頻系統尤其要驗 |

## 6. ★ 組合爆炸的收斂

當「玩法 × 彩種 × 層級 × 分類」相乘到不可能全測時，**依序套用**五個手段：

| 手段 | 做法 |
| --- | --- |
| **1. 分層抽樣** | 每個分類挑 1 個代表，而非全跑 |
| **2. 邊界優先** | 分類的第一個與最後一個 |
| **3. 挑有鑑別力的** ⭐ | 兩假說給不同答案的樣本〔例：一組玩法中只有一個的上下限與另一組定義不同 → **要驗來源只能用它**〕 |
| **4. 風險加權** | 金流全測、顯示抽樣（對應 §3 的目標深度） |
| **5. 兩兩組合（pairwise）** | 不做全笛卡兒積，只保證任兩個因子的組合都出現過 |

> ⚠️ **收斂後必須記錄「抽樣依據」** —— 否則下一個人不知道你是**抽樣**還是**漏了**。
> 寫進覆蓋矩陣的「後續詳驗要點」欄。

## 7. 批次排序：依阻塞關係，不依模組順序

問的是「**什麼沒做好會讓後面驗不準**」：

```
① 阻塞型缺陷先修          基礎數值不對 → 所有相關驗算都不準
② 建立前提資料            完整的層級鏈、各項設定 → 後面所有驗算的基礎
③ 走完一個完整生命週期     建立 → 執行 → 結算 → 報表
④ 設定類功能              各種開關與參數
⑤ 報表全家族對帳
⑥ 邊角與他人處理中的       等他人修完再回歸
```

## 8. 前置環境清單化

固定三欄：`項目 / 現況 / 說明`。

⚠️ **必須標出「尚未具備」** —— 那是下一步要先做的事，不是可以跳過的欄位。
〔典型項目：可操作的資料狀態、可用的帳號鏈、對照用的基準環境、特定情境的樣本〕

## 9. 兩個產物的標準欄位

### 產物一：覆蓋矩陣

| 欄 | 說明 |
| --- | --- |
| `#` | 區塊字母＋序號（A1、C4） |
| `功能點` | 一句話 |
| `來源` | 選單／API／對照／權限／規格（§1） |
| `風險` | 金流／資料／權限／顯示／邊角（§3） |
| `目標` | L0～L4，**可留空由腳本依風險推導** |
| `本次` | L0～L4 |
| `已知缺陷` | 單號 |
| `後續詳驗要點` | 要驗什麼、為什麼、阻塞於什麼、**抽樣依據** |

### 產物二：案例清單

| 欄 | 說明 |
| --- | --- |
| `#` | 組別＋序號 |
| `案例` | **測試對象 ＋ 情境 ＋ 預期結果** |
| `被測行為` | 決定哪些步驟必須走 UI（CLAUDE.md §5：被測行為一律走 UI） |
| `預期（oracle）` | 期望值 ＋ **來源級別 A/B/C**（§4） |
| `前置（可 API 加速？）` | 明寫「否——建立本身是被測行為」 |
| `marker` | smoke／write_action |
| `對應矩陣項` | 回指產物一的 `#`，**建立雙向追溯** |

**另外兩件事要寫在清單裡**：
- **依賴順序**（`B1、B2 → B3 → B4`）——有前置關係的案例要標明，否則執行順序錯就連鎖失敗
- **驗證鏈展開**——一條案例若含多個驗證點，逐點列出（這是「一個功能點推出多條案例」的實例）

### 解析腳本

```powershell
python scripts\coverage_matrix.py --file <矩陣.md>            # 統計與缺口
python scripts\coverage_matrix.py --file <矩陣.md> --gaps     # 只列差距最大的
python scripts\coverage_matrix.py --file <矩陣.md> --lint     # 格式完整性（缺欄位／缺標記）
python scripts\coverage_matrix.py --file <矩陣.md> --cases <案例清單.md> --orphans
                                                              # ★ 盤到了卻沒推成案例的功能點
```

## 10. 探索方法論

### 10.1 ★ 先寫 Charter 再開瀏覽器

時間盒 60～90 分鐘：

```
探索目標：<哪個功能區塊>
時間盒：  90 分鐘
要回答： ① 這區塊有哪些功能點？（五來源交叉）
         ② 哪些有對照組可比？
         ③ 哪些涉及金流／核心計算？（決定目標深度）
風險假設：<我預期哪裡會出問題，為什麼>
安全邊界：<本次唯讀？可寫入？哪些操作要先確認>
```

**收工時對照 charter 回答四件事**：涵蓋了什麼／發現什麼／還有什麼沒探／被什麼阻塞。
→ 正好是覆蓋矩陣、Bug 單、L0 項目、前置環境清單的輸入。

### 10.2 系統性探索路徑

```
① 不動任何東西，先把選單樹展開記錄     → 功能點初稿
② 開 network 面板重走一次              → 補 API 端點
③ 逐頁 L1（清點欄位與選項，不比對值）
④ 挑「有對照組」的做 L2
⑤ 挑「有公式」的做 L3                   → 這步才需要算式明細
⑥ L4 只做「這次要開單」或「規格待確認」的
```

> ⭐ **逐步加深，不是逐頁做到底。**
> 先讓 50 個點都到 L1，比讓 5 個點到 L4 更有價值 ——
> **L1 就能發現「這裡有個功能完全沒實作」這類大問題。**

### 10.3 三份產出的分流

| 產出 | 裝什麼 | 放哪 |
| --- | --- | --- |
| **機制文件** | 這東西怎麼運作（規則、公式、語法） | `docs/<產品>/` |
| **驗證項目清單** | **還要驗什麼**（覆蓋矩陣） | `docs/<產品>/` |
| **驗證報告** | **這次驗到什麼**（實際值、算式、截圖） | `docs/<產品>/bugs/_reports/`（不版控） |

⚠️ **三者不可混寫** —— 混了之後「還要驗什麼」會被埋進報告，下一個 session 找不到。
落筆分流的完整規範見 `writeback` skill。

### 10.4 什麼時候算探完

三個條件**同時**成立：
1. 五來源交叉後**沒有新的功能點**冒出來
2. **每個功能點都有深度標記**（含 L0）
3. 前置環境清單中「**尚未具備**」的項目都已列出
