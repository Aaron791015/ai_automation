# UI 自動化測試開發流程

## 階段 0：任務描述檢查（開工前必做）

理想的任務描述包含以下四要素，範例：

```
/ui-test
目標：CRUX 總監後台「代理管理 > 下級列表」
情境：總監建立一名代理後，於下級列表以帳號關鍵字搜尋
預期：列表顯示該代理，且層級、狀態欄位正確
寫入許可：本次不要建新帳號，用既有的 netgs34（不填＝依 CLAUDE.md §5 授權表）
```

| 要素 | 說明 |
| --- | --- |
| **目標** | 產品 + 前/後台 + 頁面路徑，探索時直奔目標 |
| **情境** | 操作步驟粗描述（做什麼即可，selector 細節由探索階段補齊） |
| **預期** | 明確驗收條件，避免只驗「頁面有出現」的弱斷言 |
| **寫入許可** | 是否允許建立資料。⚠️ 預設已由 CLAUDE.md §5 授權表決定（QAT 的 Web／UI 寫入**已預先授權**），本欄只在**要收窄**（如「這次不要建帳號」）或**要動 STG** 時才需填 |

**檢查規則**：

- 缺「目標」或「預期」→ **先反問使用者補齊**，不猜測開工。
- 缺「情境」→ 可先探索頁面後提出案例清單，經確認再實作。
- 缺「寫入許可」→ 依 **CLAUDE.md §5 授權表**：QAT 的 Web／UI 寫入**直接執行、不必逐項請示**；
  QAT 的 DB 一律唯讀（唯一例外：重置期數改 `DrawTime`）；STG 與影響全盤的操作仍須先確認。
- 若任務涉及可走 API 加速的步驟，先向使用者確認**這條案例的被測行為是什麼**，據此判斷哪些步驟必須走 UI（見階段 2 的 API 加速規則）。
- 任務範圍若橫跨多個功能區塊，建議拆成多個任務逐一進行（測試檔與 commit 較乾淨），並向使用者提出拆分方案。
- **判斷是否為新專案**：若目標專案在 `config/` 無環境設定、`tools/` 無對應測試框架、或 `docs/<專案>/` 無 UI 對照文件 → 改走下方「**分支流程：新專案首次探索**」，完成後才回到標準階段 2。

## 分支流程：新專案首次探索

適用：首次對一個尚無基礎設施的專案進行探索。**本分支全程唯讀，不實作測試**；產出經使用者確認後，後續任務才走標準階段 2–4。

> ### ⭐ 先確認這個產品是否已經「接進來」
> 若 `docs/<產品>/`、產品 skill、交接檔都還不存在 → **先跑一次**：
> ```powershell
> python scripts\new_product.py --id <產品名> --docs-dir <目錄名> --bug-prefix <前綴> --alias <英文名>
> ```
> 它會建好目錄骨架與交接檔並註冊產品；**本分支從「步驟 1 補齊環境設定」接續**。
>
> ### ⭐ 探索的方法論在 `testcase-design`
> 本分支只講「新專案要補哪些基礎設施」。**怎麼探索**（先寫 charter、五來源交叉盤點功能點、
> 逐步加深 L1→L4、產出覆蓋矩陣）一律見 **`testcase-design` skill §1／§10**。

### 步驟 1：補齊環境設定

1. 向使用者索取（若任務未提供）：環境 URL、登入帳密、入口路徑、目標頁面。
2. 依 `config/` 慣例補進設定：非敏感（URL、QAT 測試帳密）→ `environments.md` 與 `environments.json`；敏感（token、連線字串）→ `config.local.json`（不版控）。
3. 之後同專案的任務即可不再重複提供環境資訊。

### 步驟 2：唯讀探索

1. 載入 `browser-ops`，依其規則開瀏覽器登入並探索目標頁面。
2. **安全邊界（必守）**：見 `browser-ops` §6 —— 本分支**全程唯讀**，不投注、不建帳號、不改設定、不送出任何表單。
3. **高頻系統加記時序元素**：開獎倒數、期號切換、封盤/開盤狀態的元素與變化時機（後續併發、時序測試的關鍵素材）。
4. **外掛系統（如投注機器人）跨系統對照**：記錄其設定與七星主系統前台行為的對應關係，探索時兩邊畫面互相印證。

### 步驟 3：建立框架骨架

1. 在 `tools/` 建立該專案的測試框架目錄（參考 `crux_qa` 結構：`config_loader`、`pages/` POM）。
2. 只建**探索過頁面**的 page object 骨架（登入頁 + 目標頁），selector 走語意定位；不預先猜測未探索頁面。

### 步驟 4：產出與確認

1. 依 **`writeback` §1 的分流表**落筆，回寫後的四個必做見 **`writeback` §3**。
   ⚠️ 本階段最常犯的錯：**把操作程序與功能機制混進 `UI元素對照_*.md`** ——
   UI 對照檔只裝頁面路徑、元素定位、時序元素與 API 契約。
2. 提出**建議測試案例清單**（標明各案例的被測行為、是否需 write_action、可否 API 加速前置）。
3. 向使用者摘要並**等待確認**案例清單後，才進入標準階段 2 實作。

依序執行以下四個階段。各階段規則**必須**遵守，與 CLAUDE.md 衝突時以 CLAUDE.md 為準。

## 階段 1：探索 UI

> **瀏覽器怎麼操作見 `browser-ops` skill** —— session 隔離紀律、語意定位、自訂元件輸入陷阱
> （`press_sequentially`／假輸入框／分頁各存各的 API）、攔 payload 驗證真實寫入、轉場觀察法、
> 探索安全邊界與備援方案，都在那裡，本階段不重複。

1. 先載入 `browser-ops`，依其規則操作。環境資訊從 `config/environments.json` 取得
   （敏感資訊在 `config/config.local.json`）。
2. **本階段的產出目標**：頁面路徑、元素定位方式、可靠輸入法、相關 API 契約、踩到的陷阱。

### 探索結果回寫

> ⛔ **不要把所有東西都倒進 `UI元素對照_*.md`。**
> 探索一次會挖出好幾類知識，**分流表見 `writeback` §1**（全工作區的權威），
> 回寫後的四個必做見 **`writeback` §3** —— 本節不重複列。
>
> 只提醒本階段最容易搞混的一條：**操作程序與功能機制要另立檔**，
> UI 對照檔只裝頁面路徑、元素定位、時序元素與 API 契約。

## 階段 2：撰寫測試

> ### ★ 動筆前先確認案例是「設計」出來的，不是「想到什麼寫什麼」
> 該驗哪些、設幾條、驗到多深、期望值哪裡來 —— 見 **`testcase-design` skill**
> （五來源盤點／風險決定目標深度／Oracle 分級／推導十問／組合收斂）。
> 本階段只管「怎麼把設計好的案例寫成 pytest」。

1. Page objects 置於 `tools/<產品>_qa/pages/`（CRUX＝`crux_qa`、投注機器人＝`wbot_qa`），selector 走**語意定位**（get_by_label / get_by_role / 文字），避免脆弱的 CSS/XPath。
2. 測試案例置於 `tests/<產品>/`，命名需可看出**測試對象 + 情境 + 預期結果**。
3. 標記 pytest markers：`smoke`（不寫入資料）、`write_action`（實際寫入測試環境）。
   ⚠️ marker 只是**標示**，執行授權依 CLAUDE.md §5 授權表（QAT 的 Web／UI 寫入已預先授權）。
4. 會建立資源（如帳號）的測試需自動避重（流水號偵測遞增，`tools/crux_qa/account_naming.py`），重跑不得因重名失敗；建立的帳戶輸出 manifest 至 `reports/created_accounts/`。
5. **案例須留「驗證過程與佐證」（非僅截圖）**：每條案例的 allure 附件要能讓人看出**驗了什麼、佐證為何**——列出比對的**實際值 vs 期望值**（附公式/規格依據）、以及貨量/最大損失等的**組成來源明細**（如大類卡的組成號碼與各分量、驗證號碼關聯的注單/玩法）。PASS 與 FAIL 一律用**同一種可讀的算式明細**呈現，不得只附截圖。（教訓：虛盤001 一致性案例曾只附截圖、無數據紀錄，無法判讀「展開的組三多碼合計來自哪些號碼」而驗證過程不完整。）

### 步驟與判準（`scripts/lint_cases.py` 的守門依據，2026-08-29 補）

> 這節填的是 `lint_cases.py` 錯誤訊息裡引用、但先前一直沒寫的那節——腳本已經在守門，
> 規範卻沒有落地成文字，屬於 CLAUDE.md §1 記過的同一種失效模式（「規則已寫在 skill 裡，
> 但那是格式說明、不是會被執行的檢查」的反過來版本：**檢查已經在跑，格式說明才補上**）。

- **每條案例的操作，用 `with allure.step("…"):` 包起來**——粒度是「一組有意義的動作」，
  不是每一行都包一次。例：「導覽到頁面＋切分頁」算一步，不必拆成兩步。
- **每條案例只要有 `assert`，函式本體（或它呼叫的 helper）裡就要有至少一次 `allure.attach(...)`**，
  內容寫**實際值 vs 期望值**（呼應上面第 5 條），不是隨便貼一段文字充數。
  ```python
  with allure.step("讀取「状态」下拉選單"):
      options = ah.status_options()
  allure.attach(
      f"實際選項：{options}（期望：['启用', '停用', '停押']）",
      name="狀態下拉選項",
      attachment_type=allure.attachment_type.TEXT,
  )
  assert options == ["启用", "停用", "停押"]
  ```
- **重複案例（多層級／多分頁共用同一套驗證邏輯）優先把 step／attach 寫進共用 helper**，
  不要每個案例各寫一份——`lint_cases.py` 的檢查會**往下追一層同檔 helper**，
  helper 補好，呼叫它的所有案例會一起過關（見 `tests/xzh/test_user_management.py` 的
  `_check()`：一次補好，十個層級的 `*_count_matches` 全部一起滿足）。
- **執行**：`python scripts\lint_cases.py --product <目錄名>`；`--all` 連已豁免的也列出來。
  規範上路前就存在的案例可建一份 `tests/<產品>/case_steps_baseline.json` 豁免（**只減不增**，
  補好一條就從名單刪一條），細節見該腳本檔頭。
- ⚠️ **這是靜態解析，不是執行結果**：`allure.step`／`allure.attach` 本來是執行期才記錄的東西，
  test_platform 案例瀏覽器（`pytest_case_export.py`）用 `pytest --collect-only`（不執行）
  抓的是「案例原始碼寫了什麼」，不是「這次跑出來的值」。要看真正的執行結果仍要看 allure report。
- ⚠️⚠️ **`allure.step("...")` 的字串本身要寫出具體內容，不能只寫概括說法**（2026-08-31，
  xzh B26 踩到）——`pytest_case_export.py` 的 `_step_texts()` 只讀**字面字串**，不會展開
  f-string 變數（變數值要真的執行才看得到，test_platform 的靜態案例瀏覽器看不到）。
  例：`with allure.step("讀取表頭欄位、8 個分組收合按鈕")` 在 test_platform 上完全看不出
  是哪 6 個欄位、哪 8 個分組；要改成
  `with allure.step("讀取表頭 6 欄位（玩法／自留口径／每选项自留上限／…）、8 個分組（连码／连肖／…）")`，
  把具體名稱直接寫進字串，test_platform 才顯示得出來。**這是本工作區新綜合（xzh）產品
  案例的固定寫法，之後生成／新增 xzh 案例一律比照辦理**；其他產品若同樣用 test_platform
  瀏覽案例，也適用同一個限制。
- ⛔ **`allure.step("...")` 的字串不能用隱式多行串接**（`"上半段"` 換行 `"下半段"` 兩個字面值
  黏在一起）——`_lit()` 用 `ast.literal_eval()` 解析，只對第一行做 `lstrip`，後續行的縮排
  會讓 `ast.parse(..., mode='eval')` 噴 `IndentationError`，退回顯示帶引號的原始碼片段
  （字面上印出 `"讀取表頭...` 這種東西），不是還原後的文字。**再長也要寫成一行字串**，
  或改用變數先組字串再傳進 `allure.step()`。
- ⚠️⚠️ **「一個共用 helper、被多個測試函式呼叫、用參數帶入具體值」是另一種會踩到同一個雷
  的結構**（2026-08-31，`test_user_management.py` 的 `_check(company_page, level)` 踩到，
  跟上面「迴圈」是不同情境，容易搞混）——迴圈是**一個測試函式內部**跑好幾個對象，靜態
  瀏覽器只看得到迴圈模板，用「迴圈外加一步總覽」補救即可；但**共用 helper 被多個獨立測試
  函式各自呼叫一次**（如 10 個 `test_levelN_agent_count_matches` 都呼叫同一個
  `_check(company_page, "X级代理")`），若把 `f"...{level}..."` 這個 step 寫在 helper
  裡面，**10 個測試在 test_platform 上會全部顯示同一個沒解開的 `{level}` 佔位符**，
  完全分不出哪個函式測的是哪個層級——這裡沒有「總覽」可以補，因為 10 筆是分開的案例，
  不是同一案例內的迴圈。**正確做法**：把帶層級名稱的那個 step 移出 helper，改成由
  **每個呼叫端**自己用具體字面值包一層 `allure.step`（例：
  `with allure.step("導覽到「用户管理」頁，切換到「一级代理」子頁面"): _check(company_page, "一级代理")`），
  helper 內部只留跟具體值無關的共用步驟。判斷準則：**helper 的參數如果會被拿去組
  `allure.step` 的字串內容，這個 step 就不能留在 helper 裡**，要下放給呼叫端。

### API 加速規則（重要）

- API 只能用於「**非被測行為**」的前置資料準備。
- 案例的**被測行為本身一律走 UI**，不得以 API 取代：
  - ✅ 測「下級列表顯示」→ 前置帳號可用 API 建立。
  - ❌ 測「建立帳號」→ 建帳號動作必須走 UI 操作。
- API 批量寫入後，**結果仍需以 UI 重讀驗證顯示正確**。
- API 認證走 `localStorage.jwtToken` 的 `Authorization: Bearer`。

### 複雜表單／建立資源案例的注意事項（實戰教訓）

- **跨操作狀態污染／順序依賴**：某些設定會影響後續操作或後續建立的帳戶（如 CRUX 上級一旦設福利，會使其之後新建下級的信用額度控件失效）→ 可能需**調整測試順序**（例如先建整條鏈設好基本屬性、最後才統一設另一類設定）。遇到「單獨操作成功、完整流程失敗」時，優先懷疑狀態污染。
- **context／導航**：多層級操作不要依賴前次操作殘留的頁面 context，開戶/編輯前用 URL 或明確導航定位到目標列表。
- **公告等彈窗**會攔截點擊，關鍵操作（點編輯、點按鈕）前先關閉並在失敗時重試。

## 階段 2.5：增量驗證（省時關鍵，務必遵守）

未知 UI 的操作可靠性未知，**切勿寫完整案例後直接跑完整測試賭全對**——完整跑動輒十餘分鐘，反覆「跑完整→失敗→改→再跑」極度耗時（本專案首次任務即因此耗費大量時間）。

**作法見 `browser-ops` §7**（逐一驗證關鍵操作 → 由小到大 → 失敗時用 probe 重現那一步）。

## 階段 2.6：⛔ 紅燈有兩種，處置**完全相反**

**這是本 skill 最重要的一節。**

| 紅燈是什麼 | 怎麼處置 |
| --- | --- |
| **案例寫錯了**（selector、fixture 名、期望值算錯、前置沒備好） | 修到綠 |
| **案例抓到缺陷了**（判準是對的，系統行為不符規格） | ⛔ **不准動判準把它弄綠** |

把一條抓到缺陷的案例改成 PASS，等於**用測試把 bug 合法化**。
這是 `CLAUDE.md`「實測與文件不符時」那條規則的案例版 ——
差別只在載體是測試碼而不是機制文件，**嚴重程度一樣**：
之後沒有人會再去驗它，因為「那條是綠的」。

⭐ **回歸案例在缺陷修好之前，本來就該是紅的** —— 那是它該有的樣子，
不是待修的問題。標記它、寫明對應的 Bug 單即可。

⛔ 判不出是哪一種時：**當成抓到缺陷**（去走 `bug-report` §3.9 的開單前三問），
不要先把判準改鬆。改鬆之後就再也沒有訊號了。

## 階段 2.7：整檔跑兩次（案例交出去之前）

逐條跑（階段 2.5）抓不到下面兩類，**只有整檔跑才會現形**：

```powershell
.venv\Scripts\python.exe -m pytest <檔> -q      # 第一次：互相影響
.venv\Scripts\python.exe -m pytest <檔> -q      # 第二次：可不可以反覆執行
```

| 跑第幾次 | 抓什麼 |
| --- | --- |
| 第一次（整檔） | **互相影響** —— 共用 fixture、前一條沒還原站台狀態、順序相依 |
| 第二次 | **不可反覆執行** —— 資料殘留、名稱撞號、狀態沒收乾淨 |

⭐ **兩次結果一致才算數**（階段 2.6 的「本來就該紅」那幾條，兩次都該紅）。
不一致就是案例自己沒收乾淨 —— 那是要修的，不是缺陷。

> **為什麼值得多跑一次**：交出去的案例是要**反覆執行**的（回歸）。
> 只跑一次就交，等於把「第二次會不會過」留給下一個人在發版前才發現。

## 階段 3：執行測試

1. 執行前先向使用者**說明**會做什麼。授權依 **CLAUDE.md §5 授權表** ——
   QAT 的 Web／UI 寫入不必再取得確認；STG、DB 寫入（除 `DrawTime`）、
   影響全盤的操作（開獎／一键结账／關盤／反結算）才需要。
2. 環境未建置時先跑 `scripts\setup_test_env.ps1`（冪等）。
3. 執行：`scripts\run_ui_tests.ps1`，常用參數：
   - `-Headed`：有頭模式（除錯用）
   - `-Filter <關鍵字>`：等同 pytest `-k`
   - `-Marker <marker>`：等同 pytest `-m`（如 `smoke`）
   - `-Open`：跑完自動開啟報告
4. 測試失敗時：先讀 pytest 輸出定位，必要時用 Playwright MCP 重現操作觀察畫面，修正後重跑。

## 階段 4：產出報告

1. UI 測試任務完成後**必須**生成 allure report（`run_ui_tests.ps1` 已內建）。
   > 本 skill 的流程一定會跑 pytest，故此處恆為必做。
   > ⚠️ 但**別把這句當通則往外引用** —— 權威判準在 CLAUDE.md §5：
   > 「有跑 pytest 才要出 allure，純 MCP 手動操作不用」（如 `jira-verify` 的探索式重驗）。
2. 向使用者摘要：通過/失敗數、失敗原因、新建立的測試帳戶（manifest 路徑）。
