# perf-test：壓測與效能驗證流程

> **三個產品各有壓測工具，先看 §0.0 分流。** 本檔 §1／§3／§5 是 **CRUX 專屬**；
> §4 對外用語、§6 收尾與回寫、以及下列授權紀律**三產品通用**。
> ⚠️ **授權完整依 `CLAUDE.md` §5「QAT 的寫入授權」及其全部例外／禁止事項**；本檔只指路，不縮減或擴大該節。
> QAT 專用站台的既定流程依 §5 專用站台例外處理；共享站台或可能影響他人的操作仍依 §5 先取得確認。
> **DB 一律唯讀**，唯一常態例外是重置期數時直接調整該期 `DrawTime`；其他 DB 寫入仍須每次取得個案裁示。
> 壓測的下注／退碼／結算重置皆走工具的 API／Web 通道，不以 SQL 改值；STG 任何操作仍需逐次授權，正式環境一律不碰。
> 知識三層（長青結論、工具手冊＋陷阱、進行中進度）的路徑依 §0.0 所選產品及其交接文件為準；下方明列的 `docs/CRUX/` 路徑只在 CRUX 分流時適用。

## 1. 選輪次類型與模式（★ CRUX 專屬）

**模式**（同一控制台、同時只能跑一個）：下注壓測（Case6）／API 序列（OpenAPI）。

**輪次類型**（下注壓測的三種用法，決定參數與判讀方式）：

| 類型 | 用途 | 典型參數 | 判讀重點 |
| --- | --- | --- | --- |
| 容量階梯 | 找上限 | `run_capacity_ladder --levels 30 100 200 300`，錢包檢核**關**（工具流量會汙染量測） | 停止條件：只有 gate 不過或壓測機飽和才中止（陷阱 42），延遲/節流超標要續跑 |
| 完整測試（C-1） | 驗收＋金流 V-01 | 200u/10m、錢包檢核**開**、退碼每 5 注 | 延遲數字不併入容量曲線（含工具流量）；V-01 看 `wallet_check_report` |
| 專項重現輪 | 供 bug 驗證／佐證 | 依單而定（常配 DB 輪詢器＋UI 截圖三時點：消化中／靜止後／結算後） | 配合 `/jira-verify`；截圖要「使用者可見狀態」（收合列要展開） |

文本情境：A-4 混合密度＝`--groups mix:2 mix:3 mix:4 random:1-5 dense:35`（每會員 5 條輪替、
設計密度 ≈22.3 號碼/文本）；請求密集用 `single:01`；情境標籤記得同步報告工具的 `SCENARIOS`。

## 2. 執行與監看（★ CRUX 專屬；七星／wbot 見各自的 references）

- CLI 驅動：`run_manager.resolve_params(...)` → `start_run(params, blocking=True)`（收尾統一走
  `finalize_run`，會自動產 `sla_report`）。Web UI：`python web_ui/app.py` → :5000。
- 成敗判準看 **`sla_report.json` 的 `verdict`**，不是 exit_code／phase（陷阱 24）；
  業務成功率看 `business_summary.json`，**Locust 零失敗不代表成功**（陷阱 10）。
- run 結束**立刻**記「停止當下積壓」（`async_backlog`）——晚了就被消化掉，結算量測就沒了起點。
- 長時間輪詢用背景腳本＋每次新連線（REPEATABLE-READ 快照陷阱）；等待條件用 Monitor，不要 sleep 輪詢。
- ★ **每輪必做的常態觀察：CRUX-974 是否復發**（使用者 2026-08-14 指定）——
  跑 `recycle_issue` 前先看 `async_backlog()` 的 `settleable` 有沒有轉 `True`；
  **卡住不動時比對 `expected` 與 `processed` 四欄，「只有下注欄差、退碼欄正常」就是該症狀**
  （下注事件沒進 `ReportBetProcess` → 對賬永不歸零 → 結算／重置／反結算全被擋）。
  ⚠️ **遇到先記差值與時戳再回報 RD，別急著 recycle** —— 一 recycle 證據就沒了。
  觸發條件至今未明，故只能靠每輪觀察。詳見交接檔 §2-C4。

## 3. 指標判定口徑（★ CRUX 專屬；最容易出錯，全部實踩過）

| 指標 | 正確口徑 | 錯誤示範 |
| --- | --- | --- |
| 號碼數/秒 | `PlaceBet 穩態 RPS × 業務成功率 × 平均號碼/文本` | 漏乘成功率 → 高負載灌水 1.56 倍、結論反轉（陷阱 36） |
| 消化速率 | **處理側推進量 ÷ 實際時戳差**，每次新快照 | 用積壓差（被入水量干擾）、用 sleep 名目秒數（高估 33%）、同連線重查（凍結假象） |
| 節流率 | 對外兩口徑並列：**占 PlaceBet**（機制真值）＋占全請求（對照） | 只報占全請求（分母被工具流量稀釋） |
| 結算時間 | 停止時戳→歸零段＋結算段牆鐘（**含歸零**，2026-08-07 使用者裁示） | 只算結算引擎（差 50~100 倍） |
| 失敗時序 | `locust_stats_stats_history.csv` 相鄰差值 | grep console.log（每 10 秒重複列印 → 假均勻分佈，曾誤開單） |
| 低負載數據 | 先比對思考時間理論上限 `users × 0.38 req/s` | 把工具極限當系統容量（陷阱 39） |

DB 查詢紀律：時間欄位比大小用 UTC（本機 −8h）；分表後綴用**期數業務日期**；詳見效能結論 §6。

## 6. 收尾與回寫（三產品通用）

1. **環境還原：★ 整批測試完成後，由執行者決定要不要還原**

   ⚠️ **不是每一輪跑完就還原** —— 壓測常要連跑多輪相互比對，
   中途還原會讓後面的輪次失去對照基準。**整批做完再一次決定。**

   | 情況 | 處置 |
   | --- | --- |
   | 一般輪次，數據正常 | 依 §0.0 所選產品的還原 SOP 執行（CRUX 例：`recycle_issue --apply`）；期數留在可下注狀態供次日使用 |
   | **量到異常，可能要開單或複驗** | ⛔ **保留不還原** —— 那批資料就是現象的重現環境 |

   > **判準（同 CLAUDE.md §5）**：「**這批資料還原後，這個現象還重現得了嗎？**」
   > 重現得了（例如問題在歷史期、與本輪資料無關）就照常還原。
   >
   > ⚠️ 壓測的環境**比功能測試更難重建** —— 異步積壓、孤兒注單、額度鎖死、
   > 分批賠率的當下組合，產品的還原工具一跑就全沒了，要靠再壓一輪湊回來未必湊得出。

   **決定保留時必做**（依 `bug-report` 的「Bug 環境保留」節）：
   在 §0.0 所選產品對應的效能交接檔 **§5 測試資料與環境現況**登記
   **刻意保留、屬哪一張單、清掉會失去什麼**，並保留到該單 `status`
   轉為 `fixed`／`rejected`／`superseded` 為止。
   ⛔ 沒登記等於下一個 session 會把它當殘留清掉（`handoff` §1 A 的 ⛔ 正是在防這件事）。

   若本批使用瀏覽器，最後呼叫 `browser_close`。
2. **結論回寫分流**（權威表：`writeback` §1）：
   新的**長青效能結論**、**工具陷阱／量測方法教訓**與產品 skill 意圖對照，依 §0.0 所選產品的對應效能文件寫入；不要把 CRUX 路徑套用到七星／投注機器人。只有新增文件或改變既有文件範圍時才同步 INDEX／意圖對照。**缺陷** → 依 `bug-report` skill 建單（bugs/ 不版控）。
3. **狀態交接（★ 與上一條是兩件事）** → §0.0 所選產品的效能交接檔：
   進度與待辦、**當前 blocker**（卡在誰身上）、**等 RD／PM 裁定的事**、
   **動過但未還原的測試資料**（期數、帳號、定盤值）。
   只有上述狀態確實改變時才回寫；知識回寫完不等於交接完 —— 這幾類都不會出現在任何知識文件裡。
   跨產品的骨架與紀律見 `writeback` §4，**各工作線交接檔的對照表見 `handoff` §0**。
4. 對外報告遵守 `bug-report` skill 的測試報告章節順序（結果在前）；
   **報告一律放所選產品的 `bugs/_reports/`**（該層不版控），不放產品 docs 直下。
   > 2026-08-13 修正：先前寫成「**含測試站帳密者**放 bugs/ 層下」——
   > 條件式判斷錯就直接進版控，且與 `bug-report`／`jira-verify` 的無條件規則不一致。
   > 現統一為無條件。

   ⛔ **檔名不可自己拼，寫檔前「當下」用指令取**（CLAUDE.md §6 第 4 條）：

   ```powershell
   python scripts\new_bug_doc.py --product <選定產品> --kind perf --topic <主題>
   ```

   **最後一行輸出就是可直接寫入的路徑**（`效能測試報告_<主題>_<日期>.md`）；
   同日同主題撞名時自動遞增 `_第N批`，並列出同日已存在的檔案。
   長任務可加 `--reserve` 先原子佔位；反向檢查某路徑能不能寫用 `--check <路徑>`。
   > **為什麼不能憑感覺取名**：`bugs/` 不版控，**覆蓋掉沒有 git 可以救**。
   > 2026-08-14 就有 session 直接以固定檔名寫入，把同日另一批的報告與交接檔整份蓋掉。
   > 壓測報告的檔名雖含主題、撞名機率較低，但**同一主題重跑第二輪**正是最常見的撞名情境。
