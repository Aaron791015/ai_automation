# Bug 單與測試報告撰寫

> ⚠️ **配號規則（「配號前必須當下重查」）留在 CLAUDE.md §6，因為那是「不先知道就會出錯」的規則。**
> 本 skill 是格式與模板，動筆時載入即可。

## 1. 檔案結構

Bug 相關檔案一律置於 `docs/<專案>/bugs/`，**整層不版控**（含測試站帳密，已列 `.gitignore`）：

```
docs/<專案>/bugs/
├─ BUG清單.md              # 索引（gen_bug_index.py 自動生成，勿手改）
├─ CRUX-043_….md           # ← 活躍單（open / suggestion）
├─ shots/                  #   其截圖
├─ old/                    # ★ 歸檔層（archive_bugs.py 搬移，勿手動搬）
│   ├─ CRUX-001_….md       #   已結案單（fixed / rejected / superseded）
│   └─ shots/              #   其截圖
├─ _view/                  # 分組檢視（自動生成，勿手改）
├─ _reports/               # Bug 驗證報告（JIRA_Bug驗證報告_<日期>.md）
├─ _handover/              # 待驗項交接文件（交接_SideEffect待驗_<日期>.md）
└─ _deliver/<日期>_<主題>/  # 對外提交副本（pack_bug_report.py 生成，勿手抄；自帶 shots/）
```

> **Bug 單只會存在於兩個位置：主目錄 或 `old/`。** 索引、配號、lint 一律同時掃兩層。

### 歸檔（`scripts\archive_bugs.py`）

```powershell
python scripts\archive_bugs.py --product CRUX              # 預演（預設）
python scripts\archive_bugs.py --product CRUX --yes        # 執行
python scripts\archive_bugs.py --product CRUX --restore CRUX-019   # 取回
```

- **判準看狀態，不看日期**：`fixed`／`rejected`／`superseded` 可歸檔；
  `open` 拒絕歸檔（未修復的無論多久都要留在手邊）、`suggestion` 不歸檔。
- 圖跟著擁有者走，**所有引用路徑自動改寫**（含 `_reports/`、`_handover/`）。
  `_deliver/` 是自足的凍結快照，**不追改**。
- **不要手動搬** —— 漏改引用會產生斷連結，且 `bugs/` 不版控、無法用 git 還原。

> ⚠️ **`.gitignore` 只擋 `docs/**/bugs/`** —— 驗證報告與交接文件含測試站帳密與未公開的驗證細節，
> **必須寫在 `bugs/` 層底下**。寫到 `reports/` 或 `docs/<專案>/` 會直接進版控。

### ⛔ `_reports/` 與 `_handover/` 的檔名一律用指令取

這兩個目錄的檔名是「類型＋日期」的固定組合，**同一天兩個 session 各驗一批就必然撞名**；
而 `bugs/` 不版控，**覆蓋掉沒有 git 可以救**。所以不要自己拼檔名：

```powershell
python scripts\new_bug_doc.py --product CRUX --kind report      # JIRA 重驗報告
python scripts\new_bug_doc.py --product CRUX --kind handover    # side effect 交接
python scripts\new_bug_doc.py --product CRUX --kind requirement --topic CRUX-883綜合報表
python scripts\new_bug_doc.py --product CRUX --kind perf --topic A-7文本重複度
python scripts\new_bug_doc.py --product CRUX --kind report --reserve   # 長任務先原子佔位
```

**最後一行輸出就是可直接寫入的路徑**；撞名時自動遞增 `_第N批`，並列出同日已存在的檔案。
反向檢查某個路徑能不能寫：`--check <路徑>`（已被佔用回傳碼 1）。

（教訓：2026-08-14 有 session 直接以固定檔名寫入，覆蓋掉同日另一批的報告與交接檔。
當次靠原作者 session 還在線、依 context 重打一次才救回 —— 那是運氣，不是機制。）
> （`reports/` 只有 `allure-results/`、`allure-report/`、`created_accounts/*.json` 被忽略，
> 該目錄本身是版控的。）

## 2. ID 與配號

- `CRUX-nnn` / `WBOT-nnn` / `QX-nnn` 三碼流水，**配發後永不回收**（撤銷、非缺陷者亦保留編號）。
- 改善建議走 `-S01` 序列，不佔 bug 流水號。
- 檔名 `<ID>_<簡述>.md`；**日期只放 frontmatter、不放檔名**（同日多 bug 會撞）。
- **一條 bug 一檔**；同批探索發現的多條以 `batch:` 欄位與 `related:` 互相關聯。

> ⚠️ **寫檔的那一刻**才取號（不是任務開始時，也不得沿用稍早記下的號碼）：
> ```powershell
> python scripts\gen_bug_index.py CRUX --next-id
> ```
> **⛔ 不可用 `ls docs/<專案>/bugs/` 自行推算** —— 它看不到 `old/` 的已歸檔單，
> 而 ID 永不回收，漏掉就直接撞號。也不得憑 `BUG清單.md` 推算（索引可能未重跑）。
> 已撞號時改號的是**後寫入者**，且要一併改：檔名、frontmatter `id`、內文自我引用、
> 回歸案例註解與 allure 標題、報告與交接文件的所有引用。改完 `grep -rn "<舊ID>"` 掃過確認無殘留。

## 3. Frontmatter（狀態的單一事實來源）

```yaml
---
id: CRUX-042
title: <一句話說清楚：哪個畫面、什麼數據、錯在哪>
product: CRUX
surface: 後台            # 前台 | 後台 | H5 | 平台 | 總控
module: 日志
severity: 中             # 高 | 中 | 低 | —
status: open
found: 2026-08-10
reported:                # 見下方說明
verified:                # 重驗日期
env: QAT
regression: tests/crux/backend/test_two_factor_log.py::test_xxx
related: [CRUX-015, CRUX-016]
batch: 2026-08-10 JIRA CRUX-898 覆蓋度補測
deliver:                 # 對外交付批次
---
```

改完 frontmatter **一定要重跑** `python scripts\gen_bug_index.py` ——
它會**順便檢查截圖資產**（斷圖／死圖／命名／撞號），有問題時提示你跑
`python scripts\lint_bug_assets.py --verbose` 看詳情。

### ★ 截圖規範 → 見 [`references/截圖規範.md`](references/截圖規範.md)

> ⭐ **每張單預設都要有佐證截圖**（2026-08-26 使用者裁示，lint 的 **W10** 會查）——
> 「圖中描述問題與顯示數值，看的人更能快速理解」，這與 §4 第一句
> 「讀者要在 **10 秒內**知道哪裡錯」是同一件事。
> ⚠️ **真的沒有畫面**的缺陷（API 回應、DB 對帳、壓測數據）在 frontmatter 寫
> `no_shot: <理由>` 豁免 —— 重點是讓「不放圖」變成一個**要寫下理由的決定**，
> 而不是默默省略。
> ⛔ `surface: 前台`、或標題講的是訊息／提示／顯示／版面這一類，**非截圖不可**：
> 錯誤訊息與版面問題用文字描述永遠不如一張圖。
>
> ⛔ **不得只丟一張原始畫面。** 每張 bug 截圖都必須具備三件，缺一不可：
> ① **框選問題點**（紅框＋編號）② **實際值 vs 應為值**的說明（附依據）③ **一句話標題**。
> 「同時框錯的與對的」—— 只框錯值，讀者無從判斷基準。
>
> ⚠️ **「要有圖」與「不能只有圖」不衝突**：內文的 Actual／Expect 數值由 **W4** 強制
> （`docs/**/bugs/` 不版控，**圖丟了要讀得懂**），圖是讓人快十倍看懂的那一層。
> 兩層都要。

動筆前必知的三條（其餘作法、MCP 指令序列、回傳值檢查、命名規則見上方 references）：

| # | 一定要知道 |
| --- | --- |
| 1 | **截圖前確認瀏覽器全螢幕**（`browser-ops` §0）。MCP 預設視窗只有 929×925，寬表格會被擠壓到讀不出欄位 |
| 2 | **拍完立刻 `stamp_shots.py` 搬走**，不要等一批拍完再搬 —— `.playwright-mcp/` 的內容**會在 session 中途消失**（實際遺失過 3 張） |
| 3 | **MCP 截完必須再蓋一次標記** —— lint 的 W7 看的是 PNG 裡的 tEXt 標記，不是畫面上的紅框 |

| 欄位 | 值與意義 |
| --- | --- |
| `status` | `open` 未修復｜`fixed` 已修復重驗通過｜`rejected` 查證後非缺陷｜`superseded` 由後續單接續｜`suggestion` 改善建議 |
| `reported` | **是否已開立（提交 RD 修正）**。已開立填 `2026-08-10（CRUX-942）`；未開立**留空**（索引會列入「待開立」）。⚠️ **重新驗證前先看此欄**：未開立者 RD 尚未收到問題，重驗仍 FAIL 屬預期，勿誤判為修復無效 |
| `regression` | 對應回歸案例路徑；未填或標 `⚠️ 待補` 者會被索引列入「待補回歸案例」 |
| `no_shot` | **這個缺陷沒有畫面**時填理由（如「純 API 回應比對」「DB 對帳」）。⛔ 只是懶得拍**不算** —— 那會讓 W10 失去意義 |

> **本地 ID 與 JIRA 單號是兩套獨立編號**，CRUX 兩邊前綴相同（`CRUX-`）但號碼不相干 ——
> 回報時務必兩者並列（「JIRA CRUX-942／本地 CRUX-042」），勿混用。

## 3.9 ★ 開單前三問（動筆前先過一遍）

> **為什麼需要**：撤銷過的單至今有 8 張（CRUX-046／055／069／082／083／088／090／S04）。
> 每一張的反例都散在不同地方 —— 產品 skill 的不變量、機制文件的附錄、各處「勿重開」註記 ——
> **沒有統一入口，所以每次都靠運氣**。

| # | 問 | 怎麼查 | 答錯的後果 |
| --- | --- | --- | --- |
| **①** | **這是規格還是缺陷？** | 找得到**人為的變更聲明**（RD 留言／PM 修訂／使用者裁示）→ 規格；<br>只有「我量到不一樣」→ **缺陷**。判準見 CLAUDE.md「實測與文件不符時」 | 把規格開成單 → 撤銷；<br>**把缺陷寫成規格 → 更嚴重**（用測試者的手把 bug 合法化） |
| **②** | **這現象是不是已經被查證過？** | 查 `docs/<產品>/bugs/_view/04_已撤銷與接續.md`；<br>再查產品 skill 的不變量與機制文件的「非缺陷」附錄 | 重開已撤銷的單，浪費雙方時間 |
| **③** | **這個樣本有鑑別力嗎？** | 換一組資料還會不會出現？<br>是不是**壓測資料／他人的測試資料／歷史髒資料**？ | 拿沒有鑑別力的樣本開單 → 查下去發現不成立 |

⛔ **分不清 ① 時，一律預設當缺陷先立單** —— 本地 Bug 單成本極低（ID 永不回收、撤銷只是改 `status`），
而漏掉的缺陷會被文件更新洗掉、再也沒人發現。**兩者的代價不對等。**

> 💡 ③ 的實例：`CRUX-088` 因「報表查不到某天」開單，後查出那是**壓測期**的資料清理個案而撤銷。
> 開單前先確認帳號不是 `perf*`／`zxc*`、注數量級不在萬筆以上。

## 4. Bug 回報格式

> ### ⛔ 讀者要在 **10 秒內**知道「哪裡錯、應該是多少」
> （2026-08-19 使用者裁示：「Bug 內容都要看很久才能理解問題重點」）
>
> **順序固定為下方模板，不得增節、不得調序**；要精簡的是**每一節的內容**：
>
> | 節 | 上限 | 要點 |
> | --- | --- | --- |
> | 標題 | 1 行 | `[產品][前台\|後台][模組]` ＋ **一句可判對錯的陳述**：哪個畫面、什麼數據、錯在哪 |
> | Reproduce Steps | 5 步以內 | 只寫重現必需的操作，含具體文本／金額／期號 |
> | Actual result | 一張表或數行 | 實際值，具體數字 |
> | Expect result | 一張表或數行 | 應為值 ＋ 依據（公式／規格章節／權重表） |
> | 問題截圖 | 1～2 張 | 看完就能確認標題那句話成立 |
> | 【Test Environment】 | 一張表 | URL、帳密、彩種期號、帳號鏈 |
> | （選）附註 | 折疊 | 追溯、更正紀錄、歷史觀測。**可以不寫** |
>
> Actual／Expect 數字多時用 `欄位｜實際｜應為｜依據` 的對照表，不要寫成段落。
>
> **挑截圖的判準**：找**最單純的樣本**（單一玩法、單一注單、只有一個下級），
> 讓「實際 vs 應為」在同一畫面、**不必先驗算**就能核對。
> **一張圖只框那一件事** —— 6 個紅框＝讀者要判斷 6 次哪個才是重點。
> 多單共用一張混合圖時，**該單要有自己的專屬圖**，別叫讀者從別人的標注裡找自己那幾格。
>
> **⛔ 不要寫進 Bug 單**（寫了就是要讀者多確認一件事）：
>
> - 「為什麼會這樣」的推導、成因猜測、程式碼位置猜測
> - 「有什麼後果」「影響多大」的鋪陳 —— `severity` 欄已經表達了
> - 我方的自我更正過程、方法論檢討、判斷經過
> - 同一件事在正文與附註各講一次
>
> 這些屬**我方的內部知識**：機制／公式進 `docs/<產品>/` 的機制文件，
> 方法論教訓進 memory 或交接檔，**都不進 Bug 單**。
>
> ⚠️ **本地 `.md` 單套用同一份模板與同一個順序** —— 不是只有貼給 RD 的那份。
> 本地單被重驗、改判、承接時很容易愈長愈厚（更正註記、歷史對照、原描述保留），
> **一律往最後的「附註」壓**，前面各節維持乾淨。

```
[產品][前台|後台][模組] 標題（一句話：哪個畫面、什麼數據、錯在哪）

## Reproduce Steps
1. （從前台下注等前置動作寫起，含具體投注文本/金額）
2. …

## Actual result
（實際看到的畫面/數據，附具體數字）

## Expect result
（依規格/公式應有的結果，附依據，如權重表、領域知識文件章節）

（關聯說明：驗證號碼 關聯 注單/玩法，如「虛盤001 關聯 组三二码01」）

## 問題截圖
（嵌入圖檔）

## 【Test Environment】
總監：<URL>
帳密：<帳號>/<密碼>
（必要時補前台帳密、期號等重現所需資訊）
```

⚠️ **節名一律用 `## ` 開頭、後面不加冒號**——
這是 `jira_markup.strip_headings()` 認得出「這是節名」的唯一依據（見 §5.1），
只認 `scripts/jira_markup.py::SECTIONS` 列出的那幾個規範節名，寫成裸行帶冒號的舊格式
轉不出 JIRA 格式（2026-08-27 `CRUX-124` 就是這樣重現的）。人自己加的節（如「成因分析」）
不在這份清單裡，維持 `##` 原樣，不會被動。

**截圖**：放 `shots/`，命名 `<ID>_<序>_<說明>.png`（修復驗證圖用 `<ID>_fixed_<序>_…`）。
多單共用的圖以**首位擁有者 ID** 命名，其他單引用同一路徑、不複製。
非 bug 佐證的探索截圖放 `docs/<專案>/探索截圖/`，不得混入 `shots/`。

## 4.1 ★ Bug 環境保留（開單後不還原）

> **2026-08-20 使用者裁示。** 這條**優先於** CLAUDE.md §5 紀律 1 的「測試資料用完即還原」。

**開了 Bug 單，就把重現它所需的資料留著。** 那批資料**就是該單的重現環境** ——
還原掉之後 RD 照著 Reproduce Steps 走會看不到現象，我方要補截圖、重驗、改判時也得整段重做。

| 何時保留 | 何時照常還原 |
| --- | --- |
| 本次**新建**的注單／帳號／設定，是該單 Actual result 的來源 | 缺陷在**歷史資料**上就重現得了，與本次新建的東西無關 |
| 換一批資料就**不一定重現**（依賴特定玩法組合、中獎與否、退碼與否） | 只是為了走到某個畫面而建的過場資料 |

判準一句話：**「這批資料還原後，這張單還重現得了嗎？」** 重現不了就留著。

**保留期間**：到該單 `status` 轉為 `fixed`／`rejected`／`superseded` 為止。

**保留就一定要登記**（否則下一個 session 會把它當殘留清掉）：

1. **產品交接檔的「測試資料現況」節**加一列，寫明三件事 ——
   ① 動了什麼（帳號、期號、注單編號、金額）② **屬哪一張單**
   ③ **清掉會失去什麼**（例：「這是 CRUX-072 的唯一乾淨樣本，清掉要重新下注才拍得到圖」）。
2. Bug 單的 `【Test Environment】` 表補一列指出該資料仍在。

⚠️ **保留 ≠ 可以擴散**：仍不得動他人的測試資料，也不得因此佔用整個期數或站台；
會影響其他 session 的操作（結算、關盤、重置期數）照舊要先確認。

⚠️ **改判 `rejected` 或關單後記得回頭清**，並把交接檔那一列劃掉 ——
保留的理由消失後就變成純殘留。

（教訓：2026-08-20 為 `CRUX-072` 在 26222 新建的乾淨樣本，量測完當場退碼還原；
隔天要重拍截圖時資料已不存在，只能重新下注。）

## 5. 對外交付

```powershell
python scripts\pack_bug_report.py --product CRUX --name <日期>_<主題> --ids CRUX-019 CRUX-020
```

自動去除 frontmatter 與內部註記、只帶該批引用到的截圖。
**禁止手動複製 Bug 單**（教訓：舊 `bug回報_0728/` 與本體重複維護，兩份會漂移）。
壓縮檔與資料夾同名並置於 `_deliver/`，交付紀錄登記於 `_deliver/README.md`
（已寄出的壓縮檔沿用原檔名、不追改）。

### 5.1 對外交付的下游是 JIRA——正文預設轉成 JIRA wiki 標記

`pack_bug_report.py` 打包時**預設**把正文轉成 JIRA wiki 標記（貼過去不用再手動轉一次，
2026-08-28 使用者裁示）；要交 markdown（例如貼進 wiki 或寄信）才加 `--no-jira` 關掉。

轉換規則**只有一份實作**（`scripts/jira_markup.py`，見該檔檔頭的完整對照表），這裡只列
最常見的三條，幫你動筆時心裡有數（寫法本身不用變，轉換是自動的）：

| markdown | JIRA wiki | 動筆時要注意 |
| --- | --- | --- |
| ` ``` ` 圍欄 | `{code}` … `{code}` | 貼 log／API 回應照樣用 ` ``` `，不要自己寫 `{code}` |
| `## 節名` | 裸行（不加 `##`、不加冒號） | 節名照樣打 `##`，轉換會自動拿掉 |
| `summary:` frontmatter | JIRA 的 summary 欄 | 一句話講現象，這欄會被抽出來當 JIRA 單標題 |

⛔ **轉換規則不可以在別的地方（skill、`pack_bug_report.py`、平台落檔）各寫一份**——
2026-08-26 那套只做在平台落檔那條路，這份 skill 與 `pack_bug_report.py` 當時都沒跟上，
於是同一個工作區同時產出兩種格式的 Bug 單，且沒有任何機制會發現（2026-08-28 使用者查出）。
要改規則只改 `jira_markup.py`，三處都會跟著對。

## 6. 測試報告撰寫規則 → 見 [`references/測試報告規則.md`](references/測試報告規則.md)

**要寫對外交付的報告時**（測試報告／需求驗證報告／JIRA 驗證報告／效能測試報告）才需要讀。
**只是開一張 Bug 單的話，§1～§4 就夠了。**

那份裡有：章節順序（**結果在前、過程在後**）、內容分流規則（什麼進報告、什麼留在 Bug 單）、
佐證要求，以及 **§6.1 「佐證要寫多細」的查表**（依 ✅已修復／❌仍重現／⚠️部分修復／
⛔非缺陷／🚫無法驗證五種結論各有下限，不必每次重新拿捏）。

> ⛔ **兩件事動筆前就要知道，不必翻那份**：
> **檔名一律用指令取**（`python scripts\new_bug_doc.py --product <專案> --kind report`）、
> **一律寫在 `bugs/` 層底下** —— `bugs/` 不版控，**覆蓋即永久遺失**。

## 7. JIRA 驗證報告的結構

驗 JIRA 修復時的報告格式**以單為單位**（一張單一章，三個區塊缺一不可）——
完整規格見 `jira-verify` skill 第 6 節。此處僅提醒最容易被省略的一項：

> **③ Side effect check item 中，未檢查的項目一律照列**，標「未檢查」並說明原因。
> 漏列比未檢查更嚴重：未檢查是已知缺口，漏列會讓人誤以為已全面涵蓋。
> 不在本次補驗範圍者，須轉為交接文件（`bugs/_handover/`）。
