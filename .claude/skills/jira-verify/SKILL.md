# JIRA 單驗證流程（唯讀串接）

## 0. 角色分工與唯讀邊界（最高優先，不得逾越）

| 動作 | 由誰做 |
| --- | --- |
| 確認 bug、**開立 JIRA 單**、回填單號 | **使用者** |
| 指定單號、要求驗證 | **使用者** |
| 取單、重現、驗證、回報結論 | **Claude** |
| **關單**、變更 JIRA 狀態／留言 | **使用者** |

**Claude 對 JIRA 一律唯讀**：只能用 `tools/jira_qa/jira_api.py` 讀取。
**禁止**：開單、留言、改狀態／欄位、關單、上傳附件——即使使用者口頭要求，也先說明本工具為唯讀版並請其手動執行。

> 本地 Bug ID（`CRUX-nnn` / `WBOT-nnn` / `QX-nnn`）與 JIRA 單號是**兩套獨立編號**，
> 例：本地 `WBOT-002` 對應 JIRA `BOT-799`。回報時務必兩者並列，勿混用。
> **CRUX 兩邊前綴相同（`CRUX-`）但號碼不相干**，尤須留意——詳見第 3 節的撞名警告。

## 1. 取單

```powershell
python tools\jira_qa\jira_api.py --check                     # 首次／連不上時先驗連線
python tools\jira_qa\jira_api.py <KEY> --changelog           # 取單（含狀態異動歷程）
python tools\jira_qa\jira_api.py <KEY> --attachments --out <scratchpad>\jira\<KEY>
```

- 連線失敗的三種成因，依提示區分：**不在內網** ／ **帳密未填或錯誤**（`config/config.local.json` 的 `jira.username`/`password`）／ **CAPTCHA 鎖定**（連續登入失敗所致，此時密碼正確也會 401，需人工用瀏覽器登入解鎖）。
- description 為 Jira wiki markup 純文字，可直接讀。

### 附件（截圖）：需要 session cookie

本站台裝有 **2FA 外掛**，附件端點 `/secure/attachment/` 走 **web 層**（非 REST），
Basic Auth 與 REST session 都會被 2FA 攔截回傳登入頁 —— 兩者皆已實測失敗。

**可行解**：`config/config.local.json` 的 `jira.session_cookie` 填入使用者瀏覽器中
**已通過 2FA** 的 `JSESSIONID`，`--attachments` 即可正常下載（**2026-08-07 實測成功**，
取回位元組數與 JIRA metadata 一致）。

```powershell
python tools\jira_qa\jira_api.py <KEY> --attachments --out <scratchpad>\jira\<KEY>
```

- **附件一律下載到 scratchpad，不落 repo**（CLAUDE.md §8.3）；下載後用 Read 檢視。
- cookie 會過期，失效時請使用者從瀏覽器重新複製（工具會明確提示是「未設定」還是「已過期」）。
- 工具會偵測回傳內容是否為登入頁，**不會把 HTML 寫成 .png**（曾產出看似正常實為壞檔的圖）。
- 使用者不便提供 cookie 時的替代路徑：① description 的數字通常已足夠重現；
  ② 我方單可讀本地 `docs/<專案>/bugs/shots/`；③ 請使用者自行下載後給路徑。
  **不要因缺圖就臆測畫面內容。**

## 2. 判定單子來源，取得驗證依據

先反查本地是否已有對應 Bug 單（`reported` 欄位會登記 JIRA 單號）：

```powershell
python scripts\gen_bug_index.py            # 需要時先更新索引
```
再以 Grep 搜 `docs\<專案>\bugs\` 內文中的 JIRA 單號。

| 情境 | 驗證依據 |
| --- | --- |
| **A. 我方單**（本地有對應 Bug 單） | 以**本地 Bug 單為主**（有完整 Reproduce Steps／Expect 與 `regression` 案例路徑）；JIRA 內容用來補 RD 的修復說明與版本 |
| **B. 他人單**（本地無對應） | 以 **JIRA description 為起點**，再查 JIRA 留言／changelog 與既有權威規格補足；仍不足且會改變驗證判準才依第 3 節詢問，不自行腦補 |
| **C. 資訊不足** | 先依第 3 節查本地單、規格、留言、案例與交接；仍有會實質改變驗證的缺口才問，不猜測、不自行擴大解讀需求，並繼續可獨立處理的項目 |

### ⚠️ 關聯單先判斷必要性，再決定驗證範圍

驗一張單時，先查兩個方向的直接關聯，再判斷它是否是本次主訴求的必要依賴或有證據支持的共同影響：

1. **JIRA 側**：`issuelinks`（relates to／blocks…）帶出的關聯單。
2. **本地側**：本地 Bug 單 frontmatter 的 `related:` 欄位。
3. **同根因不同表面**：同一支程式／SQL 可能同時打到前台與後台、不同總監、不同彩種 —— 逐一驗過，勿只驗單子上寫的那一個入口。

必要依賴、同根因且有影響證據的關聯單納入本次範圍，並說明納入理由；只有 `relates to` 或沒有影響證據的項目列為建議回歸，不自動遞迴展開。使用者明確指定完整關聯矩陣時，才依該矩陣逐項處理，不得自行抽樣縮減。

實例（2026-08-07）：JIRA `CRUX-924` 是**總監2 後台**風險用戶控賠頁 SQL 錯誤，
關聯的 `CRUX-923` 與本地 `CRUX-035` 是**總監1 前台下注**失敗 —— 同一支
`RiskMemberReduceOddsRepository` 查詢，只驗後台會漏掉「下注能不能成交」這個更嚴重的影響。
本地單另註明「與彩種無關」，故排列三與福彩3D 都要驗。

回報時須列出直接關聯的查核結果、納入驗證的關聯單及排除／列為建議回歸的理由；漏掉已判定為必要依賴的關聯單才算驗證不完整。

## 3. 萃取驗證五要素（情境 B 必做；先查證，必要才問）

| 要素 | 來源 | 缺項時 |
| --- | --- | --- |
| **產品／畫面** | JIRA project key、component、description、本地 Bug 單與產品文件 | 先查既有規格、留言、回歸案例與交接；仍缺且會改變目標範圍 → 問使用者是哪個產品的前台／後台哪一頁 |
| **重現步驟** | description 的 Reproduce Steps、本地案例、JIRA 留言與既有操作文件 | 先查既有步驟；仍不足以重現且會改變操作或資料 → 問，勿自行腦補投注文本／金額 |
| **預期結果** | Expect result／需求規格／JIRA 留言／領域知識摘要 | 先查權威規格與留言；仍無明確預期且會改變 PASS 判準 → 問使用者判準，勿以「畫面有出現」當弱斷言 |
| **環境** | JIRA environment 欄位、description | **預設一律 QAT**；單上寫 STG 也**必須逐次取得授權**（CLAUDE.md §5） |
| **修復是否已部署** | `status` / `resolution` / `fixVersions` / changelog | 見第 4 節 |

缺項處理順序固定為：先讀本地 Bug 單、JIRA description／留言／changelog、既有規格與產品文件，再查既有案例或交接資料。查完仍有**會實質改變被測行為、預期判準、環境或授權**的缺口才詢問；不影響其他案例的局部缺口標記為待確認／受阻，先繼續可獨立驗證的項目，不猜關鍵值。

### JIRA project key ↔ 產品對照

| project key | 產品 | 本地 Bug 前綴 |
| --- | --- | --- |
| `CRUX` | CRUX（排列三 P3、福彩 3D） | `CRUX-` ⚠️ 見下方撞名警告 |
| `BOT` | 投注機器人 | `WBOT-` |
| 七星（key 待確認） | 七星 | `QX-` |
| （其他） | 首次遇到時**向使用者確認**，並回寫本表 | — |

> ⚠️ **CRUX 編號撞名陷阱**：JIRA project key 與本地 Bug 前綴**都是 `CRUX-`**，但兩者是**各自獨立的流水號** ——
> JIRA `CRUX-18` 與本地 `CRUX-018` 幾乎必然指向不同問題。
> 收到 `CRUX-nnn` 時**先確認是哪一邊的編號**（使用者交辦驗證時給的通常是 JIRA 單號）；
> 兩者的對應關係一律以本地 Bug 單 frontmatter 的 `reported` 欄位為準，
> **不得因號碼相同就推定是同一個問題**。回報時兩者並列並標明來源，如「JIRA CRUX-18／本地 CRUX-019」。

## 4. 狀態與版本資訊的正確用法

> ⛔ **JIRA 單的 status 不是「能否驗證」的判準，不得據此拒驗或建議延後。**
> 使用者指定要驗就驗 —— 單子轉派回使用者手上即代表可驗，與顯示 Backlog／
> Selected for Development／Resolved 無關（狀態流轉未必即時反映實際修復進度）。

狀態與版本仍要讀，但用途是**解讀結果**，不是**決定驗不驗**：

| 讀到什麼 | 用途 |
| --- | --- |
| `status` / `resolution` / changelog | 結論為 ❌ 仍重現時，附註單子當前狀態供 RD 判斷 |
| `fixVersions` | FAIL 時判斷是否為「版本未部署」而非「沒修好」；無法確認版本就在但書寫明前提 |
| **留言** | RD 常已寫出根因與修正後預期值 → **直接拿來當斷言依據**（例：CRUX-905 留言已給 −129.76） |

唯一該停下來問使用者的情況是：依第 3 節順序查證後，重現資訊仍不足且會實質改變本次驗證；不是因為狀態不對，也不是因為一個局部缺口就終止整批。其餘項目先標記受阻並繼續可獨立處理的工作。

## 5. 執行驗證

### 5.1 兩階段順序：目標單全部驗完並出報告，才回頭驗 side effect（★必守）

一次交辦多張單時，**不要一張單「驗完主項順便把 side effect 也掃一遍」再換下一張**。順序固定為：

| 階段 | 做什麼 | 產出 |
| --- | --- | --- |
| **① 目標單** | 把使用者指定的每一張單，以及依上節判定納入的必要關聯單之**主訴求**驗完 | 完整的驗證報告（含每張單的 ①②③ 三區塊，③ 先只列項、標「待驗」） |
| **② side effect**（報告產出後才開始，不必等使用者回覆） | 回頭逐項驗 ③ 列出的波及面 | 追加一節「side effect 補驗結果」，並更新③的「是否檢查」欄 |

**為什麼**：

1. **使用者要的是先看到全貌。** 七張單各驗一半、side effect 各掃一半，報告出來時每張單都是
   「部分完成」，使用者無法對任何一張單下決定（關單／退回／轉 PM）。先把主訴求做完，
   每張單就都有明確結論。
2. **side effect 的清單要等主項驗完才會準。** 主項驗證常會改變波及面的判斷 ——
   例：2026-08-13 驗 CRUX-966 時發現彈窗盈亏欄位全空（新迴歸），這條在動手前根本列不出來；
   反過來，原本以為要驗的項目也可能因主項的實測結果而不必驗。
3. **side effect 是可切割、可交接的**（見第 9 節）；主訴求不是。時間不夠時該砍的是②不是①。

階段①的報告中，③ 區塊仍**必須把 side effect 項目列全**（標「待驗」＋理由），
不可因為「還沒驗」就不寫 —— 那會讓人以為沒有波及面。

若某一張單或一個案例因環境、資料或權限小阻塞而暫時無法驗，標記阻塞原因與不影響的後續步驟，繼續處理其他可獨立驗證的目標單、必要關聯單與 side effect；不得因局部阻塞而終止整批。只有缺口會改變整批驗證判準或授權範圍時，才停下來詢問使用者。

### 5.2 寫入授權：依 CLAUDE.md §5 的授權表

**權威來源是 `CLAUDE.md` §5「QAT 的寫入授權」表；授權、還原、QAT／STG／DB／共享站台例外及正式環境（prod）禁止事項完整依該節執行，本節不重複摘要，也不放寬。** JIRA 本身仍依本 skill §0 維持唯讀，禁止開單、留言、改狀態／欄位、關單與上傳附件。

### 5.3 覆蓋度規範（判 PASS 前必檢）

> ⛔ **只驗一個樣本就判 PASS 是不完整的驗證。**
> 教訓：2026-08-07 驗 JIRA CRUX-882（分類帳中間商層級欄位改名）只驗了**大股東一層**就判 PASS，
> 但該單的訴求是「**中間商層級**」——涵蓋大股東／股東／總代理／代理共 4 層，
> 等於只驗了 1/4；同批 CRUX-898 亦只憑「有資料的 7 種日誌類型」就判全 20 種已修。

判 PASS 前，先問「**這張單的訴求涵蓋多少個對象？我驗了幾個？**」並在報告寫出**分母與分子**。

| 維度 | 要問的問題 | 常見漏驗 |
| --- | --- | --- |
| **層級** | 單上寫的層級是單一層還是一類？ | 「中間商」＝大股東／股東／總代理／代理**四層**，非一層 |
| **彩種** | 只驗排列三，福彩3D／排列五／七星彩呢？ | 本地單常註明「與彩種無關」，仍須抽驗第二個彩種 |
| **玩法／類型** | 20 種日誌類型、20 個攔貨大類、各玩法子類 | 「其餘無資料所以沒驗」→ **應主動觸發**（見 §5.2，QAT 的 Web 寫入可直接做） |
| **頁面** | 同欄位／同元件是否散落多頁？ | 日／週／月報表、實盤／虛盤／出貨盤、日分類帳／月分類帳 |
| **總監** | 總監1／總監2 行為是否一致？ | 同一支程式打到不同總監 |
| **正反向** | 該生效的生效了，**不該變的有沒有被改壞？** | 改名限縮層級、修驗證後下界仍正常 |

規則：

1. **能主動觸發就觸發**，不得以「該類型／該層級目前無資料」當作免驗理由（QAT 的 Web 寫入已授權）。
2. 確實無法涵蓋的，**在②表格中列為獨立一列並標「🚫 無法驗證」＋原因**，不可省略不提；
   同時列入③ side effect 並轉交接文件。
3. **報告須寫出覆蓋度分數**，如「中間商 4 層驗 4/4」「20 種日誌類型驗 12/20，其餘 8 種無觸發途徑」。
4. 覆蓋度不足時，結論**不得為 ✅ 已修復**，應為 ⚠️ 部分修復 或 🚫 無法驗證。

#### 分母怎麼算：**不適用 ≠ 未驗**（2026-08-13 補）

覆蓋度的分母是**適用的對象數**，不是「想得到的對象數」。三分法：

| 類別 | 定義 | 進分母嗎 | 報告怎麼寫 |
| --- | --- | --- | --- |
| **已驗** | 實際操作／讀取確認過 | ✅ 進，算分子 | 列出實際值 |
| **未驗** | 適用但這次沒做（沒時間、環境不足、忘了） | ✅ **進分母、不進分子** | 標原因；**會壓低結論等級** |
| **不適用** | 該對象**結構上不可能有這個問題** | ❌ **不進分母** | **仍要列一行並寫明「不適用＋為什麼」**，否則讀者無法分辨你是漏了還是排除了 |

> 例（2026-08-13 CRUX-949「非總監層級的出貨欄空值顯示 -」）：報表共 5 張，但**月報表按「期」列示、
> 沒有帳號欄也沒有非總監層級** —— 結構上不可能有這個問題，屬**不適用**。
> 故覆蓋度是 **4/4（另 1 張不適用）**，不是 4/5，結論可判 ✅。
> 若寫成 4/5 就會被第 4 條規則逼著降級，變成假的「部分修復」。

**判斷「不適用」的門檻要高**：必須說得出**結構性理由**（沒有這個欄位／沒有這個層級／
該功能未實作），不能是「應該不會有問題」「風險低」—— 後者是**未驗**。

#### 覆蓋度只論「主訴求」，side effect 不計入結論（2026-08-13 補）

第 4 條的覆蓋度，指的是**這張單自己的訴求**涵蓋了多少對象。
③ 的 side effect **完成度不影響結論等級** —— 否則依 §5.1 的兩階段流程，
階段①的報告裡沒有任何一張單能判 ✅（那時 side effect 本來就還沒驗），規則會自相矛盾。

例外只有一個：**side effect 檢查真的驗出新問題**時，結論降為 ⚠️ 部分修復（原本就有的規則）。
「還沒驗」與「驗出問題」是兩回事，不要混為一談。

### 5.4 PASS 判準：以使用者視角認定，不以「技術上可對應」放水

> ⛔ **「工程師查得到」不等於「使用者看得懂」。**
> 教訓：2026-08-07 驗 JIRA CRUX-898（日誌無法識別變更對象），日誌 target 由 `null` 改為
> `用户ID : 2343`、`游戏ID : 1, 玩法ID : 100` 後判 PASS —— 但**使用者看到一串 ID 仍然不知道是誰、哪個彩種、哪個玩法**，
> 必須另外查表才能對應，並未達成單子「可識別變更對象」的訴求。**這種情況應判 FAIL。**

- 斷言要對齊**單上 Expect 的字面要求**（寫「帳號」就要出現帳號，不是用戶ID；寫「玩法」就要出現玩法名稱，不是玩法ID）。
- 判斷「是否算修好」時，站在**該功能的實際使用者**（總監、客服、稽核人員）角度，而非開發或測試者角度。
- 若系統**已在別處證明有能力**輸出可讀值（如 `用户` 類型 target 同時給 `识别码` 與 `账号`），
  則其他類型只給 ID **更明確是未修完**，不可視為設計取捨。
- 有落差就是 ❌／⚠️，**不要寫成「PASS 附但書」讓使用者自己去裁定** —— 判定是驗證者的責任。

### 5.5 重現時的瀏覽器操作規則

> **載入 `browser-ops` skill 依其規則操作** —— 特別是 §1「走使用者的實際路徑，禁止 URL 直達」
> 與 §5「轉場本身就是受測範圍」。
>
> ⛔ 這條不是形式要求：2026-08-07 驗 JIRA CRUX-882 時直接導到
> `/ledger/daily?level=2&parentId=2` 省掉「點帳號下鑽」，因而**完全沒看到**該轉場的嚴重缺陷
> （表頭已切、列表仍顯上一層達 2.6 秒且無 loading），這個 bug 是使用者反映後回頭補測才發現的
> —— 即本地 CRUX-037／JIRA CRUX-936。

1. **被測行為一律走 UI**；API 只能做非被測行為的前置準備（CLAUDE.md §5）。
2. **本地已有 `regression` 案例** → 直接跑，最省時：
   ```powershell
   scripts\run_ui_tests.ps1 -Filter <關鍵字>
   ```
3. **無案例**（多為他人單）→ 依 `browser-ops` 用 Playwright MCP 重現；需要新增測試案例時再載入 `ui-test`。
   驗證完成後**補一條回歸測試案例**（以正確行為為斷言），並在本地 Bug 單 `regression` 欄登記。
4. **佐證要求**（與 CLAUDE.md 一致）：列出**實際值 vs 期望值**與其依據（公式／規格／權重表），
   PASS 與 FAIL 用**同一種可讀算式明細**呈現，**不得只附截圖**。
5. **截圖**：放 `docs/<專案>/bugs/shots/`；有本地 ID 用 `<本地ID>_fixed_<序>_說明.png`，
   純他人單（尚無本地 ID）用 `<JIRA-KEY>_fixed_<序>_說明.png`。
6. 用畢呼叫 `browser_close` 關閉 MCP 瀏覽器。

## 7. 回寫本地紀錄

> ⛔ **舊單不回頭更新，一律以新單追蹤**（2026-08-17 使用者裁示，取代本節原本的做法）。
> 本節先前寫的是「有對應本地 Bug 單 → 更新 `status`／`verified`／`regression`」，
> 已依裁示改為下表。

| 情況 | 動作 |
| --- | --- |
| 有對應本地 Bug 單，**✅ 已修復** | **不改舊單內文**。在**驗證報告**中寫明結論與佐證，並建議使用者關 JIRA 單 |
| 有對應本地 Bug 單，**⚠️ 部分修復／❌ 仍重現** | **不改舊單內文**，改**開一張新單承接殘留範圍**（配發新 ID，`related` 指回舊單，內文開頭寫明「本單承接 `<舊ID>` 的殘留範圍」）。舊單保持原狀 |
| 無本地單且 ❌ 仍重現 | 建議補建本地 Bug 單（配發新 ID，`reported` 填 JIRA 單號），供後續追蹤與回歸 |
| 無本地單且 ✅ 已修復 | 是否建檔由使用者決定；但**建議至少留一條回歸案例**，下次重驗才有依據 |

> **為什麼**：舊單是**當時那次回報的快照**，回頭改它會讓「單子說的」與「當初回報的」對不起來，
> 也讓 `git`／JIRA 上的討論脈絡失去對應。新單則自帶時間點與新佐證，追蹤鏈清楚。
> **指向關係一律由新指向舊**（新單的 `related` 寫舊 ID），不要反過來去舊單補指標。
>
> （案例：2026-08-17 驗 JIRA CRUX-773 時，`CRUX-008` 的明細層已修、匯總層未修。
> 原先做法是把 `CRUX-008` 改為「部分修復」並附複驗現況；依本裁示**已還原 `CRUX-008`**，
> 改開 `CRUX-072` 承接匯總層的殘留範圍。）

- **allure report：只有「這次真的跑了 pytest 案例」才要產**（CLAUDE.md §5，2026-08-14 使用者裁示）。
  本 skill 的重驗有兩條路（§5.5）：跑既有 `regression` 案例 → **要出 allure**；
  純 Playwright MCP 手動重現 → **不用**（本來也產不出來），佐證改以驗證報告的算式明細與截圖呈現。
  > 📝 本條原寫「產出 allure report（UI 測試任務必做）」，與 CLAUDE.md §5 新增的例外直接衝突
  > —— 而 jira-verify 的探索式重驗正是那條例外要豁免的場景。2026-08-14 依該裁示更正。
- **commit 前一律向使用者確認**，並遵守 **`commit` skill 的兩段式流程** ——⛔ **取得許可前不得 `git add`／`git stash`**（索引是 working tree 共用的），回報用唯讀指令；許可後才「暫存 → 覆核 → 提交」一氣呵成。

### 7.1 配發新 Bug ID 前，必須「當下」重查佔用情況

### 7.2 驗證過程學到的知識也要回寫

重驗常會挖出 Bug 單以外的知識（某功能的實際機制、某操作的前置條件、某頁面的轉場行為）。
