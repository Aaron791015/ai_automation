## 9. Side effect 未檢查項的交接

本次不補驗的 side effect 項目**一律寫成交接文件**，放在 `docs/<專案>/bugs/_handover/`，
讓其他 session／同事可獨立接手。文件須自足 —— 接手者不該需要回頭問前一個 session。

> ⛔ **檔名同樣用指令取**（同 §6，這個目錄一樣是固定檔名＋不版控）：
> ```powershell
> python scripts\new_bug_doc.py --product <專案> --kind handover
> ```

> ⚠️ 同 §6：**必須在 `bugs/` 層底下**才不會進版控（交接文件含環境與帳號資訊）。

每項至少包含：

| 欄位 | 說明 |
| --- | --- |
| 編號 | 沿用報告中的 `S<n>`，與驗證報告可互相對照 |
| 對應 JIRA／本地單 | 該 side effect 源自哪張單的修復 |
| 為何可能被波及 | 判斷理由（RD 留言、共用程式、相鄰功能…） |
| 驗證方式 | 具體步驟／頁面／API／可複用的既有測試案例 |
| 判斷依據 | PASS／FAIL 各該看什麼值，避免接手者自行臆測判準 |
| 優先序 | 高／中／低 ＋ 理由 |
| 環境與前置 | 站台、帳號來源（指向 `config/`，勿寫死帳密）、需要的資料狀態 |

報告的③區塊須標明交接文件路徑；交接完成後，該項在報告中維持「未檢查」並註記「已交接」。

### 9.1 ★ 批次交接檔寫完，還要「上收」到產品交接檔

批次交接檔是**一次性快照**（任務結束即凍結）。只寫它會有兩個後果：
檔案愈積愈多、且**沒人知道哪一份還活著**（CRUX 到 2026-08-13 已有 5 份，其中 4 份從未復查）。

所以收尾時**還要**更新產品的**活文件交接檔**（`docs/<產品>/<產品>_功能驗證交接.md`，
骨架與紀律見 `writeback` §4）：

| 這次產生的東西 | 去哪 |
| --- | --- |
| 本批全部的 side effect 待驗項 | 批次檔（本節）**＋** 活文件 §3 加一列索引，註明殘留狀況 |
| **等 PM／SA 裁定的規格問題** | **活文件 §2.2** —— 這類**別處沒有家**：不是 bug（不進 `BUG清單.md`）、不是 side effect、也不是知識 |
| **本次沒驗完的驗證範圍**（少驗的彩種／層級／站台） | **活文件 §2.1 或 §2.4** —— 同上，別處沒有家 |
| 卡住整條線的事（站台停用、等版本） | 活文件 §1 |
| 為取證而動過的測試資料（含已還原者） | 活文件 §5 |
| 缺陷 | 本地 Bug 單即可，**活文件不重複列**（`_view/` 自動生成） |

> ⛔ 教訓（2026-08-13）：CRUX-883 需求驗證留下的「總監3 複驗 CRUX-051」「總監1 排列五／七星彩」
> 「總控端綜合報表待前端」三項，只存在於報告內文與對話裡 —— 它們不是缺陷也不是 side effect，
> 當時沒有任何檔案收得下，**新 session 依任何關鍵字都搜不到**。活文件就是為此而設。
