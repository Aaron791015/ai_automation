# commit 紀律（多 session 共用 working tree）

> 📝 **2026-08-22 從 `CLAUDE.md` §8.2～§8.4 移入。** CLAUDE.md 只留三條硬紀律與指標 ——
> 這些流程細節只在「真的要 commit」時需要，卻讓每個 session 常駐付出約 20 KB。
>
> ⚠️ **章節編號刻意沿用原始的 §8.2／§8.3／§8.4** —— 這三節內部有大量互相引用
> （「見 §8.3 配套⑥」「比照 §8.4」…），重新編號會讓它們全部失效。
> 外部引用請寫「`commit` skill §8.3」。

## 0. 先看這幾條（CLAUDE.md 留的硬紀律）

1. **commit 前一律先向使用者確認**；未取得確認不得自行 commit。
2. ⛔ **取得許可前不得 `git add`／`git stash`** —— 索引是整個 working tree 共用的，不是你這個 session 的。
3. **只 add 自己的路徑**，禁止無條件 `git add -A`／`git add --renormalize .`。
4. ⭐ **（只在原版工作區）提交後跑一次 `export_template.py --out <鏡像> --sync`** ——
   對外發送的是鏡像，原版改了而鏡像沒跟上時**沒有任何機制會發現**（見 §8.2 的 C 段）。
   ⚠️ **你手上這份如果是匯出的範本，這一條不適用** —— 判準見 C 段。
5. **每次 `git push` 前都要列出將推送的檔案與差異，取得該次 push 的使用者確認**；原版與鏡像是不同 repository，授權不可互相推定。

以下是完整流程。

### 8.2 commit 的兩段式流程（必做）

> **`git status` 顯示的內容 ≠ 你的未 commit 工作。**

> ⛔ **取得 commit 許可之前，不得碰索引** —— 不 `git add`、不 `git stash`（stash 同樣是共用的）。
>
> **為什麼**：**索引是 working tree 的屬性，不是 session 的屬性** —— 與 §8.1 對「分支」的推理相同。
> 而「**已暫存、正在等使用者回覆**」是整個流程中**停留時間最長**的狀態（要等人），
> 偏偏也是最危險的：這段期間**任何 session 一 commit，就會把你暫存的東西一起送出去**。
> 多個 session 各自先暫存再回報，索引就變成一鍋粥，誰先 commit 誰就掃走全部。
> （2026-08-21 使用者裁示。當天雙向都發生了：本 session 被別人的暫存擋住無法提交，
> 自己暫存的內容也被別人的 commit 帶走。）
>
> 舊版的五步驟有三步是 `--cached`，**不先暫存就跑不了** —— 這才是「大家都先暫存」的制度性成因，
> 故改為下列兩段。

**A. 許可前：唯讀預檢（完全不碰索引）**

```bash
git log --oneline HEAD..main                        # A1 唯讀列出分支落後；有輸出只代表需回報／依使用者指示處理，不在預檢中自行 merge
git status --short                                  # A2 全貌，含 `??` 新檔。這份就是要給使用者看的清單
git diff --stat --ignore-cr-at-eol -- <自己的路徑>   # A3 異動量；--ignore-cr-at-eol 取代 renormalize 的去噪作用
git diff --ignore-cr-at-eol -- <共用檔>              # A4 共用檔讀整段 diff（§8.4；判準見下）
```

**B. 許可後：暫存 → 覆核 → 提交，一氣呵成（中間不停下來等人）**

```bash
git diff --cached --name-only                       # B0 ★必須為空
git add --renormalize <自己的路徑> && git add <自己的新檔>   # B1
git diff --cached --numstat                         # B2 覆核只有自己的路徑（看「加了什麼」）
git status --short                                  # B2b ★自己的路徑下必須沒有殘留（看「漏了什麼」）
git commit ...                                      # B3
git status --short                                  # B4 確認索引已清空
```

**C. 提交後：同步乾淨範本鏡像 —— ⚠️ 只適用「原版工作區」**

> ### 先確認你是不是在原版
>
> ```powershell
> Test-Path .template-export      # False → 原版（要做 C 段）｜True → 你手上就是範本（跳過）
> ```
>
> **這一條只有維護範本的那一份工作區要做。** 你手上如果是**匯出的範本**
> （根目錄有 `.template-export` 這個標記檔），你沒有鏡像、也不需要同步 —— **整個 C 段跳過**。
>
> ⛔ 這一段是刻意標範圍的：本 skill 會**跟著範本發到每個人手上**，
> 而在沒有鏡像的機器上跑那道指令，不是失敗就是指到不存在的路徑。
> **規則變成雜訊，人就會開始跳過整段** —— 連該做的那幾條一起跳過。

在原版工作區：

```powershell
python scripts\export_template.py --out <你的鏡像目錄> --sync
```

⚠️ 鏡像目錄**每台機器不同**（本機是 `C:\GitLab\QA-Template`），見 `README.md`。

⭐ **判準不是「自己判斷這次算不算範本層」** —— 那種規則一定會漂。
**commit 完就跑一次，讓工具自己回答**：沒差異它會說「鏡像已經是最新的」（幾秒鐘的事），
有差異它會**列出是哪幾個檔**，那就是本來就該同步的東西。

有差異時，先把鏡像的變更範圍交給使用者審閱。**原版 commit 的授權不包含鏡像 repository 的 commit 或 push**；鏡像同步只更新其工作樹，不自行取得這兩項授權。

```powershell
git -C <你的鏡像目錄> status --short
git -C <你的鏡像目錄> diff --stat --ignore-cr-at-eol
git -C <你的鏡像目錄> diff -- <export_template.py 列出的同步路徑>
```

鏡像 working tree 若已有未相關的 dirty changes，保留它們並只阻塞鏡像 commit；不得 reset、clean、stash 或代改其內容。取得**鏡像 commit**的明確許可後，才可依同步工具列出的**精確路徑**暫存並提交；commit 後仍須再次列出檔案與差異，取得**鏡像 push**的明確許可後才執行 `git -C <你的鏡像目錄> push`。

> **為什麼要有這一條**：對外發送的是**鏡像**，不是這個工作區
> （原版有產品資料，推不上去）。原版改了而鏡像沒跟上時，**沒有任何機制會發現** ——
> 同事拿到的就是舊的，而你以為已經給出去了。
>
> ⛔ `--sync` 的前提是**鏡像的 working tree 乾淨**（覆蓋是不可逆的，乾淨才代表救得回來）。
> 髒的話工具會拒絕並列出是哪些檔。鏡像是產物，**不要在裡面直接改東西**。
>
> ⭐ **2026-08-26 起這一步有絆線了**：`lint_docs` 的 **D13** 會在鏡像落後時報 ——
> 先前它**只靠自律**，而本 skill 自己就寫著「沒有任何機制會發現」，結果連續四輪漏掉。
> 需要在原版根目錄放一個 `.template-mirror`（一行鏡像路徑、不版控）；沒放就整項跳過。
>
> 📖 完整說明見 `README.md` 的「乾淨範本鏡像」節。

> ⚠️ **B2b 不可省，它和 B2 看的是相反的東西。**
> `--numstat` **只列已暫存的內容** —— 漏掉的檔案不會出現在裡面，畫面完全正常。
> B2b 是唯一看得到「**該暫存卻沒暫存**」的一步。
>
> 尤其是**用「加目錄」的方式暫存時** —— `git add --renormalize <目錄>` 只作用於
> **已追蹤**的檔案，該目錄下的新檔一個都不會進來，而你會以為「整個目錄都加了」。
> （教訓：2026-08-23 提交 72 個檔案時，`tools/test_platform/docs/ROADMAP.md`
> 就是這樣差點漏掉 —— A2 有看到它的 `??`，但 B1 加的是上層目錄，
> 是 B2b 才把它撿回來的。）

> ⚠️ **B0 若有輸出，代表索引已有其他待提交內容** —— **只阻塞本次 commit**；先以唯讀 diff／status 查明範圍，回報後不要把它們帶入本次 commit。
> 不要因為索引被占用而終止其他不涉及索引的獨立工作，也**⛔ 不要 `git reset`**（那會清掉他們的暫存）。
> `git reset` 只在「**你自己**暫存錯了」時才用，且它只動索引、不動檔案；
> **切勿 `git reset --hard`**，那會清掉其他 session 未提交的工作。

> ⚠️ **A2 的 `??` 不可省：`git add --renormalize` 只作用於「已追蹤」的檔案，新檔完全不會被加進來。**
> 而 B2 只列已暫存的內容 —— 新檔沒暫存就不會出現，畫面看起來完全正常。
> 兩者相加的結果是**新檔靜悄悄地漏 commit**。
> （教訓：2026-08-13 新增 `docs/CRUX/CRUX_功能驗證交接.md`，照當時的步驟跑完毫無異狀，
> 是另外看了 `git status` 的 `??` 才發現整份新文件沒被暫存。）
> A2 撿出來的若是自己的新檔，就在 B1 一併 `git add`；是別人的就別碰。

> ⚠️ **B1 務必指定自己的路徑，不要用 `git add --renormalize .`** —— 加 `.` 會作用於**整個工作區**，
> 把其他 session 開發中的檔案一併暫存（違反 §8.3）。
> 例（CRUX 壓測）：`git add --renormalize tools/CRUX_Performance docs/CRUX/CRUX_Performance_*.md`
> （教訓：2026-08-03 照 `.` 執行，誤暫存了他人的 `docs/CRUX/CRUX_利潤率計算公式.md`。）

> ⚠️ **提交後要再跑一次的檢查：凡是「只看已版控檔案」的工具。**
> 這類檢查（例如 `export_template.py` 的白名單稽核走 `git ls-files`）
> 在 commit 前**是半盲的** —— 你新加的檔案還是 `??`，它根本掃不到；
> **一 commit 就全部進了掃描範圍**。
> 所以本次異動若新增了會被這類工具檢查的檔案，**commit 後要再跑一次驗收**。
> （教訓：2026-08-23 `perf-test/references/前置檢查_*.md` 提交前四條驗收全綠，
> 提交後複驗立刻冒出一個誤報與一條測試失敗 —— 兩者都是「提交前掃不到」造成的。）

> 💡 **A4 讀共用檔 diff 的目的**：依 §8.3 的 co-commit 例外（2026-08-21 擴及 skill 等文件型共用檔），
> 讀 diff 已**不是為了切分歸屬**，而是確認**對方的內容是完整的、不是寫到一半**；
> 以及**程式與設定檔不適用該例外**，那些仍要確認沒把別人的行一起帶走。

- 他人 session 開發中的檔案不代為 commit（各自負責），看到時也不主動建議代勞
  （同上，交接活文件除外）。
- ★ **例外：交接活文件與文件型共用檔允許整份 co-commit**（2026-08-14 使用者裁示，
  2026-08-21 擴及 skill 等文件型共用檔）—— 混到別的 session 的列**不必逐行剔除**。

  | | |
  | --- | --- |
  | **適用** | 交接活文件（`docs/<產品>/*驗證交接.md`）＋ `.claude/skills/`、`docs/INDEX.md`、`docs/<產品>/` |
  | **不適用** | ⛔ **程式與設定檔**（`scripts/`、`tools/`、`pyproject.toml`、`.mcp.json`）—— 文件少一段看得出來，半成品程式看不出來 |
  | **兩個前提** | **同一個產品** ＋ **內容沒有缺少** |

  ⚠️ **「不必逐行剔除」≠「不必逐行讀」** —— 免除的是把他人的列還原掉，**不免除把整份 diff 讀過**。

  ⚠️ **不論適不適用本例外，交接檔的編號（T／D／B）一律在寫入前「當下」用指令取**：
  ```powershell

  ```
  多 session 併行沒有任何機制擋重複；撞號時改號的是**後寫入者**。
  （`CRUX_功能驗證交接.md` 實際撞過三組，`lint_docs` 的 **D9** 現在也會掃。）

  > 那裡有**六條配套**（commit 訊息要列項目編號／不得順手改他人的列＋三種正常運作的例外／
  > 內容矛盾先查證、無法可靠解決才問／編號當下取／半成品不送／不代改檔頭日期）、
  > 「被別人的 commit 帶走不算問題」的裁示範圍，以及三則實際事故。
  >
  > **本段只夠你判斷「適不適用」；真的要送之前，那六條一條都不能少。**

### 8.4 共用檔：只動自己的條目 —— 及其兩個例外

> **本節導覽**（2026-08-14 補：標題只講了通則，實際已有兩個例外，先看這張表再讀內文）
>
> | | 規則 | 適用範圍 |
> | --- | --- | --- |
> | **通則** | **只動自己的條目**，他人的一律不碰（含順手改錯字、順手整併） | 全部共用檔 |
> | **例外①（內容）** | 他人條目所陳述的**事實**被你這次的驗證推翻 → **就地更正或與你的新列合併**，不可留下矛盾的並存列。程序見 `writeback` §5 | 全部共用檔 |
> | **例外②（commit）** | **交接活文件與文件型共用檔**可整份 **co-commit**（可含他人的列），配套六條見 **§8.3** | 交接活文件 ＋ `.claude/skills/`、`docs/INDEX.md`、`docs/<產品>/`　⛔ 程式與設定檔不適用 |
>
> ⚠️ **兩個例外互相獨立，別混用**：例外① 講「**內容**能不能改」，例外② 講「**commit** 能不能一起送」。
> 交接活文件與文件型共用檔兩者都適用；**程式與設定檔**（`scripts/`、`tools/`、`pyproject.toml`、`.mcp.json`）
> 只適用例外①，commit 仍須逐行確認。

>
> ⛔ **例外① 有一條硬邊界**：**帶裁定來源的「規格」陳述不在可改之列** ——
> 實測與規格不符時那是**缺陷**，要開單而不是改文件。判準見 **§6「實測與文件不符時」**。

> ★ **交接活文件（`docs/<產品>/*驗證交接.md`）比照共用檔處理**（2026-08-14 補正）。
>
> ⚠️ **「共用」的範圍限於該產品線內部，不是跨產品** ——
> `CRUX_功能驗證交接.md` 只有**處理 CRUX 功能／需求／回歸的 session** 會寫；
> 七星或 wbot 的 session **不會也不該去動它**（§8.3 的路徑紀律照舊：
> `docs/<專案>/` 仍是該產品的專屬路徑）。它之所以要比照共用檔，是因為
> **同一產品線常有多個 session 併行**，收尾時都得寫同一份檔（§6「狀態交接」是強制的），
> 於是本節的「先讀後寫競態」與「只動自己的條目」同樣適用
> —— 而不是因為全工作區的人都會碰它。
> （`writeback` §4 紀律4 早已要求「比照 §8.4」，本節先前漏列而定位不一致。）
>
> ⚠️ 它有**自己的一套 commit 規則**：內容編輯照本節，但 **commit 時適用 §8.3 的 co-commit 例外**
> （可含他人的列，配套六條見該處）—— 該例外**同樣涵蓋 `.claude/skills/`、`docs/INDEX.md`、`docs/<產品>/`
> 等文件型共用檔**；只有**程式與設定檔**（`scripts/`、`tools/`、`pyproject.toml`、`.mcp.json`）
> 仍須「逐行確認、不得混入他人的行」。
> （2026-08-22 更正：原寫「與其他共用檔…不同」，未涵蓋 08-21 裁示擴及的文件型共用檔。）

多個 session 都會編輯這些檔，且因共用 working tree，風險是**先讀後寫的競態**（A 讀進記憶體 → B 改檔 → A 寫回覆蓋 B），而非 merge 衝突。故：

- 一律**只動自己的條目** —— 自己寫的那幾列**可以新增，也可以修改或刪除**；
  **他人的條目一律不碰**（包含順手改錯字、順手整併）。
  > 這條先前寫成「只新增，不刪改」，與 §6 要求的「改動既有檔的範圍時**同步修正該檔的 INDEX 描述**、
  > 不可只加不改」直接衝突 —— 2026-08-13 修正為「只動自己的」。
  > 判準是**條目的作者**，不是動作是新增還是修改。
- ★ **唯一例外：他人的條目所陳述的「事實」被你這次的驗證推翻時，要就地更正或與你的新列合併，
  不可另起一列放著不管。**（2026-08-14 使用者裁示）
  > **為什麼要破例**：意圖對照表、INDEX 描述、機制文件這類東西是拿來**被別人查**的。
  > 留下「舊列說 A、新列說 B」的並存狀態，下一個 session 只會讀到其中一列，
  > 而且**先讀到哪一列純屬運氣** —— 等於你把一顆錯誤答案留在索引裡。
  > 這比動到別人的字嚴重得多。
  >
  > **界線很窄，別擴大解釋**：
  > - ✅ 可改：**可驗證的事實值**（下限日期、公式、狀態、檔案路徑、API 欄位名）
  >   —— 且你手上要有**這次實測／裁定的佐證**。
  > - ⛔ 不可改：措辭、排版、分類方式、你覺得寫得不好的地方 —— 那些仍然「一律不碰」。
  > - ⛔ **不可改：帶裁定來源的「規格」陳述**（「使用者／PM／SA ×× 裁定」「as-designed」「這是規格，不是缺陷」）。
  >   **實測與規格不符時那是缺陷，要開單，不是改文件** —— 除非你手上有**新的變更聲明**
  >   （RD 留言／PM 修訂／使用者裁示）。判準與實例見 **§6「實測與文件不符時」**。
  >   > ⚠️ 這一條是 2026-08-14 補的**必要 guard**：本例外只說「有實測佐證就可以更正事實值」，
  >   > 而「只顯示已結算」這種**規格**看起來也像一個可驗證的事實值 ——
  >   > 當天就有 session 據此把一個缺陷改寫成規格（JIRA CRUX-983）。
  >   > 沒有這條，本例外會反過來鼓勵大家去覆蓋規格。
  >
  > #### ★ 更正他人條目的程序 → **見 `writeback` §5**
  >
  > 📝 2026-08-22 收斂：本段原本自稱「本段為權威」，但 `writeback` §5 也寫了同一件事
  > （且多了「改值前後各跑一次 `trace_value.py`」那一步）——**兩份都自稱權威，正是要消滅的模式**。
  >
  > **定位**：更正「**內容**」是回寫行為 → `writeback` §5；本 skill 只管「**送出**」。
  > 那裡有：可改／不可改的界線（⛔ 帶裁定來源的規格陳述不得改）、
  > 必做①寫明新值與依據、必做②回報中點名動了誰的條目、
  > 分流③（**狀態型保留原陳述／索引型直接取代**）、以及改值前後的 trace。
- commit 前檢查刪到了誰的行：
  ```bash
  git diff --cached -U0 -- docs/INDEX.md | grep '^-' | grep -v '^--- '   # 有輸出＝有刪到行
  ```
  **有輸出不代表違規**，代表要逐行確認「刪掉／改掉的都是自己寫的」。
- ⚠️ **但刪行檢查只擋得住一半** —— 它看不到「**別人新增的行被你一起暫存**」。
  共用檔數量少，**一律用 `git diff --cached -- <共用檔>` 把整段 staged diff 讀過**，
  不能只看 `--numstat` 的 `+N −0` 就放行。
  > （案例：2026-08-13 commit `423a69a` 把壓測 session 寫在 `.claude/skills/crux/SKILL.md`
  > 裡尚未提交的 2 列意圖對照一併提交了。該檔 diff 是 `+29 −0`，刪行檢查完全沒反應，
  > 我也只看了 numstat。
  > ⭐ **2026-08-21 使用者裁示後，這一件已不算違規** —— 同產品、內容沒有缺少，
  > skill 等文件型共用檔被一併帶走是可接受的，見 §8.3 的 co-commit 例外。
  > **本段保留是為了說明「為什麼要讀整段 diff」**：讀 diff 的目的已不是切分歸屬，
  > 而是**確認對方的內容是完整的、不是寫到一半**，以及**程式與設定檔不可比照辦理**。）
  （注意：Markdown 條列的 `- ` 加上 diff 的 `-` 標記會變成 `--`，故**不可**用 `grep '^-[^-]'` 過濾，會漏掉條列行。）
