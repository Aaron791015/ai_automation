> 📌 **範本內建的通用教訓。** 文中的「產品A／產品B／產品C」是範本原型留下的匿名實例，
> 只是為了讓教訓有具體場景 —— **教訓照用，例子換成你自己的產品**。

使用者 2026-08-13 交辦七張 JIRA 單重驗時明確指定的作法：
**「上列 JIRA 單子測試完成後，請先整理測試結果報告；將目標驗證的單子完成後，再回頭驗證其他 side effect」**，
並要求把它「加入規範」。**規則本體見 `jira-verify` skill 的「兩階段順序」節**（該處為權威）。

順序固定為：① 目標項全部驗完 → 出完整報告（side effect 只**列項**標「待驗」）→
② **報告產出後就開始**補驗 side effect、**不必等使用者回覆**，並追加一節結果。

> （2026-08-22 更正兩處：
> ① 原寫「**使用者看過報告後**，才回頭補驗」——與 skill 現行寫法「不必等使用者回覆」相反。
> 　回查 2026-08-13 的原始指示只說「目標單子完成後再回頭驗 side effect」，
> 　**並沒有「要等使用者看過」這個條件**，是本則自己加上去的。以 skill 為準。
> ② 原指向 `§5.-1`，該章節號不存在（現為「5.1 兩階段順序」）。
> 　依 memory 使用規範，**章節引用一律用標題而非編號**——編號會漂，標題相對穩。）

**Why:** 每張單各驗一半，報告出來時每張都是「部分完成」，使用者無法對任何一張下決定
（關單／退回／轉 PM）。而且 side effect 清單要等主項驗完才會準 —— 本次驗 A-966 時
才發現彈窗盈亏欄位全空（新迴歸），那條在動手前根本列不出來。side effect 可切割可交接，
主訴求不行；時間不夠時該砍的是②。

**How to apply:** 收到「一次驗 N 項」的任務（JIRA 重驗、需求驗證、覆蓋度補測皆適用）時，
先宣告兩階段並照做；階段①的報告仍要把 side effect **列全**（標「待驗」＋理由），
不可因為還沒驗就不寫，否則讀者會誤以為沒有波及面。未在本批補驗者轉
`docs/<專案>/bugs/_handover/`。相關：[[ui-test-task-guidelines]]、[[api-vs-ui-rule]]。
