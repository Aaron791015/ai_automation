> 📌 **範本內建的通用教訓。** 文中的「產品A／產品B／產品C」是範本原型留下的匿名實例，
> 只是為了讓教訓有具體場景 —— **教訓照用，例子換成你自己的產品**。

要斷定「這個角色（總監／中間商）**有沒有** 某項功能的操作入口」時，**窮舉選單名稱是不夠的** ——
必須拿到該功能的 **API 端點**，再反查哪一個頁面會呼叫它。

**Why**：功能的**內部名稱**與**畫面上的選單名稱**經常對不上，於是「選單裡沒有這個詞」會被誤讀成
「沒有這個入口」。實例（產品A，2026-08-11 開單 → 2026-08-21 推翻）：日誌類型 `游戏设置`(700000)
被判定為「總監後台完全沒有操作入口、只有總控會寫」，依據是把主選單 9 項＋設置 6 項＋下級管理
＋帳號下拉全部窮舉過一輪。實際上 **`设置 > 期数模板`** 頁面的「自动开盘」「可下注」兩個開關
寫的就是這個類型 —— 入口一直都在，只是頁面叫「期数模板」而日誌類型叫「游戏设置」。
（順帶一提：RD 當時列的是 `GameSetting/UpdateAutoCreateIssue`／`UpdateIsBetEnabled`，
但實測那兩個開關送的是 **`Issue/UpdateIssueTemplates`** —— 連 RD 給的端點都可能不精確，
所以第 3 點的「實際操作一次看送什麼」不能省。）
這個錯誤撐了 10 天、進了 JIRA 單、還寫進回歸案例的斷言，最後是 RD 在單上列出 API 端點才被發現。

**How to apply**：
1. 要主張「**沒有**入口」之前，先問：**這個功能對應哪支 API？** 沒有端點就別下這個結論，
   改寫成「窮舉選單未找到，端點未確認」。
2. 有端點時，**最省力也最決定性的作法是掃前端 bundle**：把該後台的所有頁面點過一輪
   （讓 lazy-load 的 chunk 都載入），再用 `browser_evaluate` 抓
   `performance.getEntriesByType('resource')` 裡的 `.js`，逐一 `fetch` 後搜尋端點字串。
   **命中 0 ＝ 該介面在程式層面就呼叫不到**，比窮舉選單強得多。
   ⚠️ **一定要放對照組**（挑兩個你確定存在的端點一起掃），否則掃不到時分不清是「真的沒有」
   還是「chunk 沒載到／字串被壓縮改寫」。
   ⚠️ 只抓 `document.querySelectorAll('script[src]')` 會漏掉動態 import 的 chunk
   （實測只看得到 1 個入口檔，實際有 78 個）。
3. 或者逐頁開啟候選頁面、實際操作一次，看 `browser_network_requests` 送出什麼 ——
   這也常會發現「RD 列的端點」與「UI 實際呼叫的端點」不是同一支
   （實例：`游戏设置` 日誌的總監入口實為 `Issue/UpdateIssueTemplates`，
   而非 RD 列的 `GameSetting/UpdateIsBetEnabled`；後者總監前端根本沒有）。
4. RD 回覆「後台其實有實作」並附上端點時，**先照著查證再回應** —— 這類回覆通常是對的。
5. 反向也成立：主張「**有**入口」時，要能指出是哪一頁的哪一個控件，不能只說「應該在設定裡」。
6. 這條與 〈產品專屬 memory〉 是**兩個不同的失誤來源**：那條講「用錯帳號層級
   會看不到選單」，本條講「看到了選單也可能認不出它就是那個功能」。兩個都要過才算窮舉完成。
