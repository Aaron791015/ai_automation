AI 自動化測試框架Framework Overview
給要一起用這套東西的人

測試的記憶，寫在檔案裡

一個 QA 用 Claude，快的是當下那一次。這套框架要解決的是下一次—— 讓每次探索、每條案例、每張單、每個沒驗完的尾巴，都自動落回純文字檔； 下一次（下週的你，或下一個新開的 Claude）就從那些檔案接著做。

先講它解決什麼

同一個團隊裡，每個人的 Claude 都很聰明，但彼此的做法與口徑對不起來 —— 這套東西處理的是「對不起來」的那一半，不是「聰不聰明」那一半。

痛點一
每次都要重講一遍
產品規則、環境、上次驗到哪，每開一個對話就要重講。講漏一句，它就用錯的前提做完一整輪。
痛點二
沒有人記得狀態
哪張單還沒開、哪個尾巴沒驗完、哪批測試資料還不能清 —— 這些單一次對話看不到， 而上一次的對話關掉就沒了。
痛點三
口徑各走各的
你說「這條驗到 L3」，對方理解成別的意思；他的覆蓋率 68% 和你的 68% 不是同一件事。
所以框架做的是三件事： 把方法論寫成 skill（該驗什麼、驗多深、期望值哪裡來）、 把紀律寫成會執行的指令（靠自律的規範一定會漂掉，所以做成 lint 與配號腳本）、 把狀態寫回固定的檔案（交接活文件、Bug 單、覆蓋矩陣）。

整套東西由四層組成

由下往上：規範 → 知識 → 執行 → 介面。 上面三層都可以單獨用；介面層（測試助手）是選配，不開它，其餘照樣運作。

規範層Rules
CLAUDE.md ＋ 9 支流程 skill —— Claude 一進來就讀的規則書， 以及「開工／探索／寫案例／開單／驗修復／壓測／收尾／回寫／提交」各自的作法。 每個產品另有一支 skill，裝該產品的不變量與「我要做 X → 讀哪一份」的意圖對照表。
知識層Knowledge
docs/ ＋ 交接活文件 ＋ memory —— 機制、公式、操作程序寫在 docs/； 「做完了／卡住了／哪批資料動過」寫在交接活文件；反直覺的坑放 memory（會主動浮現的那一種）。 三層各有職責，落錯地方就等於沒寫。
執行層Execution
pytest ＋ Playwright ＋ Allure，加上 scripts/ 的 25 支治理腳本 （lint_docs 體檢、gen_bug_index 配號、coverage_matrix 算覆蓋、 analyze_run 把失敗分成真失敗／前置未備／環境問題…）。 這一層不需要 AI 也能跑，終端機直接用。
介面層Assistant
測試助手（本機服務，各自跑一份、綁自己的 Claude 帳號）—— 把上面三層的東西收成看得到的清單：案例、Bug、待辦、執行紀錄、知識地圖； 再把常做的事做成按鈕：按下去就開一個已經載好規範、已經知道產品狀況的 Claude。

一件事怎麼從頭跑到尾

七站，每一站都有固定的產出、固定的落點。 最後一站把狀態寫回去，下一次的第一站就從那裡讀 —— 這個圈就是整套框架的重點。

01開工接手handoff
你按「開工接手」，或直接問「今天該做什麼」
AI讀交接檔的 blocker 與測試資料現況，列出可立即動手的事
留下什麼不寫檔 —— 這一站是讀
02探索新功能testcase-design ＋ browser-ops
你指定功能區塊與安全邊界（唯讀？可以下注？）
AI開瀏覽器實際走一遍，五個來源交叉盤點，標風險推深度
留下什麼docs/<產品>/ 的機制文件與覆蓋矩陣
03撰寫案例ui-test
你從覆蓋矩陣挑要轉成自動化的功能點
AI照矩陣產 pytest，落檔後當場 collect 驗證跑得起來
留下什麼tests/<產品>/test_*.py（終端機也跑得動）
04執行pytest ＋ Allure
你勾要跑的案例、選環境，按執行
AI不參與 —— 這一站是純機器，跑完自動分類失敗原因
留下什麼每一輪一個獨立目錄：輸出、Allure 報告、失敗分類
05開 Bug 單bug-report
你在產品頁的 Bug 分頁檢視它開了什麼，成立就轉給 RD、把 JIRA 單號回填
AI走開單前三問（是規格還是缺陷／是不是已經有單／樣本有沒有鑑別力）後直接開單，寫重現步驟與佐證
留下什麼docs/<產品>/bugs/<ID>.md，寫檔那一刻才配號（不回收、不撞號）
⛔ 只有一種情況要你先按：測試跑失敗生出來的草稿。 因為測試失敗不等於有缺陷 —— 同樣那幾條會反覆失敗，自動開單只會洗出一堆假單。 它自己判定的缺陷則直接開，那是有走過判斷的； 要你一筆筆核准未完成的判斷，等於把工作量還給你。
06驗 JIRA 修復jira-verify
你給單號（一次可以給一批）
AI逐張重現、比對實際值與期望值，判 PASS／FAIL 並留算式明細
留下什麼驗證報告 ＋ side effect 待驗清單（沒驗完的不會消失）
07收尾handoff ＋ writeback
你按「收尾體檢」，看它抓到什麼漏做的
AI把學到的知識分流落位、把狀態寫回交接檔，最後跑一次體檢
留下什麼交接活文件的待辦、blocker、測試資料現況
↻  回到 01 —— 下次開工時（不論是你自己，還是新開的一個 Claude）讀到的，就是第 07 站寫下的東西。
不必七站都走。只驗一張 JIRA 就走 01 → 06 → 07； 只跑回歸就走 01 → 04 → 07。頭尾兩站是固定的，因為那是「接得上」的唯一保證。

誰做什麼

分界線只有一條：需要判斷的事是你的，需要記得與重複的事是它的。

你
做判斷
開出來的單成不成立、要不要轉給 RD、這批資料能不能清、什麼時候可以發版。 框架不替你決定這些 —— 但也不會拿未完成的判斷來煩你： 該它判的它判完才給你看，你檢視的是結果，不是半成品。
Claude
做事與寫下來
實際去點、去算、去比對、去寫案例與報告，並把結果落回檔案。 它被規範綁著走：載哪支 skill、能碰哪些工具、寫入哪些路徑，都是宣告好的。 連 commit 也能請它代勞 —— 但要不要提交由你點頭。
平台
記得與開頭
掃檔案算出現況、把常做的事變成按鈕、開對話時先把前因後果講清楚。 它不自己實作邏輯 —— 底下跑的是同一批腳本與同一份 skill。

東西都落在哪

畫面上的實際是什麼檔為什麼重要
Bug 清單docs/<產品>/bugs/*.md 一張單一個檔，開頭那段就是狀態的單一事實來源。⛔ 整層不進版控（裡面有測試站帳密）
待辦與交接docs/<產品>/<產品>_驗證交接.md 每條產品線一份的活文件 —— 收尾寫的就是它，開工讀的也是它
測試案例tests/<產品>/test_*.py就是 pytest，不綁平台
產品定義config/products.json單一來源 —— 腳本與平台都讀它
執行紀錄每一輪一個獨立目錄輸出、Allure、失敗分類都留著，可回頭比對

沒有資料庫。全部是打得開、改得動的純文字檔，用什麼編輯器都看得到 —— 平台關掉，東西還在；出問題時你可以直接改那個檔，不必透過任何介面。

⚠️ 但別把它當備份。 docs/<產品>/bugs/（Bug 單、驗證報告）整層刻意不進版控 —— 裡面有測試站帳密。 也就是說這些東西只活在你自己這台機器上，換一台就不見了。 對外的正式流通管道是 JIRA，本機那份是工作底稿。

不能破的四條

這四條不是提醒，是寫進規範、而且大多有程式在擋的東西。

邊界怎麼守
⛔ 正式環境不碰 測試站可以自由寫入（下注、建帳號、改設定都是測試的常態）；正式環境一律不碰， 客戶在用的 STG 每次都要另外授權。
⛔ 資料庫只讀 查詢、對帳隨便跑；改值一律走畫面或 API。直接改 DB 會繞過所有應用層邏輯， 改出來的狀態未必是系統真的產生得出來的 —— 那樣驗到的結論不成立。
⛔ git 等你點頭 不是不能提交 —— 是不能自己決定要不要提交。 你在終端機用的那個 Claude 會幫你在本機 commit（訊息也它寫）， 但一定先把改了哪些檔攤給你看、你說可以才動手；在那之前連暫存都不做， 而且只送出自己動到的路徑。
平台開的任務 session 也能跑腳本、能寫檔（不然它照不了規範做事）—— 但 git 的寫入操作被擋下來：索引是整個工作目錄共用的，而它身邊沒有人可以點頭。 它改完檔，平台會在那一輪結束時列出「動了哪些檔」，由你決定要不要提交。
⛔ JIRA 只讀 單子要不要開、怎麼寫，是你跟 RD 的事。框架只把 JIRA 的狀態讀進來比對。
還有一條最容易被忽略的：實測與文件不符時，先問「有沒有人說要改」。 找得到人為的變更聲明（RD 的留言、PM 改需求）→ 更新文件； 只有「我量到不一樣」→ 那是缺陷，要開單，文件原句不動。 把缺陷改寫成規格，等於用測試者的手把 bug 合法化 —— 而且之後再也不會有人去驗它。

怎麼開始用

拿到範本之後三個指令，就有一個接好自己產品、可以開始跑的工作區。

步驟做什麼
先裝兩個Python 3.11+ 與 Node.js 18+ —— 兩個都是必裝。 少了 Node，瀏覽器起不來，而探索、重現、JIRA 重驗全都要瀏覽器 （症狀還很難查：它會安靜地少掉那幾個能力，然後交一份只驗得到讀取面的報告）。
① 建環境scripts\setup_test_env.ps1 —— 冪等，可重複跑
② 裝通用 memorypython scripts\bootstrap_workspace.py —— 把通用的 QA 教訓裝進本機
③ 接自己的產品python scripts\new_product.py --id ... —— 一次建好目錄、產品 skill、交接檔並註冊。 ⛔ 不要手動建，漏一步就不會被體檢檢查到
④ 第一次探索跟 Claude 說「載入 /testcase-design，我要探索某個功能區塊」，照它走。 這一步的產物就是你的知識起點。

不想用指令的話，這幾步在測試助手裡都是按鈕（設定 → 工作區）。

它是範本，不是成品

你一定會長出自己的流程 —— 那是預期中的。範本只保證起步一致。

畫面上的東西幾乎都是宣告出來的，不是寫死在程式裡： 一支工具是一份 *.tool.json、一顆任務按鈕是一份 tasks/*.json、 一個產品是 config/products.json 的一列。改這幾份檔就會改變畫面與流程，不必動平台程式。 用不到的刪掉、缺的自己加、整條動線換成你們現在的做法都可以。

⛔ 但有一小塊必須保持共用，否則團隊價值就沒了。 共同語言那二十來個名詞 —— 深度分級、風險對應深度、期望值來源分級、覆蓋矩陣的欄位、 Bug 狀態值、驗證結論五值。這些分岔了，大家就看不懂彼此的報告： 你說「驗到 L3」對方理解成別的意思，他的覆蓋率 68% 和你的 68% 不是同一件事。 要改可以，但要一起改。
想動手看細節？ 平台的使用手冊（/static/manual.html）有每一頁、每一顆按鈕的實拍畫面與四段說明； 工作區根目錄的 README.md 是上手五步與治理腳本表； CLAUDE.md 是給 Claude 讀的規則書 —— 你不必先讀完它。
