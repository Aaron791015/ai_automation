## 1. 定位：平台 ＝ **帶狀態的 Claude Code**

⛔ **不是** Claude Code 的簡化版，**不是**把對話包成表單。

| 純終端 Claude Code | 平台 |
| --- | --- |
| 對話 ✅ | 對話 ✅（`#/sessions` ＋ 全域的置中大視窗；**已接真**，走 MCP 讀平台索引） |
| 狀態隨對話結束消失 | **持久索引**（案例／Bug／待辦／覆蓋率／run 歷史） |
| 看不到別的 session 在做什麼 | **跨 session 視野**（本工作區常態併行） |
| 線性 | **非線性瀏覽**，一眼看全貌 |
| 逐次 permission prompt（只有當事人看得到） | **`propose_run` 確認卡** —— 提議可被檢視、可被記錄 |
| 只有自己 | **可作為團隊範本分發** |

**平台的價值在「對話給不了的東西」，不在取代對話。**

### 分工原則

```
平台：看狀態、觸發已定義的任務、瀏覽歷史、跨產品比較
對話：探索、判斷、追問、改變方向、寫報告
接點：平台觸發 session → session 產出結構化 markdown → 平台索引與渲染
```

**判準：這個流程已經寫成 skill 了嗎？**

| 適合放平台 | 留在對話 |
| --- | --- |
| 已標準化的流程才跑得穩 —— 依 `testcase-design` 產覆蓋矩陣、依 `jira-verify` 走重驗、依 `bug-report` 產 Bug 草稿、分析測試結果三分類 | 沒有 skill、需要來回追問的 —— 新功能首次探索、規格對不上時的追查 |

## 2. ⭐ skill 是平台的大腦

平台起的 session 讀的是 **`CLAUDE.md` 與 `.claude/skills/`**（cwd=repo root，自動載入）—— 對話與九支任務按鈕都是。

> **skill 品質直接決定平台回答的品質。**
> 所以 `testcase-design`、`writeback`、`handoff` 等 skill **不是平台的周邊，是它的前置條件**。
> 平台上沒有「產出覆蓋矩陣」這顆按鈕，是因為那支 skill 還不存在——不是因為 UI 沒做。

⇒ **skill 與規範沒成形前，先不要擴張平台功能。**

## 3. 分發模式：各自跑實例，**不服務化**

`config/platform_config.json` 綁 `127.0.0.1:5300`、每人用自己的 Claude 帳號 —— **這是正確設計，不是待改進的限制**
（理由見 `README.md`「啟動」節：改 0.0.0.0 別人連進來會用你的額度與 OS 身分執行 run）。

**因此下列全部不需要**：部署、多人併發、身份系統、權限系統、帳號池。

**範本分發的是「結構」，不是「服務」** —— 同事 clone 下來在自己 PC 跑、餵自己產品的知識。
真正要處理的是**範本化**（產品定義收斂成單一來源、`new_product.py` 接入 SOP），不是服務化。

### G 的實際進度（2026-08-23 實跑後更新）

**三支壓測全部接真**，每支都跑過真實輪次並與舊控制台比對產出。

| 工具 | 真實輪次 | 產出比對 | 「填了不生效」欄位 |
| --- | --- | --- | --- |
| **七星** | 幸運五星彩 running→completed／exit 0 | 檔案組成**零差異**，四份 JSON 欄位一致 | **0** |
| **CRUX** | 總監3（僅會員）completed／exit 0 | 檔案組成零差異；平台執行的「期數回收」把 preflight 從 ❌ 修到全綠 | 1（`remark`，引擎無此旗標） |
| **wbot** | smoke 輪次 completed／exit 0<br>下注 3／成功 3、退碼 3／成功 3、**無殘留注單** | 檔案組成零差異 | **0** |

⚠️ **實跑才發現的問題**（讀程式碼看不出來，這是為什麼一定要真的跑一輪）：

**平台側**

1. **`CliAdapter` 的 run 型四個方法還是 `NotImplementedError`** ——
   三支壓測的主命令按下去會直接炸。階段 C 只做了 `PytestAdapter`。
2. **直譯器選錯**：平台一律用 `.venv`，但 `.venv` **沒有 `locust`／`gevent`**
   （CRUX／七星要用系統 Python，兩支工具自己的 `run_server.bat` 早就寫明）。
   而三支 tool.json 的 hint 當時還寫著「統一 .venv，已含 locust」。
3. **16 對重複欄位**：補欄位時以 key 去重，但控制台的 id（`master_count`）
   與 tool.json 的 key（`masters`）是同一設定的兩種叫法。最糟的一對是
   `--wallet-check` 與 `--no-wallet-check` 同時送出 —— 引擎會直接拒絕執行。
4. **8 個欄位掛錯命令**：控制台「OpenAPI 壓測」頁的設定被塞進了下注壓測，
   **填了不會生效，而且看不出來**。
5. **`health()` 只長在 `CliAdapter` 上**，基底是「永遠回 ok、零檢查」——
   `ui_tests` 的健康檢查頁一直是**假綠燈**。已移入基底，所有 adapter 共用。
6. **沒有人把平台 phase 從 `starting` 推到 `running`** —— 一輪跑 30 分鐘的壓測
   從頭到尾顯示「啟動中」，儀表板的「執行中 N」也算不對（兩個 adapter 共通）。

**被吸收的工具側**（吸收會逼出原本沒人碰到的介面缺陷）

7. **wbot `preflight_check.py` 拿 `masters[0]` 的帳號配 `Environment.master_url` 的網域**
   —— 而後者指向另一個主投的站台。症狀**極具誤導性**：
   P-01 登入**綠燈**（帳號全站共用），P-02 才炸成
   `GetPlayerList 301 → https://www.baidu.com/`，
   而 P-01 的修復建議寫著「網址過期，請到總控重新複製」——
   照著做完全查不到，因為 `masters[0].url` 一直是對的。
   `runner/wbot_runner.py:272` 早就用 `account.resolve_url()` 修好，只有 preflight 沒跟上。
8. **wbot `resolve_params()` 從不讀 body 的 `run_id`** ——
   `RunParams` 明明有這個欄位，外部指定的值被**靜默丟掉**，
   於是引擎開在另一個目錄名下、報告全部找不到，**而沒有任何錯誤訊息**。
9. **wbot `run_perf.py` 少開 10 個旗標** —— 那些設定 `RunParams` 早就有、
   控制台也填得到，只有 CLI 沒開口，於是在平台表單上填了不生效。已補齊。

⛔ **壓測是真金流下注** —— 本輪的驗證輪次都刻意壓到最小規模
（3～5 會員、2～3 分鐘；CRUX 用 `--no-director` 不動關盤結算；
wbot 用 `smoke` profile：每人每期 1 注、下注後立即全退、不留殘留注單）。

## 6. 新工具的專屬頁面：三層擴充原則

**多數工具不需要生成頁面** —— 新增一個 `.tool.json` 就會出現在 `#/tools`，
參數表單由 `ui/form.js` 依 12 種 field type 動態渲染，`views/` 底下**沒有任何工具專屬視圖**。

真的遇到宣告式不夠用時，**依序往下走，不要跳級**：

| 層 | 做法 | 可複用？ |
| --- | --- | --- |
| **①** | 用現有宣告能力：field type／`run.phases`／`metrics`／`artifacts`／`options_from` | — |
| **②** ⭐ | **擴充宣告能力**：新增一個 field type 或 result kind，讓所有工具都能用 | ✅ **是**（`case_picker` 就是這樣來的） |
| **③** | 才寫 `views/tools/<tool_id>.js` | ❌ 一次性 |

⭐ **優先擴充「宣告能力」而非新增「專屬頁面」** —— 前者讓後續每個工具受益，後者只服務一個工具卻要長期維護。

第③層的四條規範見 `CONTRIB_TOOL.md` 第 9 步。
