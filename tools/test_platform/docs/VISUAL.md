## 主題與色票

**權威來源是主題檔，不是這裡，也不是 `tokens.css`**：

```
.claude/skills/theme-factory/themes/starlight-telemetry.md
```

`tokens.css` 的每個色票值都必須能在主題檔找到對應 —— **不得在 CSS 裡憑感覺加顏色**。
要調色先改主題檔，這是 `theme-factory` 的流程（產出主題 → 給使用者審核 → 才套用）。
前兩次改版失敗都卡在這一環：直接改 CSS，使用者看到成品才說「不是理想中的畫面」。

| 角色 | 值 | 備註 |
| --- | --- | --- |
| 底 | `--bg #020a14` | 最深止於 `#04080f`，不用純黑 |
| 面板 | `--panel-top rgba(10,25,41,.66)` → `--panel-bot rgba(4,13,23,.74)` | ★ **半透明，而且比底色更暗** —— 背景輝光要透得出來 |
| **面板框線** | `--frame rgba(77,160,200,.38)`／`--frame-on rgba(127,213,240,.80)` | ★ 卡片的識別在**框**，不在面 |
| 內部分隔線 | `--border #1b3040`／`--border-strong #27506a` | 與面板框線是**兩件事**，不要混用 |
| 正文 | `--text #d0e0f5`／次要 `--text-muted #97abc4` | 對比 ≥ 7:1（13.2／7.5） |
| 卡片標題 | `--title #adc2dc` | ⚠️ **淡鋼藍，不是飽和藍**。飽和藍只給線條與圖表 |
| 主藍／次藍 | `--accent #7fbbf0`（8.65:1）／`--accent-2 #297de0`（4.3:1） | ⚠️ **次藍不可當文字**，只給線條與填色 |
| 金／綠／紅 | `#f0b429`／`#4ade80`／`#ff5a5f` | 語意色，**不參與色相旋轉** |

### ★ 色相：藍（208–214°），不是青（2026-08-21）

原本主色落在 **193°（青）**，參考圖是 **208–214°（天藍）** —— 使用者比對後指出
「我們是青色，參考圖是藍色」。全站以**色相 +14°（上限 214°）**整組旋轉，
共 24 種顏色（含 `js/ui/hero.js` 裡星雲／星系的漸層），語意色與七星紫不在範圍。

| | 前 | 後 |
| --- | --- | --- |
| 主訊號 | `#7fd5f0`（193°） | `#7fbbf0`（208°） |
| 次藍 | `#29a8e0`（200°） | `#297de0`（212°） |
| CRUX | `#4fd2ff`（193°） | `#4fa9ff`（209°） |

⚠️ **旋轉之後一定要重量對比。** 藍的亮度係數（.0722）遠低於青所含的綠（.7152），
**同樣的 HSL 明度旋過去就會變暗**。本次有兩個值因此跌破紀律，已修：

- `--text-muted` 6.86 → 提亮到 `#97abc4`（7.53:1）
- 連結由 `--accent-2`（4.3:1）改為 `--accent`（8.65:1）；`--accent-2` 只留給線條與填色

📌 **`--danger #ff5a5f` 在面板上是 5.8:1，低於「≥ 7:1」的紀律 —— 但這是刻意保留的。**
2026-08-21 使用者裁示：**紅是語意色，不改色。**
理由是「紅＝有問題」的辨識一致性比這 1.2 的對比差距重要，而且它總是伴隨燈號或標籤出現。
⛔ **不要為了讓對比稽核全綠而動它** —— 這不是漏網之魚，是決定。

**產品色**逐點取樣自參考圖對應物件的色相：

## 形

**圓角，不切角。** 這是第三版最大的一筆改動 —— 前兩版用的是切角＋L 型角標＋掃描線的
**軍事 HUD** 語彙，而參考圖是**乾淨的金融儀表板**：圓角矩形、無角標、無掃描線。
氣質完全不同，這是「怎麼調色都還是不像」的主因。

- `--radius 3px`（按鈕／輸入框）、`--radius-card 4px`、`--radius-modal 6px`、pill `999px`。
  ⚠️ 原訂 6/10/12，**2026-08-21 依參考圖收小**：10px 讀起來是「卡片」，4px 才讀得出「儀器面板」。
- ⛔ **不要再加回** `clip-path` 切角、`::before/::after` 的 L 型角標、`.scanline` 掃描動畫。
  「執行中」改用**卡片邊框轉青＋左緣光棒**表示。
  > ⚠️ 2026-08-21 抓到一個**從第一版活下來的漏網之魚**：`.metric::after` 是右上角的 L 型角標，
  > 第三版拆 HUD 語彙時只掃了 `clip-path`，沒掃 `::before/::after` 的小方框，所以它躲過了。
  > **巡查時要連 pseudo element 一起看**；`css` 全掃一次的判準是
  > 「6–8px 見方、只有兩邊有 border、背景透明」的偽元素。</br>
  > 現在可以用這段在 console 自查（回傳應為 0）：
  > ```js
  > [...document.querySelectorAll('*')].filter(e => ['::before','::after'].some(q => {
  >   const cs = getComputedStyle(e, q);
  >   return cs.content !== 'none' && parseFloat(cs.width) <= 8 && parseFloat(cs.height) <= 8
  >     && (cs.borderTopWidth !== '0px' || cs.borderRightWidth !== '0px')
  >     && cs.backgroundColor === 'rgba(0, 0, 0, 0)';
  > })).length
  > ```
- 留白放大：卡片 padding 14px、標題與內容間距 **15px**、卡片間 gap 14px。
- ⛔ **卡片標題與內容之間不畫線** —— 參考圖的面板沒有任何標題分隔線；
  加了線之後每張卡都被切成兩塊，畫面會碎掉（2026-08-21 比對後移除）。
- 分段控制（報告頁篩選）用**圓角膠囊**，不用 `<select>`。

## 光影：背光的 HUD 面板（2026-08-21 重做）

**單一光源，但光在「後面」，不是在上面。** 語彙定義在 `css/tokens.css`，加新表面時沿用。

| token | 用途 |
| --- | --- |
| `--panel-top` / `--panel-bot` | 面板填色（半透明，比底色更暗） |
| `--frame` / `--frame-on` | 面板框線（靜／hover） |
| `--frame-glow` / `--frame-glow-on` | 框線外輝 ＋ 內側頂緣一線微光 |
| `--edge-lit` / `--edge-lit-on` | 巢狀面板的內側頂緣微光 |
| `--sunken` | 凹面（輸入框、下拉、code 區） |
| `--lift-1` / `--lift-2` | 離地投影，**只給真正的浮層** |
| `--glass` | 浮層的 `backdrop-filter` |

### ⚠️ 這一段被推翻過一次，兩版差在哪

| | 第一版（08-20，已作廢） | 現行（08-21，依參考圖） |
| --- | --- | --- |
| 光的方向 | 前上方打光 | **背光** |
| 面板 | 比底色**亮**、不透明、上緣高光 | 比底色**暗**、**半透明**，讓背後輝光透出來 |
| 識別 | 面的明暗 | **框線** ＋ 框線外輝 |
| 深度 | 離地投影 | 背景輝光 ＋ 框線外輝 |

第一版把卡片做成了**實體浮雕面板**，與參考圖的 HUD 氣質相反 ——
2026-08-21 使用者拿參考圖比對後改掉。**不要改回去。**

> 第一版留下的一條結論仍然成立、且是這次改法的根據：
> **在 `#020a14` 這種近黑底上，黑色投影幾乎沒有色差**（色差不到 2/255，等於沒畫）。
> 所以投影只留給**真正壓在內容之上**的層：modal／指令列／dock／toast／tooltip。

### 氛圍的唯一來源是 `body::before`

參考圖的畫面之所以「有氣氛」，是因為背景有一團**中央偏下的青色輝光**
（`rgba(45,170,225,.30)`，1250×780；參考圖裡是地球那一帶），面板半透明地疊在上面。
**調暗這一層，整個畫面就會回到死平** —— 它不是可有可無的裝飾。

⚠️ `main.view` **不要自己再打光**：那會把面板的透光洗掉，等於白做。

### 層級規則

- **凸面 vs 凹面**：面板／按鈕／表頭是凸（框線＋內側頂緣微光）；輸入框／下拉／code 是凹（`--sunken`）。
- **巢狀面板**（`.card .card`、`fieldset.section`、`.hint`）用 `--panel-in` ＋ 更淡的框線，
  **不給外輝** —— 同一組值套兩層會讀成同一個平面。
- **hover 只改框線與外輝，不做位移** —— 卡片一移動，裡面的數字與表格會跟著抖。
- **浮層一律玻璃**：半透明 ＋ `--glass` ＋ `--frame-on` ＋ `--lift-2`。

## 字

字型檔自帶於 `web_ui/static/fonts/`（OFL 授權，離線也一致），latin 子集，`font-display: swap`。
中文不自帶（完整繁中 5MB+ 不划算），fallback 走 `"Noto Sans TC", "Microsoft JhengHei"`。

| 角色 | 字體 | 用途 |
| --- | --- | --- |
| 顯示 `--font-display` | **Sora 600** | 品牌、卡片標題、柱面產品名 |
| 正文 `--font` | **Inter**（可變字型，一支檔涵蓋所有字重） | 全站正文、標籤、**所有大數字** |
| 等寬 `--mono` | **JetBrains Mono 400** | console／log／nodeid／run_id 等真正的代碼 |

⚠️ **大數字用 Inter ＋ `tabular-nums`，不用等寬字。** 等寬讀起來是「終端機」，
參考圖是幾何無襯線細體大字。等寬只留給真正的代碼。

### ★ 型階的落差本身就是質感（2026-08-21）

參考圖的「質感」有很大一部分不是顏色，是**標籤與數字的落差**：
標籤極小（約 9px）、字距拉到 `.22em`、顏色沉；數字大（約 30px）而且**細**（300）。
兩者差 3 倍以上，一眼就分得出層級。先前是 10px 對 21px（差 2.1 倍），
讀起來像一般表單，沒有儀表板的重量感 —— **調完色仍覺得「不像」時，先檢查這裡。**

| 角色 | 值 |
| --- | --- |
| 大數字 `.stat .v` / `.metric .v` | **2rem / weight 300 / `-.015em`** |
| 數字標籤 `.k` | **.57rem / `.22em` / 大寫 / `--text-muted`** |
| 卡片標題 | .64rem / 600 / `.2em` / 大寫 |
| 表頭 | .63rem / `.18em` / 大寫 / `--accent` |
| 正文 | 13px |

⚠️ **標籤不要再調暗。** `--text-muted` 在新面板上是 7.15:1，已經貼著「≥ 7:1」的下限。
參考圖的標籤更暗（約 5:1），但那是行銷渲染圖，不是要盯一整天的工具 —— 這一項**刻意不照抄**。

⚠️ **側欄的「系統概況」用固定五欄 grid，不要交給 `flex-wrap`。**
側欄只有 380px，數字放大到 2rem 之後 flex 會在第 5 個折行，卡片憑空長高、把下面全部推掉。

⚠️ 表頭由 `--accent-2` 改為 `--accent`：前者在新的暗面板上只有 6.5:1，低於紀律。
（舊有問題，面板變暗後才量出來。）

## 版面

- **殼**：左 64px icon rail（底部 Claude 連線燈）＋ 44px 細 header＋全域右下浮動 dock。
- **總覽單屏、三塊**（2026-08-24 重排）：**頂部狀態列（全寬）** ／ 左 HERO 主視覺 ／

  > 原本的三張狀態卡（系統狀態／執行狀態／環境健康）**合併為一張「系統概況」**，
  > 省下兩組卡框與標題列，正是騰出空間的關鍵。
  >
  > ### ★ 卡片的「存在」不該靠捲動才發現（2026-08-24 使用者回報）
  > 合併之後側欄仍有五張卡、自然高度超過欄高，於是「待辦與 Bug」「助手提示」
  > 整張落在摺線下 —— **連標題都看不到**，使用者根本不知道有這兩張卡。

  > 於是「有幾張卡」變成版面保證的事，不是運氣。
  > ⛔ 不要再往側欄加第五張卡 —— 加了就回到原狀。內容可以捲，標題不行。
- **其他頁**：`.page` = flex column，`page-head`／`page-bar`／`page-foot` 固定，
  內容區單區捲動 —— 操作列與選取列永遠可見。
- **小螢幕降級**：`max-width:1279px` 或 `max-height:759px` 時側欄改為主視覺下方橫列並解鎖頁捲。

## HERO 場景（總覽主視覺）

`viewBox="0 214 1200 606"`。由後往前四層：**深空 → 地板電路 → 產品基座列 → 螺旋星系**。

### 深空背景（`bgCache`，只算一次）

星雲色暈 → 斜過畫面的銀河帶（620 顆）→ 星空 → 地板資料點。
⚠️ 這一層純屬氛圍、與資料無關，**必須快取** —— `drawHero()` 會被 store 訂閱與輪詢反覆呼叫，
每次重算約 2,000 個節點的字串是白花的。

### 產品基座（`slotsFor(n)` 自動等距排開，加產品不必改版面）

寫實金屬基座（三段柱身＋分模線＋底盤外沿）＋投影裝置（光錐／掃描橫帶／發射環），
柱面刻三行字（產品名／案例數／BUG·HP）。上方是**真 3D 全息體**。

> ⚠️ **整座基座（柱身／底盤／外沿）一律半透明，不可用不透明填色**（2026-08-19 使用者三次指正定案）——
> 不透明（柱身原為 `drumGrad`、底盤 `#060f19`、外沿 `#071019`）會在地板與星空上壓出一整塊近黑量體，
> 把密集節點打斷成三個黑洞。現值：柱身 `fill-opacity .42`、底盤 `.3`、外沿 `.24`
> —— 星空與地板電路都穿得過去，讀起來就是**玻璃台座**（等同 `.dim` 狀態那種通透感），
> 又比完全不填色保有體積感。
> ⚠️ 要再調低前先確認柱面三行字（產品名／案例數／BUG·HP）還讀得清楚 —— 它們就疊在柱身上。

### ★ 真 3D 全息投影（`ui/model3d.js` ＋ `ui/models.js`）

前兩版物件是手繪 2D 多邊形，**沒有面的前後關係**，所以再怎麼加細節都不夠寫實
（使用者連續三輪指出）。第三版改成真的頂點／面模型：

① 透視（近大遠小）② 面的前後遮擋 ③ 依法線的明暗 ④ 背面不剔除、畫得更暗（全息體要看得穿）

| 產品 | 題材 | 組成 |
| --- | --- | --- |
| CRUX | **開獎搖球機** | UV 球艙＋頸環＋錐台機身＋底盤；艙內 10 顆球標 0–9（獎號由 0–9 組成） |
| 七星 | **渾天儀** | 赤道環／子午環／黃道環（傾斜 23.5°）＋中心球＋地平環＋雙支柱；七顆星釘在黃道環上 |
| 投注機器人 | **聊天室** | 懸浮對話視窗＋兩個浮泡＋發射座；面板 `yaw = -0.62` **抵銷全域視角**才會正對觀者 |

> ⚠️ 最後那條是踩過的坑：面板若跟著場景一起轉，投影後只剩斜斜的平行四邊形，看不出是視窗。

**共通刻意沒有基座** —— 它貫穿所有產品，知識量改為散佈成整個場景的星塵。

### ★ 點數 ＝ 知識量（資料誠實的 signature）

```
亮點數 = min(340, 案例 + 規格檔 + 驗證紀錄 + 活躍 Bug)     ← 依面積加權灑在 3D 表面
暗點數 = max(0, 60 - 亮點數)                              ← 補到最低密度，明顯較暗＝「尚未取樣」
```

亮點依種類分亮度，**活躍 Bug 畫成紅點** —— 有問題的產品線一眼看得出來。
另有固定 420 顆掃描顆粒屬純質感，不帶語意。
（`ui/pointcloud.js` 只剩 tooltip 說明與底部 bloom；2D 點陣引擎已被 3D 取代。）

### 中央：螺旋星系 ＋ 融入其中的知識雷達軌道

地球移除（使用者要求），改為代表「整個測試宇宙」的螺旋星系：核球＋兩條對數螺線旋臂＋盤面散星。
原本在側欄的知識雷達五圈改成**星系外圍的軌道環**融進主視覺：五條壓扁橢圓（規格／案例／缺陷／紀錄／健康），
每個產品在軌道上佔一段弧，弧長＝正規化值；進行中的 run 以推進弧疊在外圈。

## 動態紀律

- **明顯吸睛的動態 ≤ 3**（狀態燈脈動、執行中光管脈動、進度弧推進）。
- HERO 的光管呼吸、投影閃爍（5.5s）、rail logo 旋轉屬**環境級氛圍**，不計入上限。
- **★ hover 擺動**：游標停在某座基座上時，**只有那一個**全息體繞 Y 軸來回擺 ±0.28 rad（≈16°），
  5.2s 一個週期；移開後緩降回基準視角。三道成本控制：
  ① 一次只有一個產品在動 ② 上限 30fps ③「降低動態」下完全不啟動。
  > **為什麼是擺動不是整圈旋轉**：wbot 是平面聊天視窗，轉到 90° 會整個消失；
  > 而搖球機與渾天儀整圈轉會變成「轉盤展示」，參考圖的全息體是懸浮微擺。
  > ±16° 已足夠讓球艙的前後面、渾天儀三圈的交錯關係跑出來。
- ⚠️ **擺動一定要逐屬性更新，不能每幀重寫 `innerHTML`**（實測 8.6ms/幀 → 3.2ms/幀）。
  做得到是因為明暗用**模型空間**法線算、與視角無關，且面序沿用基準視角的排序
  —— 於是每幀真正要改的只有 `d`／`cx`／`cy`／`r`／`opacity`。
- ⚠️ 寫「降低動態」的關閉規則時**要檢查特異度** —— `.hero .globe.state-idle .globe-edge`（0-4-0）
  會壓過 `html[data-motion="0"] .hero .globe-edge`（0-3-1），開關就形同失效（2026-08-19 實測抓到）。
- ⚠️ **不要在 `.glyph-wrap` 上掛濾鏡** —— 那會把上千個子節點整組送去高斯模糊，
  游標拖過去會明顯頓。發光一律用 `drop-shadow()` 掛在細線元素上。
- 發光只給邊框與 ≤24px 小面積，**絕不給正文**；正文對比 ≥ 7:1。背景格線透明度 ≤ .035。
- **全域「降低動態效果」開關**（頂欄 ✦；預設尊重 `prefers-reduced-motion`；`html[data-motion="0"]`）
  —— 一律**全部停止**，包含環境級動態與 hover 擺動。
- **★ 換頁轉場**（`main.view.view-enter`，2026-08-20）：一道青色光帶由左掃到右
  —— 寬 **33% 畫面**、**1s** 等速掃過；同時內容區上緣掃過一條光線（.45s）。
  轉場是**瞬時**的，不計入「明顯動態 ≤ 3」的上限。
  - ⚠️ **緩動要等速**。原本用前重曲線，光帶在前 1/3 的時間就掃完、剩下都在畫面外空轉，
    那時**把 duration 調長也不會變慢**，只是空轉更久。掃描光本來就該等速。
  - ⚠️ 改光帶寬度時位移量要跟著改：**位移量 ＝ (100% + 光帶寬) ÷ 光帶寬**（寬 33% → 400%），
    少算的話光帶還沒離開畫面動畫就結束、會直接消失。
  - ★ **只動蓋在上面的兩個 pseudo element，不動內容**。這條是硬規則，見下方〈換頁的效能〉。
  - ⚠️ CSS 動畫是在元素**開始符合選擇器**的那一刻起跑，所以 `router.js` 必須
    **先掛 class 再讓 view 插入內容**；`remove → 讀 offsetWidth → add` 那三行是重啟動畫用的，
    少了中間那行，連續換頁時 class 沒變化就不會重跑。
  - ⚠️ `main.view` 是 flex 容器，`::before`／`::after` 必須 `position: absolute` 出流，
    否則會變成額外的 flex item 把版面撐開。
- **★ 執行中狀態**（2026-08-20）：使用者的判準是「**設定測試執行後，回到總覽，就知道是什麼任務正在進行中**」。
  - ⚠️ **光效只能暗示，不能代替文字**。基座上方掛「執行中標籤」，直接寫**工具名 · 階段 · 進度%** ＋ 進度條。
    加上行進虛線的頂面環與光柱裡上升的能量點，執行中的那一座就已經夠顯眼。
  - ⛔ **不要把沒在跑的基座壓暗**。曾經做過（`opacity: .34`），2026-08-20 使用者裁示移除 ——
    上面那組訊號已經足夠，壓暗只是讓另外兩個產品的案例數／Bug／健康度變得難讀。
    長工具名由 `fitName()` 先縮字級再截斷 —— SVG 的 `<text>` 沒有 ellipsis，不處理就會撞上百分比。
  - 側欄的「運行中」卡在有 run 時**升到最上面**（`.dash-side.has-run` → `order: -1`）並放寬到 340px。
    先前它固定排第二、內容鎖 168px，兩個 run 就有一個被切掉半張，答不了上面那個判準。
- **★ 閒置動畫**（2026-08-20）：全息投影每隔一陣子「重建」一次 —— 一條亮線（＋一層淡暈）
  由下往上掃過字樣，掃到時發射環同步亮一下，像投影在刷新。取的是主視覺本來就有的語彙
  （投影機、掃描帶、取樣點），不是憑空加一個效果。三條紀律：
  - **週期 4.2s、掃描只佔前 33%（約 1.4s），其餘 2.8s 完全靜止**
    （使用者 2026-08-20 指定「3–5s 顯示一次」）—— 屬環境級氛圍，不計入上限。
  - **三座同步**（使用者同日裁示「不用輪流」）。先前是錯開相位，結果三座接力之下
    幾乎沒有全靜的時刻；同步反而更省，也更像「整個投影系統一起刷新」。
  - **執行中的那一座不播** —— 那時該由執行中標籤與行進虛線說話，兩套動畫疊在一起會打架。
  - ⚠️ 掃描帶會經過字樣那一片點雲，動的時候底下那塊要重新光柵化
    （headless 實測整個週期平均 +2.8ms/幀；週期由 11s 縮到 4.2s 是主因，同步本身是省的）。
    所以**一定要留靜止的空檔**，不要把可見比例調高或把週期縮短到沒有空隙；
    也**不要改成動 `.glyph-wrap`** —— 那個群組底下約 1,800 個節點，等於每幀重新光柵化一大片。
- 規則式產出（助手提示）要在 UI 標「規則式」，與 Claude dock 的版面分開，不用「AI 分析」措辭。
  > 📝 2026-08-24 移除**播報 ticker**（使用者：「用途不大」）。它原本負責回答
  > 「人怎麼知道有東西可以看了」—— 那份資訊現在由對話串流的 `drafts` 事件承接。

## 效能

### ★ 捲動卡頓與畫面跳動的三個成因（2026-08-24 使用者回報）

使用者：「檢視檔案內容時，滾動會卡頓、畫面跳動／對話視窗滾動卡頓」。實查是三件事：

| # | 成因 | 為什麼會這樣 |
| --- | --- | --- |
| **①** | **巢狀捲動鏈** | `.docview-body`（`max-height:66vh; overflow:auto`）巢在 `.modal .box`（`max-height:88vh; overflow:auto`）裡。內層捲到底之後**事件往外傳**，整個對話框自己滑一截 —— 那就是「畫面跳動」 |
| **②** | **不透明面板上的 `backdrop-filter`** | `.rail` 早就因為這個被拿掉（實測 11ms/幀），但 `.modal .box`（93~95% 不透明）、`.dock-panel`（96~97%）、`.toast`、`.cmdbar .box`、`.chat-portal` 全都還留著。**模糊一片自己已經蓋住的東西＝花成本買 0** |
| **③** | **浮層開著時，背後還在動** | 全螢幕遮罩的 blur 成本 ＝ 面積 × 背後多久變一次。背後只要有**任何**無限迴圈動畫（rail 旋轉環、AI 燈呼吸、入口訊號點、掃描線），就得**每一幀重算整片模糊** —— 即使那些動畫早被糊掉、根本看不見 |

處置：① 所有內層捲動容器加 `overscroll-behavior: contain`，docview 開啟時由
`.box.no-scroll` 把外層那一層捲動關掉；② 只有**全螢幕遮罩**保留 blur，
不透明的框一律不放；③ `body.overlay-open` 時把背後的迴圈動畫 `animation: none`。

**實測（headless，同一份 40 幀的捲動）：7,448ms → 4,620ms，快 38%。**
⚠️ headless 走 CPU 軟體算圖，會**放大** backdrop-filter 的成本；
實機的差距會小一些，但方向與排序是可靠的。

### 對話視窗：卡頓不是 CSS，是重畫頻率

`streamReply` 每收到一個 SSE 片段就 `draw()` 一次，而 `draw()` 是**整個訊息區重建**
＋每則重跑一次 markdown 渲染 —— 串流一段長回覆是每秒數十次。
而且每次都 `scrollTop = scrollHeight` **強制拉到底**，人往上捲的動作當場被搶回去。

→ `scheduleDraw()` 用 `requestAnimationFrame` 合併成「一幀最多畫一次」，
並且**只有原本就貼在底部時才自動捲**。
⛔ 不可以改成節流計時器：最後一次更新會落在計時器上，`done` 之後畫面會停在
倒數第二個片段。rAF 天生對齊繪製，沒有這個尾巴。


主視覺約 6,900 個 SVG 節點，靠三件事撐住：

1. **內容簽章**（`overview.js` 的 `heroSig`）—— 資料沒變就不重畫。這是最有效的一招
   （10 次輪詢 372ms → 2.8ms）；背景字串快取幫不上忙，因為成本在 DOM 解析不在組字串。
2. **零 SVG `filter: url()`** —— 全改 `drop-shadow()`（60 次 mousemove 8.1ms → 6.8ms）。
3. **tooltip 走 rAF 節流 ＋ `transform` 定位**，不觸發 layout；密集層加
   `shape-rendering: optimizeSpeed`、`pointer-events: none`、`contain: paint`。

> ⚠️ **headless 量不到真實幀率**：軟體光柵下「這一格有沒有重繪」就決定成本，
> 關掉 39% 的節點量到的 rAF 間隔完全沒變。上面的毫秒數都是**主執行緒 JS 成本**，
> 順不順仍須在真瀏覽器目視確認。

### ★ 換頁的效能：保住 view，不要重建

主視覺是 **5,347 個 SVG 節點**。實測「讓它重新出現」的成本差距一個數量級：

| 做法 | 成本 |
| --- | --- |
| 重建 DOM（`innerHTML`，408KB 標記） | **86 ms** |
| 把上次建好的節點搬回新容器 | 58 ms |
| `display: none` → 顯示 | 38 ms |
| `visibility: hidden` → 顯示 | 27 ms |
| **`content-visibility: hidden` → `visible`** | **8–12 ms** |

所以 `router.js` 改成**一個 view 一個 `.view-pane`**，重的頁面宣告 `keepAlive = true`
（目前只有總覽）：切走時只加 `.pane-off`，切回來時拿掉。`content-visibility: hidden`
會保留算好的排版狀態，恢復幾乎不用重排 —— 這是唯一能把換頁壓進一格 16ms 預算的做法。

三件配套，缺一就會把省下來的賠回去：

1. **`keepAlive` 的 view 要有 `pause()` / `resume()`** —— 切走時停掉輪詢與訂閱（但**不動 DOM**），
   切回來重新訂閱並用手上的資料立刻重畫。
2. **任何持續寫 DOM 的東西都要跟著停**。輪詢、打字機、計時器沒停時，
   Chrome 會回報「Rendering was performed in a subtree hidden by content-visibility」——
   等於在隱藏的子樹裡繼續排版。所以 keepAlive 的 view 一律要在 `pause()` 裡清掉。
   （原本的例子是播報列的 4s 輪詢與 18ms 打字機，該元件已於 2026-08-24 移除。）
3. **窄螢幕要退回 `position: relative` ＋ `display: none`** —— pane 若維持絕對定位，
   `main.view` 就沒有內在高度，解鎖頁捲之後整頁撐不開。

### ★ 轉場動畫：動蓋在上面的東西，不要動內容

第一版轉場是讓 view 的根節點做 `opacity` ＋ `translateY` 進場，結果**反而更頓**：
對 5,347 節點的子樹（或數百列的表格）做動畫，瀏覽器得把整層重新光柵化。
實測換頁到總覽的平均每幀 **23ms → 39ms**。

改成只動兩個 pseudo element 之後，動的東西恆定是兩層純色，與頁面多重無關。
第二個坑是**面積**：

| 轉場做法 | 換頁平均每幀 |
| --- | --- |
| 全幅半透明暗幕 | 36.9 ms |
| 只留上緣光帶 | 30.3 ms |
| **窄光帶掃過（現行）** | **28.5 ms** |
| 完全不做轉場動畫 | 29.5 ms |

窄光帶已經與「不做動畫」同一水準；全幅遮罩則要每幀把整個畫面重新混色。
**要加轉場效果時守住這兩條：動的是覆蓋層、動的面積要小。**
（現行寬度已再縮到 33%、時長 1s —— 使用者 2026-08-20 指定，面積更小、成本只會更低。）

### ⛔ 殼上不要放 `backdrop-filter`（2026-08-21，最大的一筆）

`.rail` 與 `.top-hud` 原本各掛一個 `backdrop-filter: blur()`。實測**一支就吃掉 11ms/幀**：

| | 總覽閒置每幀 |
| --- | --- |
| 有 backdrop-filter | **27.3 ms**（≈37fps） |
| 移除後 | **15.4 ms**（≈64fps） |

原因：rail 是 64×1080 的長條、header 橫跨整個畫面，**只要主視覺有任何動畫在跑，
它們每一幀都要把背後重新模糊一次**。而背後只有一層平滑的漸層 ——
**模糊一片平滑漸層，視覺上完全看不出差別**（移除前後截圖比對無差異），等於花 11ms 買 0。

而且它會**連坐**：移除之前，主視覺的每一組動畫看起來都很貴（關掉全部動畫可省 9.7ms）；
移除之後**每一組動畫都變成免費**（關與不關都是 15.6ms）——
那 9.7ms 從來不是動畫的成本，是動畫**觸發模糊重算**的成本。
⚠️ 之後量到「動畫很貴」時，先確認畫面上有沒有 `backdrop-filter` 在連坐。

玻璃效果只留給**真正壓在內容之上**的浮層：modal／指令列／dock／toast／tooltip。

### ⚠️ hover 的輝光走 opacity，不要 `transition: box-shadow`

`transition: box-shadow` 會在 .18s 內把整片模糊陰影重畫十幾次（單張卡 +3ms/幀、五張 +6.6ms）。
改為一層 `.card::after` 承載 hover 態的輝光、只過場 `opacity`（合成層屬性）後降到 +1ms。
⚠️ `::before` 已被 `.card.is-running` 的左緣光棒佔用，所以用 `::after`。

### ⚠️ 一次塞幾百列 DOM 會產生 long task

用 `PerformanceObserver({entryTypes:['longtask']})` 量得出來，`requestAnimationFrame`
的平均值看不出來（工作會被算進「一幀很長」而不是「很多幀」）。已處理的兩處：

- **報告頁**：200 列 × 9 格一次 `innerHTML` → **71ms ＋ 89ms 兩個 long task**。
  改為先塞 25 列、其餘每個 rAF 補一批 → 長任務消失。
- **總覽 `resume()`**：五個 draw 疊在同一幀 → 待辦與熱度條延到下一幀。
- **案例樹**：`.tree .children` 加 `content-visibility: auto`，展開後畫面外的分支不參與排版。

📌 **仍在的**：首次進入某一頁（模組載入＋首次建構）仍有約 50–60ms 的長任務，
且在 headless 下量測起伏很大。這是各 view 自己的建構成本，要再壓就得動 `renderTree` 的分批，
評估後**這一輪沒做**（動到選取與展開狀態，風險與收益不成比例）。

### ⚠️ 進度更新不要重建場景

`drawHero()` 的簽章**不含進度百分比** —— 它每幾秒變一次，列進簽章等於每幾秒重建 5,347 個節點，
跑測試時整個畫面會週期性地頓。進度改由 `updateHeroRuns()` 原地改屬性
（標籤的 `rt-fill` 寬度、`rt-pct` 文字、`run-arc` 的 points），只有**階段變化**才重建。

### ⚠️ 換頁回總覽不要空等 API

`views/overview.js` 的 `knowledge`／`health`／`bugs`／`todos`／`cases` 都是**模組層變數**，
離開總覽時不會被清掉 —— 第二次以後進來其實資料早就在手上。
先前卻仍是 `await Promise.all([四支 API])` 之後才畫，實測那段空窗 **≈ 282ms API ＋ 37ms 繪製**，
而主視覺佔了整頁大半面積，看起來就是**先黑一下才顯示**（2026-08-20 使用者回報）。

修法是 mount 內先 `if (knowledge) { drawHero(); drawTop(); drawTodo(); drawHeat(); }`，
資料回來再畫一次 —— 同一份程式碼跑兩趟，不必另做骨架屏。修正後首幀 **34～77ms**。
新增依賴外部資料的區塊時，記得一併加進這個「先畫快取」的清單。
