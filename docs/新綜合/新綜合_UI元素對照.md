### API 契約：`PUT /api/LayOffSetting` 的併發偵測旗標（2026-09-09 實測確認用途）

送出的每筆 `settings` 除了要改的值，還要帶 **`expectedIsSelectionDetailEnabled`＝送出前
該筆的實際 `isSelectionDetailEnabled`**。值對不上時整個請求被拒：

```
HTTP 400　选项明细开关已变动，请确认后重新送出
```

不帶這個欄位也會被當成對不上而 400，整批（含其他 55 筆玩法）一起失敗。做法是先
`GET /api/LayOffSetting?gameId=<彩種>` 取當下值，逐筆填進 payload 再 PUT，即回 204。

⭐ 這推翻了先前「用途待查」的記載（`tests/xzh/test_system_setting.py` B62 檔頭曾記為
「懷疑是後端用來偵測併發修改，用途仍待查」）：2026-09-09 還原英國天天彩 `aaa111` 的
`pickTwoHitBonus` 時實際撞到並解除，確認就是**樂觀鎖**。批次收尾用 API 還原父設定時
一定會遇到，因為測試過程本身就會改動這個開關。

### 2.1 ⭐ 代表列 → 注單層葉的映射（2026-09-18 實測；寫案例前必讀）

**設定頁／賠率頁看到的列，不等於注單層的 `playTypeId`。** 有兩組是「代表列」，一列在注單層對應多個獨立玩法 id：

| 代表列 | 設定頁列數 | 注單層葉數 | 葉的 `playTypeId` |
| --- | --- | --- | --- |
| 七碼 `sevenNumberOdd{k}`（k＝0～7） | 8 | **32** | `sevenNumberOdd{k}`／`sevenNumberBig{k}`／`sevenNumberEven{m}`／`sevenNumberSmall{m}`；`selection` 為空字串，葉即 `playTypeId` |
| 兩面 `twoWay` | 1 | **5** | `positionBigSmall`／`positionOddEven`／`positionDigitSumOddEven`／`positionTailBigSmall`／`sumBigSmall` |

- **七碼映射**：`sevenNumberOdd{k}` → `Odd{k}`、`Big{k}`、`Even{7−k}`、`Small{7−k}`。
  事件等價：单k ≡ 双(7−k)、大k ≡ 小(7−k) ⇒ 同組四葉只有兩個獨立事件。
  已用 odds 通道實證 5 組（k＝0,2,3,5,7）：`Big0`→210、`Even7`→210、`Small0`→161、`Big7`→161、`Even2`→5.68，皆等於代表列 odds。
- **兩面的 5 個葉不在 101 列（差分設定）或 102 列（賠率設定）清單中**，odds 全等於 `twoWay` 的 1.974。

> ⛔ **寫案例時不可假設「下注玩法 ID ＝ 設定玩法 ID」。** 實測 `positionOddEven`（位置单双）不在任一份清單裡，
> 其定價與差分掛在 `twoWay`。同理，一注 `twoWay` 只覆蓋 5 個葉中的 1 個、一注七碼只覆蓋 32 葉中的 1 個——
> **不能當成「一般玩法已驗」或「七碼已驗」**。稽核工具的對應防線見
> `tools/xzh_qa/odds_gap_audit.py` 的 `SEVEN_LEAF_PREFIXES`／`TWO_WAY_LEAF_PLAYS`
> （2026-09-18 補；先前只認 `sevenNumberOdd` 前綴，`sevenNumberBig3` 標成 standard 會直接通過而繞過四葉檢查）。

原始佐證：`scratchpad/gap-b101-20260918-batch3/leafmap.json`、`branch-probe.json`。

### 4.1 表格 DOM 結構（2026-09-16 實測，開發賠率差 pytest 框架時發現）

- 佔成報表的 `<thead>` 是**兩層**：第一層為分組表頭（「会员」colspan=4／「一级代理」colspan=2／「公司」colspan=8），另有第一欄「帳號」與第二欄「昵称」各 rowspan=2；第二層才是實際對應 tbody 的 14 個葉欄。**直接 `thead th` 會讀到 19 個表頭，但 tbody 每列只有 16 個 `td`** —— 依表頭出現順序去對應欄位會整排錯位，必須依 rowspan/colspan 展開後才能正確配對。
- **第一欄的欄名會隨下鑽層級變動**（公司層顯示「一级代理」，下鑽一層後變「二级代理」……），不存在固定的「账号」欄名；不可拿欄名字串當鍵去找該欄，否則會讀回空 dict，出現「UI 與 API 一致」的假通過（兩邊都是空值）。
- 葉欄名有重複（「盈亏」出現 3 次），須用「分組／葉欄」的合成名稱才能唯一指到「赔率差金额」。
- 正確讀法已實作於 [`tools/xzh_qa/pages/odds_gap_report_page.py`](../../tools/xzh_qa/pages/odds_gap_report_page.py) 的 `_READ_TABLE_JS`，新增讀表格的案例直接沿用該函式，不要重寫一份 thead 解析。

### 4.2 篩選控制項的實際型別（2026-09-16 實測）

- 「结算状态」是 **radio**（`已结算`／`未结算`，同一個 `name`），不是下拉選單。2026-09-29 實測：外觀是 el-segmented，radio input 為隱藏元素，直接 `check()` 會逾時；須點包含該 input 的可見 `.el-segmented__item`，再核對已選中（「已结算」是預設值，所以只查已結算時不會發現）。
- 日期起訖是 placeholder 為「开始日期」「结束日期」的 input（`role=combobox`）。
- 彩種篩選是「游戏 14/14」按鈕展開後的一組 checkbox，**預設 14 個全選**；送出查詢的 API 參數 `gameIds` 是**重複出現的同名參數**（`gameIds=a&gameIds=b`），不是逗號分隔字串。讀報表時若沒注意到預設全選，容易誤以為查詢只涵蓋賠率差適用的三個彩種。
- 2026-09-16 補驗：checkbox 的 `input.el-checkbox__original` 是隱藏元素；先點「清除」，再點包含指定 checkbox 的可見 `label.el-checkbox`，最後用 `is_checked()` 核對。直接 `.check()` 隱藏 input 會逾時，屬定位問題。
- 另有快捷按鈕「今天／昨天／本周／上周／本月／上月」，以及「查询」「返回」。

### 4.3 導覽選單定位陷阱（2026-09-16 實測）

- `get_by_role("menuitem", name="报表")` 必須加 `exact=True`。進入報表頁後子選單會展開成「占成报表／玩法报表／货量折扣报表」，非精確比對會一次命中 4 個 menuitem，觸發 Playwright strict mode violation（第二次呼叫導覽時才會炸，第一次可能因為子選單尚未展開而不會發現）。

### 4.4 注單查詢完整性與資料來源（2026-09-16）

- 會員注單 GET 必須明確傳 `date`、重複的 `gameIds`、`settlementState=settled`、`pageIndex`（由1起）及 `pageSize`。回應依 `totalCount`／`pageCount` 遍歷，驗證總數穩定、所有頁讀齊、`serialNumber` 無重複。
