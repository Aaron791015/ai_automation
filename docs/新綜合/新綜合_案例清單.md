## 0.2 test_platform 案例詳情欄位

「飛單選項明細設置」在 `test_platform` 會依序顯示六個區塊：

1. **前置條件**：列出帳號、頁面、期別與設定還原／保留條件。
2. **測試範圍**：列出實際涵蓋的彩種、玩法與選項。
3. **步驟**：只顯示 QA 可在畫面上執行的操作與觀察。
4. **判準（attach 佐證）**：顯示每一步可直接比對的預期結果。
5. **佐證方式**：提示應保留截圖、頁面值，以及需要時的自動化 API／網路紀錄。
6. **已知問題**：獨立顯示已確認或待追蹤的現象，不混入正確判準。

2026-09-11 依 Aaron 要求統一風格：33 個函式（參數化後35條）以函式 docstring 的「平台案例：」文件作為上述內容來源，舊案例仍依 fixture／附件解析。步驟統一2～4步，預期結果與執行附件分開；没有已知問題時不顯示空白區塊。實際測試斷言、資料、參數與操作不變。

## 0.2 三彩種功能層延伸與最小飛單額交叉驗證（2026-08-31 設計並實作完成）

B26~B54 那批把 K4／K7 從結構到行為分了六層驗證鏈（見 §4），但收工後盤點時發現兩個缺口
（過程見對話紀錄，已回寫 `testcase-design` skill §6 新增的「抽樣依據可證偽」規則）：

1. **B28~B36 這批功能層案例全部只在預設彩種（香港六合彩）驗過**——B27 做結構性比對時，

   等於推翻了「三彩種共用同一份資料結構」這個先前用來收斂功能層測試範圍的假設。
   按新補的 skill 規則，抽樣依據被推翻後必須回頭展開受影響的案例——這批（**B55～B59**）就是回頭展開的結果。

   「自動飛單」與「每選項自留上限」兩欄受明細設定開關影響，「最小飛單額」是否受影響只是**隱含在 B30 裡沒被排除**，

地基沒驗就往上疊，疊出來的每條案例都可能在測一個不存在的行為。
