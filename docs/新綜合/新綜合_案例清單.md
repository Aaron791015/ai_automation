## 0.2 三彩種功能層延伸與最小飛單額交叉驗證（2026-08-31 設計並實作完成）

B26~B54 那批把 K4／K7 從結構到行為分了六層驗證鏈（見 §4），但收工後盤點時發現兩個缺口
（過程見對話紀錄，已回寫 `testcase-design` skill §6 新增的「抽樣依據可證偽」規則）：

1. **B28~B36 這批功能層案例全部只在預設彩種（香港六合彩）驗過**——B27 做結構性比對時，
   自己驗出三彩種鎖定列數落差極大（港 70/70、英 6/70、賓 13/70），且只有香港六合彩有 8 個分組按鈕，
   等於推翻了「三彩種共用同一份資料結構」這個先前用來收斂功能層測試範圍的假設。
   按新補的 skill 規則，抽樣依據被推翻後必須回頭展開受影響的案例——這批（**B55～B59**）就是回頭展開的結果。
2. **「最小飛單額」從未被納入「開啟飛單選項明細設定」的互斥/耦合檢查**——B28／B33 只確認了
   「自動飛單」與「每選項自留上限」兩欄受明細設定開關影響，「最小飛單額」是否受影響只是**隱含在 B30 裡沒被排除**，
   沒有案例明確斷言過。**B60～B62** 補上這張決策表的第三欄，並比照 B35 查是否有對稱的整列持久化陷阱。

✅ **2026-08-31 已全部實作成 pytest 並跑通過**（交接檔 T29 已結案）。重大發現：
①B55 證實「狀態自洽」判準（不要求全部鎖定）在英國天天彩／賓果六合彩皆成立，環境資料健康；
②B58 網路攔截確認英國天天彩 `gameId=ukLucky7`、賓果六合彩 `gameId=bingo6`，排除「彩種切換沒切換
查詢參數」的混淆假設；③**B62 用網路攔截證實「最小飛單額」與「每選項自留上限」（B35）有對稱的
整列持久化陷阱**——payload 帶 `isSelectionDetailEnabled` 欄位，會把 UI 上尚未持久化的解鎖狀態一併
送出，reload 後也確實仍是解鎖，附帶觀察到 `expectedIsSelectionDetailEnabled` 欄位此時值與送出值
相反（用途待查，非本次範圍）。

兩批皆為 **[邏輯驗證]／[功能驗證]**，多數 oracle 標「待驗」——沿用既有案例（B27~B35）已建立的事實作對照基準，
但沒有先驗證過在其他彩種／其他欄位是否成立，不可預先假設答案，這正是本次要補的驗證動作本身。

## 4. 驗證鏈展開範例（一個功能點推出多條案例）

2. B2：下限邊界值 0／負數（異常輸入）

**這組案例的主軸是一個教訓：一個功能點可以每條案例都通過、覆蓋率標到最高，卻從沒驗過它到底有沒有在做它該做的事。**

**第一層 — 結構在不在**（B26、B27、B40、B41、B42）
先確認欄位齊全、列數對得上、分類數對得上，**才有資格談行為驗證**（同一套做法用在 C7~C9／C15 驗一級代理）。
本次新增 **B27／B42 三彩種軸線**——先前所有飛單案例都只跑在預設彩種上，但機制文件 §5.2 明寫 8 個子選單「皆依目前選中的彩種分別設定」，等於**有三分之二的設定面從沒被看過**。

**第二層 — 我以為的機制是真的嗎**（B29、B34）
⭐ 這層是本次新增的。B35 的「整列持久化陷阱」與那套繁複的鎖回程序，整個建立在「切換明細設定純屬前端、不送 API」與「保存按鈕對這欄無效」兩個假設上，
而**機制文件與 POM 對後者的說法直接矛盾**（見 B29），前者則從未被反向驗證過。
地基沒驗就往上疊，疊出來的每條案例都可能在測一個不存在的行為。

**第三層 — 設定值存不存得住**（B30~B33、B35、B36、B43~B50）
自檢不變量（存進去＝讀出來）、邊界值、互斥狀態機、逐列獨立性、批次工具、payload 資料模型。
**舊的 17 條案例全部落在這一層**——它們是對的，但它們合起來只證明了一件事：這個設定頁的**表單功能**正常。

**第四層 — 前端擋住不等於後端擋住**（B32）
B30／B31 只證明前端會拒絕負數。⭐ 繞過 UI 直接打 `PUT /api/LayOffSetting` 從沒做過（§5④）。

**第五層 — 聲明等於行為嗎**（B38、B49）
⭐ 兩處系統**自己講出口**、卻沒人驗過它是否兌現的宣告：
K7 確認框說「飛單設定的金額將會失效、自動出貨將變更為手動模式」（從沒在 K4 側檢查過），
「比大小」畫面說「共用自留上限將存為 0、所有組合無條件全飛」（從沒比對過 payload）。
**畫面文字是待驗的宣告，不是 oracle。**

**第六層 — 它真的有飛單嗎**（B51、B52、B53）
⭐⭐ **這才是飛單設置存在的理由，而至今一條都沒驗過。**
機制文件 §5.2 定義它是「注單超過公司自留額度時**自動轉嫁出去**分散風險」——
前五層全部通過，也只證明了「額度設定得進去」，完全沒碰過「超額之後真的轉嫁了嗎」（§5① 可設定 vs 真生效、§5⑩ 時序邊界）。
B53 另外提一個先前沒人想過的風險：**「排程約 1 分鐘」與賓果六合彩「1~2 分鐘一期」是同一個數量級**，低頻彩種永遠碰不到這個競態。

**貫穿各層 — 環境本身會不會騙你**（B28、B54）
B28 先掃出解鎖殘留列，避免拿髒環境當基準；B54 查 T12 的週期性導回會不會讓 K7 的多步驟保存靜默失敗——
⭐ **這條同時是測試穩定性風險與產品風險**，先前沒有人把 T12 跟 K7 連起來看。
