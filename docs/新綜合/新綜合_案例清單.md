## 0. 現況誠實說明（動手寫 pytest 前必讀）

首次探索目前多數功能點停在 **L1**（選單/欄位清點過，賠率公式與判定邏輯未查），且**前台網址尚未確認**（矩陣 I1 阻塞）——
凡「被測行為」需要走前台送出投注的案例，目前**只能列框架、不能列具體步驟與斷言**，
硬寫出來的 oracle 會是我自己編的，不是真的規格。

三分法標記：
- **✅ 可執行**：資訊足夠、不依賴 blocked 項，可以直接轉 pytest
- **⛔ blocked**：依賴前台網址（I1）解封，目前只占位
- **⚠️ 待深挖**：需要先完成 T3（21 種玩法賠率公式）或 T7（五來源交叉的剩餘四個來源）才能寫出有依據的 oracle，**不適用，不計入現階段案例數**

## 1. 批次排序（依阻塞關係，見 testcase-design §7）

```
批次 A 登入與環境（建立前提）
批次 B 系統設置類（QAT Web/UI 寫入已預先授權，可直接做）
批次 C 規則展示比對（L1→L2 淺案例）
批次 D 核心邊界規則（風險最高，等待或製造情境）
批次 E 報表家族（依賴真實下注資料）
批次 F 跟單機制
批次 G 前台下注流程（⛔ blocked，待前台網址）
```

## 3. 依賴順序

```
A1 → A2、A3、A4（同一批登入案例，無先後限制）
B1~B5（系統設置類，彼此獨立，可任意順序）
C1~C3（獨立，可任意順序）
D1（依賴：賓果六合彩摇出不足 7 個 1~49 號碼的邊界情境——低機率事件，
     需先確認 QAT 有無辦法人為製造，見矩陣「抽樣與收斂備註」）
E1、E2（依賴：H5 開獎歷史需已有資料；E2 依賴目前空狀態，一旦前台開通有真實下注後需重新設計）
F1（獨立）→ F2（依賴 G 批次前台解封）
G1~G4（全部依賴 I1 前台網址解封 ＋ T3 賠率公式查明）
```

## 4. 驗證鏈展開範例（一個功能點推出多條案例）

以矩陣項 **K6 投注限額** 為例，展開為：
1. B1：正常改值＋保存＋讀回一致（基本自檢）
2. B2：下限邊界值 0／負數（異常輸入）
3.（待前台解封後）G 批次新增：前台下注金額超過「單注上限」→ 送出應被拒絕或金額被截斷至上限（這是**服務條款第 7 條的直接被測行為**，目前列於批次 G 占位，尚未展開成具體案例）
4.（待前台解封後）G 批次新增：單一玩法多筆注單加總超過「單項上限」→ 超出部分應被公司取消（服務條款第 7 條後半句）
