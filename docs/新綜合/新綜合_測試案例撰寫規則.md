## Step 1：確認測試目的

先從原始需求、既有案例或自動化程式理解：

* 這個案例要測什麼功能
* 要做什麼操作
* 要確認什麼結果

不可自行擴大原本測試範圍。

---

## Step 2：確認實際 UI 名稱

案例中只要出現：頁面名稱、欄位名稱、按鈕、開關、玩法、表頭、提示文字、設定區塊——

**必須優先使用**：
1. 實際 UI 畫面
2. [`新綜合_UI元素對照.md`](新綜合_UI元素對照.md)

**不可根據**：Python 變數、locator 名稱、API 欄位、舊案例、AI 自己理解，自行翻譯成 UI 名稱。

> ⚠️ **UI 名稱不是「挑一個看起來對的」**——同一頁面常有多個結構家族／情境各自的正式名稱
> （例如「飛單選項明細設置」裡標準型玩法用「每選項自留上限」、組合型玩法用「共用自留上限」，
> 兩者不可互相取代，見 `新綜合_UI元素對照.md` §1）。查不到時去看實際畫面，不要用猜的、
> 也不要沿用舊案例可能已經寫錯的措辭。
>
> 若 `新綜合_UI元素對照.md` 尚未收錄要用到的頁面／欄位，先去實際 UI 畫面核對，
> 核對完回頭補進該檔（依 `writeback` skill §3 的回寫必做步驟），不要把新查到的名稱只留在
> 這一條案例裡、下次又要重查一次。

---

## Step 3：確認測試覆蓋範圍

目前彩種：英國天天彩、香港六合彩、賓果六合彩。

只要功能適用於玩法，**三個彩種都必須執行**。玩法覆蓋範圍的完整定義見附錄 B，
核心原則：**禁止代表玩法或抽樣**，除非案例本身明確聲明某彩種／某玩法不適用。

## Step 4：產生案例名稱

格式：`[測試類型] 案例編號：功能名稱：實際操作後要確認的結果`

標題必須讓 QA **只看標題**就知道「做什麼操作＋要確認什麼結果」，優先用
「實際操作＋結果是否正確」造句。

不要寫：「自留上限持久化驗證」
改成：「修改每選項自留上限並保存後，重新整理資料是否保留」（欄位名稱依實際測的結構家族，
查 `新綜合_UI元素對照.md`）

不要寫：「總開關狀態轉移驗證」
改成：「關閉／開啟總開關後，各玩法欄位是否正確鎖定與恢復」

> 📝 **2026-09-02 使用者補充**：案例只要有輸出 Step 5 的「測試範圍」區塊，**標題就不要再重複
> 「所有彩種」「所有標準型玩法／所有組合型玩法／所有玩法分類」這類覆蓋範圍字眼**——
> 涵蓋範圍已由測試範圍區塊唯一承載，標題重講一次是純重複，不屬於「操作＋結果」。
>
> 不要寫：「所有彩種所有標準型玩法修改自留上限並保存後重新整理資料是否保留」
> 改成：「標準型玩法修改自留上限並保存後重新整理資料是否保留」（保留「標準型玩法」是因為
> 它指出被測的是哪個 UI 結構家族，這是功能識別、不是覆蓋範圍宣告；拿掉的只有「所有彩種」
> 與「所有」這個全稱量詞）
>
> ⚠️ 案例**沒有**測試範圍區塊時（單一彩種／單一玩法、或只是畫面觀察），標題不受此限，
> 該怎麼寫仍照本節其餘規則。

⛔ **禁用詞**（出現在標題／步驟／判準都算）：持久化、roundtrip、狀態轉移、分支、邊界行為、
scope、套用範圍驗證、穩定性觀察、reload，以及「XX 驗證」這種只收尾不講操作與結果的抽象詞
（狀態轉移驗證、roundtrip 驗證、聲明驗證、套用範圍驗證、穩定性觀察、邊界值驗證）。
固定翻譯對照見附錄 A。

## Step 5：輸出測試範圍

只要案例涉及**多個彩種或多個玩法**，就必須在「步驟」之前輸出一段「測試範圍」區塊——
用途是讓 QA 不必讀完步驟細節，一眼就能確認本案例實際要執行哪些彩種、哪些玩法。

格式：

```
測試範圍：

彩種：
* 英國天天彩
* 香港六合彩
* 賓果六合彩

玩法：
* [依本案例實際適用範圍列出]
```

彩種：涉及多彩種時逐一列出三個彩種名稱，不寫「三彩種」這種概括詞帶過。

玩法（依附錄 B 的固定清單展開，不可自行縮減或省略）：
* 案例測試「所有標準型玩法」→ 完整列出附錄 B 的 15 個標準型玩法。
* 案例測試「所有組合型玩法」→ 完整列出附錄 B 的 10 個組合型玩法。
* 案例測試「所有玩法」→ 標準型 15 個＋組合型 10 個，共 25 個全部列出。
* 案例只適用部分玩法 → 依實際適用範圍列出對應玩法名稱，不可用「代表玩法」帶過；
  並在測試範圍區塊註明為何只適用這些玩法。

⚠️ **完整列出玩法清單只在「測試範圍」區塊做一次**——步驟（Step 6）與判準（Step 7）
延續精簡寫法，用「所有標準型玩法」等概括詞回指本區塊，**不要在判準裡重複列出完整玩法清單**。

## Step 6：產生步驟

**2～4 步**，每一步都要是 QA **可以直接照著操作**的內容——⛔ 不可只寫「驗證邏輯」
「驗證行為」「確認結果」「驗證畫面」「驗證邊界值」這種說了等於沒說的動詞。

步驟需包含：
1. 導覽到哪個頁面
2. 執行什麼操作
3. 要觀察什麼畫面或資料結果
4. 必要時還原原始設定

要點：
* **畫面驗證不能只寫「核對畫面元素」**——要明確指出檢查的元素類型：欄位名稱、輸入框、
  開關、勾選項目、按鈕、表頭、設定區塊、提示文字。
* **功能驗證要明確說明**：修改什麼、是否保存、是否重新整理、重新整理後資料應該是什麼狀態。
* **測異常資料（負數、超大值、空值、特殊字元等）時要明確描述**：是否允許輸入、是否允許保存、
  是否顯示提示、欄位值是否被修正、重新整理後資料結果。
* **已明確指定的特殊功能元件名稱要保留、不可全部改寫成「相關畫面元素」**——例如关连、
  每選項自留上限／共用自留上限（依結構家族）、自動觸發、快速設置、保存。精簡格式只是不逐一
  展開「玩法／分類清單」（見附錄 B、Step 5），不是把功能元件名稱也一併抹掉。

---

## Step 7：產生判準

* **有明確規格時，直接寫出具體正確結果**，不要只寫抽象的「符合預期」／「驗證通過」。
  例：~~邊界值驗證通過~~ → 「負數輸入後應顯示為 0，重新整理後仍為 0；666666 應可正常保存，
  重新整理後仍保留 666666。」
* **尚未提供明確規格時**，才可以用：
  ```
  判準（attach 佐證）
  驗證通過
  ```
* **實際測試失敗時，固定輸出失敗格式**（只列失敗項目，不列已通過項目）：
  ```
  判準（attach 佐證）
  驗證失敗：
  - [彩種]／[玩法]：[具體異常狀況]
  ```
  異常狀況要具體到「哪個彩種」＋「哪個玩法」＋「哪個功能或欄位」＋「實際發生什麼異常」，
  禁止「功能異常」「有問題」「驗證失敗」這種沒有具體內容的說法。
* **不同類型玩法的判準不同時可以分開寫**：
  ```
  判準（attach 佐證）

  標準型玩法：
  * [具體正確結果]

  組合型玩法：
  * [具體正確結果]
  ```
  但**不要在判準這裡重新列出 15 個或 10 個玩法名稱**——完整玩法清單只出現在 Step 5
  的「測試範圍」區塊。

## Step 8：輸出前自我檢查

> ⚠️ **2026-09-02 教訓：「改寫」也算數，不是只有全新案例才要跑這節**——
> B47（為了解掉卡住的 skip）與 B68（今天新寫）都是因為改寫時只顧著解掉功能問題本身
> （reload 卡死、覆蓋缺口），沒有回頭跑本節，結果分別漏了禁用詞「持久化」（標題＋步驟共
> 3 處）與標題重複列出覆蓋範圍字眼「所有玩法分類」，直到使用者事後指出才發現、修正。
> **任何動到既有案例標題／步驟／判準的原因**（修 bug、解 skip、擴充覆蓋、調整斷言邏輯……
> 不限於「新增案例」）都要重跑本節；改完仍要跑 `python scripts\lint_cases.py --product 新綜合`
> 並用 `POST /api/cases/rebuild` 確認 test_platform 畫面已同步。

輸出案例前，逐項確認：

* [ ] 標題是否一眼看得懂要測什麼
* [ ] 是否仍有持久化、roundtrip、branch、scope、reload 等工程術語（見附錄 A 禁用詞）
* [ ] UI 名稱是否與 `新綜合_UI元素對照.md`／實際畫面完全一致（**不是自己翻譯或沿用舊案例**）
* [ ] 是否誤把程式變數名稱、locator、API 欄位名當成 UI 名稱
* [ ] 涉及多彩種或多玩法時，是否有輸出「測試範圍」區塊（見 Step 5）
* [ ] 三個彩種是否都有覆蓋（見附錄 B）
* [ ] 所有適用玩法是否都有覆蓋，是否偷偷使用代表玩法或抽樣
* [ ] 測試範圍區塊是否完整展開彩種與玩法清單，且判準裡沒有重複列出完整玩法清單
* [ ] 有測試範圍區塊時，標題裡是否還留著「所有彩種」「所有標準型／組合型玩法」等覆蓋範圍字眼（應拿掉，見 Step 4）
* [ ] 步驟是否能讓 QA 直接操作（2～4 步、無「驗證邏輯」這類空話）
* [ ] 判準是否明確可判斷 Pass／Fail
* [ ] 是否自行新增原需求沒有的驗證內容

任何一項不符合，都必須先修正再輸出。

固定輸出格式：

```
[測試類型] 案例編號：功能名稱：實際操作後要確認的結果

測試範圍：

彩種：
* ...

玩法：
* ...

步驟：
1. ...
2. ...
3. ...

判準（attach 佐證）
（依 Step 7 規則，具體結果／失敗清單／依玩法類型分開寫，其中一種）
```

⚠️ **只改文件／描述性文字，不動實際測試邏輯**——pytest 的 `assert` 斷言、Page Object 呼叫、
資料驗證迴圈**維持不變**，「精簡」「易讀」指的都是人類可讀文字，不是刪掉實際會執行的驗證程式碼。

## 附錄 A：固定翻譯對照表

遇到工程師用語就照這樣改寫，不要自己另造說法：

| 工程師用語 | 改寫成 |
| --- | --- |
| 持久化 | 重新整理頁面後資料是否保留 |
| reload | 重新整理頁面 |
| 取消分支 | 點擊「取消」後設定是否維持不變 |
| 邊界行為 | 是否允許輸入、保存，以及重新整理後資料結果 |
| retentionCap=0 | 未勾選項目的自留上限應為 0（欄位正式 UI 名稱查 `新綜合_UI元素對照.md`） |
| 套用範圍 | 是否只影響指定項目 |

對照範例（K7 案例真實踩過的例子）：
- ~~總開關狀態轉移驗證~~ → 總開關切換後各玩法欄位狀態是否正確
- ~~標準型代表樣本 roundtrip 驗證~~ → 修改自留上限後保存與重新整理資料是否保留
- ~~快速設置面板套用範圍驗證~~ → 快速設置是否只套用已勾選項目
- ~~頁面停留穩定性觀察~~ → 頁面閒置後是否維持在目前頁面

## 附錄 B：三彩種全玩法**全選項**覆蓋範圍（永久規則，禁止抽樣）

新綜合任何「適用於玩法」的測試案例（涉及分類、欄位、設定、操作流程），只要功能本身對該
玩法適用，就必須：

1. 完整執行**三個彩種**（英國天天彩／香港六合彩／賓果六合彩）——不可只測預設彩種。
2. 每個彩種底下**所有玩法**全部執行——不可只挑「代表分類」「代表樣本」「標準型代表樣本」
   這類抽樣寫法。
3. 每個玩法底下**所有選項（表格所有列）**全部驗證（2026-09-02 使用者裁示新增的第三維度）——
   不可只測「选项」欄第 1 列或抽樣少數列。標準型 15 玩法的列數見
   `新綜合_案例清單.md` B68／`tests/xzh` 的 `_STANDARD_CATEGORIES_15`（合計 343 列/彩種）。
   - **讀取類驗證**（鎖定狀態、開關狀態、套用結果）：一次 `page.evaluate` 撈整張表逐列斷言，
     成本極低，沒有任何理由抽樣。
   - **寫入類驗證**（逐格輸入邊界值）：逐格填完**整個分類才保存一次**，不可逐格保存
     （執行時間會爆炸）；持久化核對優先用 API GET 逐列讀後端值（CLAUDE.md §5 明文允許的
     「讀取驗證」），UI reload 每分類抽查一次畫面渲染即可。
4. **除非案例本身明確註明「某彩種／某玩法／某選項不適用」**（例如某功能的 UI 只存在於
   特定玩法），否則預設一律視為三彩種、所有玩法、所有選項都要測。

**Why**：先前 K7（飛單選項明細設置）案例大量使用「選代表分類測」的寫法節省執行時間與
維護成本，但使用者認為這樣測不出「其他玩法有沒有問題」，要求往後一律全覆蓋、不允許抽樣。

**案例文字可以精簡，但執行不能抽樣，「測試範圍」區塊是精簡原則的例外**：標題／步驟／判準
（Step 4、6、7）可以保持精簡，不需要逐一列出玩法／分類全部名稱（統一寫「所有玩法」「所有
分類」等概括用語即可）；但 Step 5 的「測試範圍」區塊職責就是完整展開，**不適用**這條精簡
原則——測試範圍必須把彩種與玩法（依「所有標準型玩法／所有組合型玩法／所有玩法」對應的
固定清單）逐一列出。「案例文字可以精簡」跟「實際要測哪些玩法」是兩件事：**實際執行時三
彩種×該彩種所有適用玩法一律全跑，不可抽樣／挑代表**。

**How to apply**（撰寫或改寫案例時）：
- 依 Step 5 先輸出完整展開的「測試範圍」區塊（彩種＋玩法逐一列名）。
- 步驟（Step 6）可寫成「依序切換英國天天彩、香港六合彩、賓果六合彩，針對測試範圍所列玩法
  執行驗證」這類概括句，不需要在步驟裡重複列出玩法名稱。
- 判準（Step 7）失敗時只列出**實際失敗**的「彩種／玩法／欄位／異常內容」，不列已通過項目，
  也不重複列出完整玩法清單。
- 若功能只適用於部分玩法（如快速設置面板只存在於特定 3 個玩法），測試範圍要**明確聲明
  適用範圍與原因**，不能悄悄縮小範圍卻寫得像涵蓋全部。

### 玩法完整清單與「所有玩法」等詞的固定定義

標準型玩法共 15 個：特码、正码、正特码、两面、生肖中、生肖不中、半波、特肖、尾数中、
尾数不中、色波、七码、五行、一肖量、尾数量。

組合型玩法共 10 個：连码、过关、六肖、连肖、连尾、不中、多选中一、特平中、合肖、比大小。

案例文字若使用以下概括詞，一律依此固定範圍展開執行（不可自行縮減）：
- 「所有玩法」＝ 25 個玩法（標準型 15 ＋ 組合型 10）全部執行。
- 「所有標準型玩法」＝ 上列 15 個標準型玩法全部執行。
- 「所有組合型玩法」＝ 上列 10 個組合型玩法全部執行。

## 附錄 C：案例瀏覽器的靜態解析限制（跟內容精簡與否無關，必須遵守）

> **2026-09-11 平台文件支援**：需要精簡平台文字、但保留詳細執行步驟時，可在函式 docstring 首行明確宣告 `平台案例：<標題>`，依序以 `前置條件：`、`測試範圍：`、`步驟：`、`預期結果：`、`已知問題：` 分節，各項一行；步驟2～4項。`實作備註：` 之後保留原技術說明，不匯入平台步驟。匯出器只對明確宣告者優先採用此文件，缺少必要節或步驟數不符會報錯；其他案例仍依下方既有 AST 規則。文件只能描述既有實作，不得把未斷言項目寫成已覆蓋。`lint_cases.py` 繼續檢查執行步驟／附件，文件格式由匯出器與 `test_platform_case_documentation.py` 檢查。

`test_platform` 的案例瀏覽器（`tools/test_platform/collect/pytest_case_export.py`）是
**靜態解析**（AST，`--collect-only` 不執行案例），只讀 `allure.step()`／`allure.attach()`
呼叫本身的字面文字。不管字串長或短，以下限制都成立：

1. **字串必須是單行、不能用隱式多行字串串接**——`ast.literal_eval()` 對跨行拼接的字面
   字串會解析失敗，退回顯示帶引號的原始碼片段。
2. **只解析 `allure.step()`／`allure.attach()` 呼叫本身，docstring 裡手寫的「步驟：」
   「判準：」散文段落完全不會被案例瀏覽器讀取**——docstring 跟實際顯示是兩條互不相通的路，
   兩邊都要改成一致的字串內容（親身教訓：曾經只改 docstring，案例瀏覽器顯示的還是舊的
   `allure.step()` 原始碼）。
3. **迴圈變數若來自執行期才讀得到的值**（如 `for name in sp.category_labels():`），
   案例瀏覽器**永遠沒辦法**把 `f"...{name}..."` 的 `{name}` 換成具體值——這不是 bug，
   是靜態解析（AST，不執行案例）的天生限制。最簡單的解法是**乾脆別在迴圈的
   `allure.step()` 字串裡用變數**，改成固定字面字串（例如 `"核對分類畫面元素"`，不帶
   `{name}`）。
4. `_step_texts()`／`_attach_titles()`／`_helper_names()` 依 `(lineno, col_offset)`
   排序，步驟順序會依原始碼出現順序顯示，`for`／`if` 區塊裡巢狀的步驟不會被排到區塊之後
   （2026-09-01 已修正，見 `pytest_case_export.py` 檔頭註解）。
