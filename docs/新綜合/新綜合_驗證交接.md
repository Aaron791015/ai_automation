### 7.11.2 六肖結構釐清（推翻先前誤判）

先前記錄「六肖的選擇欄位不是 checkbox role，讀到 0」是**檢查方式用錯**——用

`selection` 欄位的 `hit:`／`miss:` 前綴區分屬於哪個區塊。POM 既有的 `block_index` 參數

支援雙區塊，六肖可以直接納入，不需要另外設計互動方式。

   `switch_game()` 後立刻 `select_category()`，總開關畫面已顯示開啟但該分類欄位鎖定狀態未跟上，
   卡滿 `wait_until_category_unlocked()` 的 45 秒逾時。新增
   `_goto_combo_target_and_ensure_switch()`，卡住時 reload 整頁重新導覽當救援手段重試——
   ⚠️ 這跟本節解掉的「驗證持久化要 reload」不是同一個問題，這裡的 reload 只在**進入分類**
   這一步失敗時才當救援，不影響驗證流程完全不用 reload 的設計。
3. **`set_shared_cap()` 的 `press("Tab")` 提交懷疑非同步**：第一次以為是這個造成 B47 大量
   失敗（新增 `_set_shared_cap_confirmed()` 輪詢確認畫面值已更新才繼續），**但加上這個修正
   後失敗清單完全沒變**——後來查出真正原因見下一節，`_set_shared_cap_confirmed()` 保留（防禦
   性寫法，不影響正確性），但不是本次失敗的根因。

### 7.11.7 ⭐ 核心發現：「共用自留上限」套用對象隨「关连／不关连」相反（T38，待裁示）

B47（关连＋共用自留上限保存持久化）第一輪改寫後跑，34/45 個組合失敗，**兩次完整跑下來失敗
清單逐字相同**（不是時序偶發，是穩定可重現的行為）。用 MCP 直接操作 QAT「过关」分類＋API
讀回反覆驗證確認：

| 关连狀態 | 已勾選項的 `retentionCap` | 未勾選項的 `retentionCap` |
| --- | --- | --- |
| 关连（related） | 設定值（如 777） | 強制 0（符合既有 POM 文件記載） |
| **不关连（unrelated）** | **強制 0** | **全部變成設定值（如 777）** |

實測數據（`过关`／`markSix`，`compareBigSmall`同理）：切到「不关连」、填 777、保存後，
API 讀回 27 個未勾選項全部變成 777、唯一勾選的 `1-big` 反而是 0。這解釋了 B47 第一輪失敗的
真正原因——原始設計會 toggle 关连/不关连，toggle 後若落在「不关连」那一側，斷言卻還是預期
「勾選項＝設定值」，注定失敗；「连码」剛好每次 toggle 後都落在「关连」側，才會每次都過。

**這是一個先前沒有任何文件記載過的行為**，POM 檔頭原文只寫「已勾選的組合可以有非0值；未
勾選的組合一律強制為0」，沒有區分「关连／不关连」兩種狀態——現在發現這規則**只在「关连」
狀態下成立**。依 CLAUDE.md §6，這不是「文件寫錯」（沒有人聲明要改），暫記為**疑似缺陷、
待使用者裁示是否開單**（2026-09-02 使用者當場裁示：先記錄，之後視情況決定）。

**已完成的因應**（不管上題怎麼裁定都要做）：
- **B47** 拆成兩個獨立驗證：①單獨切换关连/不关连並保存，只驗 relationMode 持久化，不動
  cap；②固定在①剛確認過的关连狀態下，單獨修改共用自留上限並保存，依①讀到的方向決定預期
  （关连→錨點項應為設定值；不关连→錨點項應強制歸零）。不再於同一次保存內同時改兩者。
- **B49**（設定共用自留上限後已勾選/未勾選金額是否正確）**沒有主動 toggle 关连**，但原本
  假設「勾選拿到值、未勾選歸零」放諸四海皆準——若目標玩法**原本**就是「不关连」，這假設一樣
  會錯。已修正為：**只讀取（不修改）** 目前的关连狀態，依讀到的方向決定預期的
  `expected_marked_cap`／`expected_unmarked_cap`。
- **B64**（负数/超大值邊界）不涉及 relationMode 切換，本身不受此發現影響，但尚未實跑
  確認（見下方待辦）。
