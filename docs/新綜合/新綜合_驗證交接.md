**已確認的產品行為（本輪新發現，皆用 MCP 探索+pytest 雙重驗證）**：
- 波色（紅波/藍波/綠波）選中號碼與號碼球自身顯示的顏色分類（DOM class）完全一致（B69）。

- 切換分類後再切回，快速設置的已選號碼與屬性勾選**不保留**、全部重置（B76）。
- 批次工具（一鍵自動/一鍵手動）**無條件覆蓋全部列**，包含剛手動改過的列，沒有排除邏輯（B80）。

**過程中發現並排除的問題（非產品缺陷，測試方法本身的瑕疵）**：
1. `quick_set_select_by_property()` 點擊 disabled checkbox 會等到 Playwright 預設 30 秒逾時
   ——改用 `force=True, timeout=5000`（鎖定情境下 Element UI 的 disabled checkbox 即使強制
   送出點擊事件也不會真的觸發勾選，不影響「應該鎖住」案例的正確性）。
2. B78 的「保存後立即觸發本次選項自動飛單」checkbox 用 `get_by_role("checkbox")` 直接點擊
   逾時——Element UI 底層 `<input>` 視覺隱藏，跟既有 `select_sub_item()` 檔頭記載的陷阱同一類，
   改用文字定位 `get_by_text(...).click()`。
3. B73/B74 逐一還原49個選項耗時過久導致整條案例卡住——改用「全部設置」批次還原成最常見的
   原始值，只對離群值（如「特码」的選項1=99、選項5=0）逐一修正。

**已記錄的真實環境現況（非測試方法問題）**：
1. ⚠️ 「正特码」在按下 Enter 保存後、下一次 reload 之前，讀 `option_cap_value(1)` 會讀到
   空字串，只有「正特码」出現、其餘14個標準型玩法皆立即正確；重跑兩次穩定重現，輪詢等待
   （5次×300ms）無效。reload 後兩次都正確讀回 0／888888，代表**實際保存的資料沒有錯**，
   只是「填入當下那一刻」的畫面讀值不穩定。疑似跟「正特码」頁面本身有2個table的既知結構
   有關（見 POM `_table()` 檔頭），根因未查——B79 已改成只用 reload 後的值判斷「正特码」，
   其餘14個標準型玩法仍以填入當下與reload後兩者共同判斷。
2. B79 實跑時撞上 T35／§7.2 已記錄的「`page.reload()` 後重新導覽偶爾整整30秒點不到」問題
   （這次是「色波」分類），改用既有的 `_reload_and_navigate_with_retry()` 重試機制後穩定通過
   ——**這個問題本身仍未解決**，只是套用了已有的緩解措施，不是本輪新查出根因。

**環境問題（與案例邏輯無關，過程中排除）**：MCP 瀏覽器 session 與多輪 pytest 執行殘留了
25 個 `chrome.exe` process，導致新的 headless browser 啟動逾時（`BrowserType.launch: Timeout
180000ms exceeded`）——經使用者確認後 `taskkill /F /IM chrome.exe /T` 全部清除，之後恢復正常。
